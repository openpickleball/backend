# CLAUDE.md

This file gives Claude Code guidance for working in this repository.

## What this repository is

The backend for OPEN, the Open Pickleball Evaluation Network: a free, open-source, community-governed pickleball rating network. This repository will hold the services and APIs that store players and matches and serve ratings. The rating math itself lives in the separate `engine` repository.

Planned services, from the project roadmap:

- **Results API:** platforms, clubs, and tournaments submit matches.
- **Ratings and stats API:** any app can read OPEN ratings, history, and stats for free.
- **Organizer tools (backend side):** upload results, confirm starting ratings, review flagged matches.

A test pins the order.

## Account emails

- An Account's email is its login. Forms (through `clean()`) and the manager normalize it: NFKC, strip, then lowercase one character at a time.
- The normalized email must be ASCII, at most 254 characters, and a valid address. The field validator and the manager enforce these rules. Keep every new check on the normalized value, not the raw input.
- The database enforces the column length, case-insensitive uniqueness (`Lower("email")`), and ASCII. It does not normalize. Raw writes (`save()` without `full_clean()`, `bulk_create`, `update`) skip normalization, so create Accounts through the manager or a form.
- Find an Account by email (an identity lookup, such as login or linking) only through `get_user_model().objects.get_by_natural_key()` (or `aget_by_natural_key()`), which compares with the unique constraint's own `Lower("email")` expression. Do not use `email__iexact` or an exact match on raw input: on Postgres `iexact` compares `UPPER()`, which can match accounts the constraint treats as distinct.

## Authentication

ADR 0014 records these decisions. Login and the lookups behind it are the base for identity linking, a security-sensitive area (hard rule 8).

- django-allauth runs headless only (`HEADLESS_ONLY`), at `/_allauth/browser/v1/` (session cookie and CSRF) and `/_allauth/app/v1/` (`X-Session-Token`). Its OpenAPI document is at `/_allauth/openapi.json`, `.yaml`, and `.html`, with OPEN's age check added (ADR 0020). No social login, MFA, or user sessions app is installed: each is its own issue (social login #176, MFA #99 and #117, user sessions #100).
- Login is by email only, and email verification is mandatory: no login before the address is verified. Verification and password reset use emailed links to `FRONTEND_URL` pages, not codes. Sign-up and password reset answer the same way whether or not an Account has the address, and neither mails an address that has no Account.
- An address allauth stores (sign-up, change of address) goes through `AccountAdapter.clean_email` (`apps/accounts/adapter.py`), which normalizes it and applies the Account email rules. An address used to find an Account (login, password reset) must be canonical (`is_canonical_email`): stripping and lowercasing it gives its normalized form, and it is ASCII. A variant that NFKC folds onto an Account's address never logs in and gets no reset mail. The one exception is the Kelvin sign (U+212A), which allauth's email field lowercases to ASCII `k` before OPEN's check, so it reaches the same Account (accepted, ADR 0014). A reset key is mailed only to the Account's own `User.email`.
- allauth's own lookups match any `EmailAddress` row, including another Account's pending change of address. So OPEN overrides allauth's sign-up, password reset request, and email verification views (`apps/accounts/headless_views.py`, served ahead of `allauth.headless.urls` for both clients). Sign-up counts an address as taken only when it is some Account's login, reset finds an active Account only through `get_by_natural_key`, and verify refuses (`email_taken`) an address that is another Account's login. When allauth adds a view that looks up an Account by email, override it the same way, for both clients, with a test on each.
- A save that changes `User.email` (staff in the admin, or any code) deletes the Account's other `EmailAddress` rows in the same transaction (`User.save()`), so an old address never stays tied to the Account. Raw writes (`QuerySet.update`, `bulk_update`, raw SQL, `loaddata`) skip this, so change an Account's email only through a save. When the Account has no row for the new address, its next headless login adds one, unverified.
- Code-based flows stay off (`ACCOUNT_LOGIN_BY_CODE_ENABLED`, `ACCOUNT_EMAIL_VERIFICATION_BY_CODE_ENABLED`, `ACCOUNT_PASSWORD_RESET_BY_CODE_ENABLED`, `ACCOUNT_EMAIL_VERIFICATION_SUPPORTS_CHANGE`). Login by code opens allauth's login code request, which finds an Account with allauth's own lookup. Verification by code together with `ACCOUNT_EMAIL_VERIFICATION_SUPPORTS_CHANGE` opens allauth's change-email input, which skips `clean_email` and the sign-up rule. An issue that turns these on must first override those views like the sign-up, reset, and verify views. It must also add OPEN templates for the emails they send (see Email).
- `AUTHENTICATION_BACKENDS` lists `ModelBackend` first (the admin login and every successful headless login) and OPEN's allauth backend second. Both find the Account through the manager. The admin login does not check email verification; staff Accounts are made by operators.
- allauth's user payload carries no row id (`HeadlessAdapter`). allauth's verification and reset keys do encode a row id (a signed `EmailAddress` id, and the Account id in base36). They are opaque, and only the mailbox owner sees them: the one exception to the row-id rule (see Public identifiers).
- Sign-up takes `birth_year`, `birth_month`, `gender_division` (`mens` or `womens`), `first_name`, and `last_name`, and optionally `city` and `region`, on both clients (`SignupAgeForm`, ADR 0017, ADR 0019, ADR 0022). OPEN's `SignupView` checks allauth's rate limit, then allauth's 409 and 403, then these details, then allauth's input, so a refused age never reaches the email lookup or sends mail. Under 13 gets one fixed `signup_refused` answer and flags the session (`open_signup_refused`), and every later sign-up in that session gets the same answer; `AccountAdapter.logout` keeps the flag. The Player create endpoint sets and honors the same flag: an under-13 or future age there gets one fixed 422 on `body.birth_month`, and so does every later create in that session. Two concurrent requests in one session can lose the flag; ADR 0017 accepts this. The age check (`POST /_allauth/{client}/v1/auth/signup/age-check`, `SignupAgeCheckView`, ADR 0020) runs the same screen on `birth_year` and `birth_month` alone (`SignupBirthForm`, which `SignupAgeForm` extends), in sign-up's order and on sign-up's rate limit counter: a pass writes nothing to the session, and under 13 gets `signup_refused` and flags it. It reads no email address. Sign-up and the check share `_screen_birth()`, so change the screen there. allauth's OpenAPI document lists the check because OPEN serves `/_allauth/openapi.json` and `.yaml` itself (`apps/accounts/openapi.py`, built on allauth's internal `get_schema()`). Read and set the flag only through `apps.players.signup.is_signup_refused()` and `refuse_signup()`. A passing sign-up holds the age, gender division, legal name ("First Last"), first name, and city and region in the session bound to the new Account (`open_signup_details`); read them only through `apps.players.signup.peek_signup_details()` and take them only through `take_signup_details()`. The Player create endpoint takes them once the Player exists, or when the Account already has one (409). Keep the session changing the same way for a new and a taken address, or the app client's session token reveals which it was. In tests, the headless `signup()` helper sends an adult age, a gender division, a made-up name, and a place (`SIGNUP_DETAILS`).
- Protect a first-party API operation with `auth=account_auth` (`config/auth.py`), which accepts either client. `request.auth` is the Account itself on both, so pass it straight to a service. To read or change a session value (the signup details), use `auth_session(request)`: the session the `X-Session-Token` names for the app client, `request.session` for the browser client. Django's middleware saves only `request.session`, so a view that changes the token session calls its `save()`, which keeps the key. A request with no signed-in user gets 401 before any CSRF check; a signed-in session's unsafe request still needs its CSRF token (ADR 0015). Operations for partners will use OAuth tokens instead (#27).
- In tests, drive the flows through the helpers in `apps/accounts/tests/headless.py`. allauth's rate limits use the cache: the accounts tests clear it in an autouse fixture, and any other test that drives allauth's flows must clear it too.

## Audit log

- Write an `AuditEvent` only through `apps.audit.services.record_event()`, inside the same `transaction.atomic()` as the change it records. Record a delete before calling `delete()`. Build `before` and `after` with `snapshot(instance, fields)`, which takes an explicit field list, so a password hash is never captured by accident. `record_event` redacts values under sensitive key names, but never put a secret, token, recovery code, or the value of an identifying personal data field (ADR 0009) in `before`, `after`, or `reason`.
- Audit rows are append-only. In app code the ORM refuses every change or delete. A database trigger (migration `0002_append_only`) refuses `UPDATE`, `DELETE`, and `TRUNCATE` of a non-empty table. Inside a migration, a historical model gets no ORM guard, so only the trigger protects the rows. The trigger does not stop the table's owner or a database superuser, who can disable it. The runtime database role must not own the table: #103 must make sure of that (a comment there asks for it).
- A new action type is a new `AuditAction` value plus its generated migration. The issue that adds a feature records that feature's events, with a test.
- `flush` (and so the teardown of a transactional test) fails once the audit table has a row. Tests that record events should run in a transaction that rolls back (the default `django_db` mark).
- An event's actor is an Account (`actor_user`), a Partner Application (`actor_application`, `record_event(actor_application=...)`), both, or nobody. `actor_user`, `actor_application`, and `target_content_type` use `PROTECT`: an Account or application that has acted cannot be hard-deleted (deactivate an Account; #29 revokes applications), and a content type an event points at cannot be removed. django-oauth-toolkit's `PartnerApplication.user` cascades, so an Account whose application has acted cannot be hard-deleted either. The same holds for an Account or application that submitted a Match (see Matches). Plan account deletion around this.

## Email

ADR 0016 records the outbox decisions (the rules on queuing, sending, retries, and the sweep). The template rules come from issue #36.

- Every email goes through `apps.emails.services.queue_email()`, never `EmailMessage.send()` or `send_mail()` in a request. It stores the rendered message as a `QueuedEmail` row and, after commit, queues `send_queued_email` with only the row's id. allauth's emails reach it through `AccountAdapter.send_mail`. A message must have one recipient and no cc, bcc, reply-to, extra headers, or attachments, and at most one text/html alternative.
- A `QueuedEmail` row holds the address and often a key. It is deleted once sent or finally failed, and the sweep (`sweep_queued_emails`, every 15 minutes) deletes any row older than three days and queues again rows with no attempt in the last hour. Before a retry, `last_attempt_at` is set so the lease ends exactly when the retry is due: the retry claims the row, and any other task for it (a sweep copy, a redelivered message) skips it during the wait, so a row has one retry chain. When the sweep queues a row, it sets `last_attempt_at` to one lease ago, so the queued task can claim it at once but later sweeps skip it for most of an hour. Never register an admin for it, and never log a row's address, subject, or body.
- `ANYMAIL_REQUESTS_TIMEOUT` (5 seconds to connect, 20 to answer) keeps a provider request well under `send_queued_email`'s 60-second soft time limit, so a slow provider is a retried timeout. Keep it so when changing either. It applies only to anymail's requests-based backends, Resend among them. The SES backend uses boto3 and ignores it: a slow SES request reaches the soft time limit, the row is kept, and the sweep retries it about an hour later. Optional tuning, not a switch step: `ANYMAIL["AMAZON_SES_CLIENT_PARAMS"]` with a botocore `Config(connect_timeout=5, read_timeout=20, retries={"max_attempts": 1})` gives SES timeouts backoff retries too.
- `send_queued_email` retries network errors, timeouts, 429, and 5xx (and SMTP and socket errors) up to five times, each wait at most 600 seconds, and treats every other provider error as final. It never logs a provider error's text, which can quote the address: retries and failures carry `EmailSendRetry` and `EmailSendFailed`, which hold only the id, template, error class, and status code. Keep any new log line to those values.
- Delivery is at least once: after a crash between the provider accepting a message and the row's delete, the sweep queues the row again about an hour later (it waits for an hour with no attempt, then for its next 15-minute run), and the message is sent twice.
- A `QueuedEmail` row has no link to the Account. Account deletion (#116) must delete the rows addressed to the Account's addresses; otherwise they age out within three days.
- Email templates live in the root `templates/` directory (`TEMPLATES` `DIRS`), which is searched before app directories, so `templates/account/email/` overrides allauth's own. Every email has `<prefix>_subject.txt`, `<prefix>_message.txt`, and `<prefix>_message.html`, and the message files build on the shared layout in `templates/emails/` (`base_message.txt` and `.html`), whose `reason` block says why the person received it. Text templates turn autoescape off themselves (the text base and every `_subject.txt` wrap in `{% autoescape off %}`), so a new text template extends the base or wraps itself; HTML keeps autoescape on. Templates never use `current_site`, `user_display`, or `{{ email }}`, so the request's host and the recipient's address stay out of the body. Subjects are the template's text alone (`ACCOUNT_EMAIL_SUBJECT_PREFIX` is empty). Render OPEN's own emails with `apps.emails.rendering.render_email()`, then queue them with `queue_email()`.
- Templates hold no promotional or marketing content, images, tracking pixels, scripts, external stylesheets or fonts, and no link but action links built from `FRONTEND_URL`. An `href` in a template is a single template variable. The hygiene checks in `apps/emails/tests/hygiene.py` check for these (a short word list and the usual image, script, and stylesheet markers, so they catch the common cases, not all) on every template file and on each rendered message a test passes them; run them on any new email.
- OPEN has templates only for the allauth emails its settings can send: verification (`email_confirmation`, `email_confirmation_signup`), password reset (`password_reset_key`), and `account_already_exists`. Security notifications (`ACCOUNT_EMAIL_NOTIFICATIONS`), the unknown account email (`ACCOUNT_EMAIL_UNKNOWN_ACCOUNTS`), and the code flows stay off, and a test pins them. Turning one on needs OPEN's templates for the emails it sends first, or allauth's defaults go out.
- An email names no other player and quotes no text another person wrote. The match confirmation request lists each Match's OPEN Code, date, and scores from the recipient's side, with a link to `{FRONTEND_URL}/matches/{code}` (`match_url()`, a new web app route that #37 and the web app adopt). `render_confirmation_request()` refuses a Player whose Account is inactive, an empty list, a repeated Match, a Match the Player did not play in, a Match that is not pending, and a Match with no games. It reads the Match's status and the Account's `is_active` from the instances it is given, so a caller passes freshly fetched rows.
- In tests, tasks run eagerly, but the test transaction never commits, so a queued email is not sent until on_commit callbacks run. The accounts tests run each test client request's callbacks when it returns (`run_on_commit_after_each_request` in `apps/accounts/tests/headless.py`); mark one `hold_on_commit` to keep them instead. Any other test that reads allauth's emails (through the `headless.py` helpers, say) uses the `commit_after_each_request` fixture from the root `conftest.py`. Elsewhere, use `django_capture_on_commit_callbacks(execute=True)`.

## Players

- Create a Player only through `apps.players.services.create_player()`, which also creates its `PlayerPrivacy` row. Change profile fields only through `update_profile()` and privacy settings only through `update_privacy()`. Both refuse any actor but the Player's own active Account, and record one Audit Event when a value changes. The birth year and month and the gender division are set once, when the Player is created: `update_profile()` refuses them (`SET_ONCE_FIELDS` in `apps/players/models.py`), whatever the value (ADR 0023).
- A profile change records only the changed field names, never a value (ADR 0009). A privacy change records the old and new levels of the changed settings.
- `Player.account` uses `PROTECT`, so an Account with a Player cannot be hard-deleted. #116 decides what Account deletion does with it. `MatchParticipant.player` uses `PROTECT` too, so a Player who has played a Match cannot be deleted.
- Age limits follow `apps/players/age.py` (ADR 0017): the end-of-month rule, judged on the date at UTC-12 (`age_limit_date()`). Never compare ages any other way. `Player` refuses a birth year and month under 13 whenever they are set or changed, and `create_player()` starts a player aged 13 to 17 with every privacy setting `PRIVATE`. Nothing changes privacy at 18.
- In tests, build Players with `PlayerFactory` (`apps/players/tests/factories.py`), which goes through `create_player()`. It makes adults only, so default privacy holds; use its `minor` trait for a player aged 13 to 17. A raw `Player.objects.create()` has no `PlayerPrivacy` row.
- The Player fields are the ones ADR 0009 allows. Adding a personal data field updates `docs/privacy/personal-data-inventory.md` in the same pull request.
- Player search (`search_players`, ADR 0018) returns only each Player's OPEN Code and display name, never a Player whose Account is inactive, and includes players aged 13 to 17. It is allowed before Ratings are published. Keep its minimum query length, result limit, and per-Account throttle when changing it.
- A player's profile (`get_player`, `GET /api/v1/players/{code}`) shows any signed-in Account only the OPEN Code, the display name, and the city and region while `city_region_visibility` lets the viewer (null when hidden or empty, so the two look alike). A Player whose Account is inactive gets the same 404 as an unknown code. Never add the legal name, birth year or month, or gender division to it.
- `POST /api/v1/me/player` (`create_my_player`) creates the Account's Player only when the Account's own login address (`User.email`) has a verified `EmailAddress` row (403 otherwise), and gives 409 for a second Player, including one that loses the race to `create_player()`'s lock. Every value comes from the signup hold (`peek_signup_details`, then `take_signup_details` once the Player exists or on a 409, so a create refused for any other reason can retry), the held legal name as the legal name and, for an adult, the display name (a player aged 13 to 17, judged with `is_minor()` at create, starts with "First L."), and from the body only when the session holds none, where the display name, birth year, month, and gender division are then required (ADR 0017, ADR 0019, ADR 0022). `GET` and `PATCH /api/v1/me/player` return and change the own profile; PATCH calls `update_profile()` and `update_privacy()` in one transaction, so a 422 on either changes nothing. PATCH refuses the birth year and month and the gender division with a fixed 422 (`set_once`) on each one sent, and the OpenAPI document does not list them for PATCH (ADR 0023).

## Clubs and organizers

- A verified Organizer's submissions count as confirmed, so verification is a security-sensitive area (hard rule 8). Change `Organizer.verified_at` and `verified_by` only through `apps.clubs.services.verify_organizer()` and `unverify_organizer()`. They refuse any actor but an active Account with the `clubs.verify_organizer` permission that is not a member of that Organizer, and record one Audit Event when the status changes. The `Organizer.save()` docstring lists the writes that skip them; `bulk_create` and `loaddata` skip them too (see Public identifiers).
- While an Organizer is verified, the Account that verified it cannot become its member (`bulk_create` and `QuerySet.update` skip this check). A verified Organizer cannot be deleted: unverify it first (`QuerySet.delete()` skips this check). An Organizer with an Event or a Partner Application cannot be deleted either, even through `QuerySet.delete()` (see Events, Partner applications). A Club with a Match cannot be deleted (`Match.club` uses `PROTECT`).
- `OrganizerMember.account` uses `PROTECT`, so an Account that is a member cannot be hard-deleted. `Organizer.verified_by` uses `PROTECT` while the Organizer is verified; after that, the verify event's actor keeps the Account row (Audit log). `ClubRole.account` cascades.
- Every Organizer's name may be a person's name, so it is an identifying field. #116 carries out what ADR 0009's Retention section decides for memberships, Club Roles, and Organizer names.
- The permission rules that use these roles are in `apps.matches.permissions` (see Matches). In tests, build a verified Organizer with `verify()` or `verified_organizer()` (`apps/clubs/tests/factories.py`), which go through `verify_organizer()` and so record an Audit Event (use a test transaction that rolls back, see Audit log). Membership and role changes record no Audit Event until #158 lands. Club Application Grant changes record none yet either (a comment on #158 asks it to cover them).

## Events

- An Event's `kind` is the Match Type its matches count as. Its values are the engine's `MatchType` values except `self_reported`, since self-reported matches have no Event (decision F1). Never add a value the engine lacks.
- An Event has no weight. The engine weights a match only by its Match Type and takes no per-event weight (openpickleball/engine#30), so never add or apply one in the backend (hard rule 2).
- `Event.organizer` and `Event.club` use `PROTECT`, so an Organizer or Club with an Event cannot be deleted. `Match.event` uses `PROTECT`, so an Event with a Match cannot be deleted.
- Event fields override Django's default messages that include the submitted value: an invalid choice or date, and a foreign key that names no row (whose default names the row id).
- A form that edits an Event subclasses `apps.events.admin.EventAdminForm`, and an override of its `clean()` calls `super().clean()`. The form gives `kind` a message without the value (a ModelForm's choice field repeats it), and its `clean()` clears a date that failed, so the model's order check does not compare the other new date with the stored one.
- Event changes record no Audit Event until #125 lands.
- In tests, build Events with `EventFactory` (`apps/events/tests/factories.py`).

## Matches

- `apps/matches` is the match ledger (hard rule 3). A Match is never deleted, and no field but its status ever changes. The ORM refuses (`MatchImmutable`) to delete a Match, Match Participant, Game, or Match Confirmation, to save an existing one (except a Match with `update_fields=["status"]`), and `QuerySet.update`, `delete`, `bulk_update`, and an upsert on any of them. Raw SQL, raw saves (`loaddata`), and migrations' historical models are not guarded. In tests, change a Match only through a service, or through the `raw_update()` helper (`apps/matches/tests/factories.py`, Match only) when a test needs a state no service produces.
- Every change to a Match after it is created goes through `apps.matches.workflow` (ADR 0013): `confirm_match`, `dispute_match`, `resolve_dispute`, `void_match`, `edit_match`, and `expire_unconfirmed_matches`. The only other status change is `record_match()`'s duplicate path, which confirms a pending Match. Never set `status` anywhere else. An edit voids the old Match and creates a corrected one through `record_match()`'s creation core, with `corrects` pointing to the old one; the correction is pending when the old Match was pending, and confirmed otherwise (a moderator's edit of a disputed Match confirms it). Each service checks permission first (`MatchActionDenied`, fixed text), then locks and checks state (`MatchStateError`, fixed text), writes one Audit Event per transition, and sends its signals inside the transaction. A moderator is an active Account with `matches.moderate_match`; only a moderator's free-text reason is stored, and `dispute_match` takes none, because the audit log cannot be erased. Every status change takes the Match's lineup advisory lock before its row lock: keep that order in any new path. Those locks last until the outermost transaction ends, so call each service in its own transaction, as with `record_match()` (the one exception is `create_match`, see below). Each transition writes one Audit Event: `match.confirm`, `match.dispute`, `match.void`, `match.expire`, `match.edit`, or `dispute.outcome`.
- `apps.matches.signals` sends `match_confirmed` once each time a Match becomes confirmed (a correction of a counting Match sends `match_changed` with `change=edit` instead) and `match_changed` (with `change` and `earliest_date`) when a counting Match is voided, corrected, disputed, or held by a new flag, and when a held Match counts again because the Match holding it was voided. Both are sent synchronously inside the transaction that made the change: a receiver may write rows there (the webhook outbox, #85), must enqueue other work with `transaction.on_commit`, and rolls the whole change back if it raises. Which Matches count is `Match.objects.counted()`: confirmed and not held by a `possible_duplicate` flag linked to a Match that is not voided. A receiver checks it, since a held Match can be confirmed.
- The database enforces allowed choice values, exactly one submitter (`submitted_by_user` or `submitted_by_application`), each Player once per Match, game numbers 1 to `MAX_GAMES` with each number once per Match, no negative scores, the `played_at` and `external_id` rules below, and one Match that is not voided per fingerprint (see duplicate detection below). `full_clean()` reports each of these with a plain message, except the game number range, which gives Django's generic constraint message. No model or database rule requires a game or contiguous game numbers. The models check only the score range, not the scoring rules (see the next rule). `record_match()` creates a Match with an Event or a Club confirmed (its submitter passed the permission rules, decision F4), with a `match.confirm` Audit Event and `match_confirmed`, and a self-submission pending. `record_match()` records no confirmation itself; `create_match` (`apps/matches/api.py`) then calls `confirm_match` for the submitter in the same transaction, so a player's submission counts as their team's confirmation and the match waits only for the other team (ADR 0013, #197). That is the one place two services share a transaction: `confirm_match` takes the lineup lock `record_match()` already holds, then the row lock of a Match no other transaction can see yet, so the lock order holds. `record_match()` returns `RecordedMatch(match, created)`: `created` is False when a permitted submitter's exact duplicate confirmed an existing pending Match instead of raising `DuplicateMatchError` (ADR 0013).
- Every path that submits a Match creates it through `apps.matches.services.record_match()`, never `Match.objects.create()`. `record_match()` first checks that each submitter it is given may submit the match (see the next rule), before any validation, then calls `validate_match()` and then `full_clean()` on the Match, its participants, and its games before any lock, lookup, or write, then checks for duplicates and writes the Match, its participants, games, and flags in one transaction. `validate_match()` holds the score validation rules, such as the game scores (the winner reaches the target and wins by 2 or more, or, past the target, wins by exactly 2), team size per format, no player twice, the allowed best-of and game target, 1 to `MAX_GAMES` games that decide the match, and no future `played_on`. It also applies the defaults for a submission (target 11, side-out) and infers a missing best-of. Add a new score validation rule there, never in a submission path.
- Who may submit and change a Match is a security-sensitive area (hard rule 8), decided in one place: `apps.matches.permissions` (ADR 0012). `can_create_match(actor, submission)`, where `submission` is a `MatchSubmission`, needs event authority for a match with an Event (a member, either role, of the Event's Organizer while it is verified, or an approved application that verified Organizer owns) and club authority for a match with a Club (any Club Role there, or an approved application the Club granted), so a match with both needs both. A match with neither is a player's self-submission (decision F1): only an active Account whose Player plays in it, never an application. `can_change_match(actor, match)` allows only the approved application that submitted the match, a member of its Event's verified Organizer, or an admin of its Club; an edit also needs `can_create_match` for the new match. Moderators (`is_moderator`) act through `apps.matches.workflow` from #40's admin, not through `can_change_match`. `participant_player` decides who may confirm or dispute as a player, and who may read one match (`get_match`). `can_confirm_as_organizer` decides who may confirm a pending Match alone. Every rule reads verification, approval, roles, grants, and `is_active` from the database by id, and refuses an unsaved actor. `record_match()` raises `MatchPermissionDenied`, with fixed text that never says which rule failed, before any validation detail, duplicate lookup, lock, or write, so a refused submitter learns nothing about other matches. No rule reads payment status (hard rule 7). Add a submission rule there, never in a submission path.
- `validate_match` raises one `MatchValidationError` that lists every issue it finds as field, code, and message, the shape of the API's `FieldError`.
- Give `validate_match` one canonical reference per player: resolved Players, or codes already passed through `normalize()`. Use one kind for the whole call. The duplicate and both-teams checks compare references by equality, and a call that mixes kinds fails with `mixed_player_references`.
- `validate_match` sets no upper bound on scores and does not read `played_at`. `Game.full_clean()` refuses a score above the field's limit, and `Match.clean()` ties `played_at` to `played_on`.
- Duplicate detection is a security-sensitive area (hard rule 8). `record_match()` refuses an exact duplicate (a Match that is not voided, from any submitter, with the same two teams in either order, the same `played_on`, and the same game scores) and an `external_id` its Partner Application already used (for a Match in any status). Both raise `DuplicateMatchError` with `kind` and `existing_code`. The exception: a submitter with Event or Club authority whose exact duplicate matches a pending Match confirms that Match and gets it back (`RecordedMatch(created=False)`), as does its retry (ADR 0013). `existing_code` is the earlier Match's OPEN Code only when the submitter may know it (the same Account or Partner Application submitted it, or the submitting Account's Player played in it), otherwise None; a repeated external id always names it. For an edit's duplicate, the editor takes the submitter's place, and a moderator always sees the code. The API turns it into a 409 `ErrorResponse` (`config/api_errors.py`) whose item carries `existing_code` under the same rule, and leaves the key out when it is None. A near duplicate (same teams and date, other scores) is saved with one `MatchFlag(reason=possible_duplicate, duplicate_of=...)` per earlier Match. Advisory locks serialize submissions of one lineup and date, and of one external id, so concurrent submissions are caught too. The locks last until the outermost transaction ends, so call `record_match()` in its own transaction, never several times inside one outer `transaction.atomic()`: two such callers can deadlock whatever order they sort their matches in. A batch path (#71, #72) must record each match in its own transaction and report a result per match; #71's all-or-nothing mode must get its all-or-nothing result another way (ADR 0011).
- `Match.fingerprint` is the SHA-256 of the teams, date, and scores (`match_fingerprint()`). A partial unique constraint allows one Match per non-blank fingerprint unless it is voided, so the same teams playing the same scores twice on one day count as one match (`sequence` is not in the fingerprint). A Match written outside `record_match()` has a blank fingerprint and escapes the exact check, though a later submission flags it as a near duplicate. The factories set the fingerprint when a Match has participants and games.
- A `MatchFlag` holds a Match for moderator review (CONTEXT.md, Flagged Match) and is its own row, so review (#40) never edits the Match. An open `possible_duplicate` flag holds both its `match` and its `duplicate_of` from counting until moderator review resolves it (#40), whatever the new Match's status or submitter: `counted()` excludes both, unless the other Match is voided (ADR 0011, ADR 0013). This lets any permitted submitter hold a real Match until review, including a match from another Club or Event (ADR 0011, ADR 0012). Flags are not under the ledger guard; #40's resolution must send `match_changed` when it releases a hold. Both links use `PROTECT`, so a flagged Match cannot be deleted.
- `played_at` is stored with `played_at_utc_offset` (minutes east of UTC where the match was played), because Postgres keeps a timestamptz in UTC and drops its offset. Both are set or both empty, and `played_at` shifted by the offset must fall on `played_on` (a check constraint). `clean()` refuses a `played_at` without a time zone. A plain `save()` stores a naive value as UTC, so always pass an aware datetime.
- `external_id` is a Partner Application's own id for the Match. Only an application's Match has one, unique per application among Matches that are not voided, so a correction keeps it; `record_match()` still refuses an id used by a Match in any status. A check constraint refuses leading or trailing whitespace (every character `str.isspace()` matches).
- `location` is a place's name, such as a court or park, never a street address, postcode, or exact location (ADR 0009). Nothing enforces this.
- Choice values follow the engine: `ScoringType` has `open_engine.ScoringType`'s values, `GameTarget` the points in `ALL_GAME_FORMATS`, and `MatchFormat` the two base `RatingFormat` values. `BestOf` is 1, 3, or 5 (decision F15). Import these and the limits (`MAX_GAMES`) from `apps.matches.models`; never redefine them. The match type is not stored: the engine adapter derives it (ADR 0024). An Event match has its Event's kind, a match with a Club and no Event is `rec_verified`, and a match with neither is `self_reported`.
- `Match.rating_format` is the match's engine rating format (`singles`, `doubles`, `mixed_doubles`, `doubles_men`, or `doubles_women`, ADR 0024). `record_match()`'s creation core (and so each `edit_match()` correction) sets it from the players' gender divisions at that moment, through `derive_rating_format()`, and nothing changes it afterward, so a later division removal never moves a past match. A check constraint ties it to `format`. The adapter reads it, never the players' current divisions. The API does not return it, because a category value reveals all four players' divisions.
- The adapter sends `confirmed_by` as the players with a confirm decision, except for a self-reported match a moderator confirmed (a `dispute.outcome` to confirmed, or a correction created confirmed by `edit_match`, read from those Audit Events), which sends every participant (ADR 0024). Keep those Audit Events' `before` and `after` keys as they are: the adapter reads them.
- `Match.submitted_by_user`, `submitted_by_application`, `event`, `club`, `corrects`, `MatchParticipant.player`, and `MatchConfirmation.player` use `PROTECT`. An Account that submitted a Match, an Account whose application submitted one, and a Player who played one cannot be hard-deleted. #116 must plan for this.
- Fields on these models override Django's messages that include the submitted value, including a non-integer foreign key id, whose default message comes from the target's primary key field.
- In tests, build Matches with `MatchFactory` and `DoublesMatchFactory` (`apps/matches/tests/factories.py`), with traits `best_of_1`, `best_of_3`, `best_of_5`, `side_out`, `rally`, and `by_application`. Pass `games=False` or `participants=False` to skip the generated rows.

## Ratings

ADR 0025 records these decisions. Rating changes are a security-sensitive area (hard rule 8).

- Write `RatingState`, `RatingHistory`, and `RatingReplay` only through `apps.ratings.services`: `apply_rating()` and `record_replay()`. `RatingHistory` and `RatingReplay` rows are append-only: the ORM refuses (`RatingHistoryImmutable`) to save an existing row, to delete one, and `QuerySet.update`, `delete`, `bulk_update`, and an upsert, through the default and base managers. Save a `RatingState` only through `apply_rating()` (the ORM does not refuse a plain `save()` or `create()`). The ORM refuses (`RatingStateWriteRefused`) to delete one, insert it in bulk (`bulk_create`), or change it in bulk. `bulk_create` of history and replay rows still inserts, but it skips the services' checks and Audit Event, so never use it outside tests. Raw SQL and `loaddata` are not guarded.
- Store what the engine returns (hard rule 2): values come from `engine_adapter.rating_summary()`. Never compute or round a rating in the backend, and compare stored values exactly (no tolerance) when deciding whether anything changed.
- Every rating change records one `rating.change` Audit Event in the same transaction, with no actor, targeting the `RatingState`: `before` is the old values (None for a new state), `after` the new values plus the `kind`, the Match's OPEN Code, and the replay's id. An apply whose values equal the stored state writes nothing and returns None, and so does a live update when that Match already updated that player in that format (a redelivery, even after an engine or spec version change). A partial unique constraint allows one live update row per player, format, and Match. This guard covers live updates only: a redelivered replay change after a newer live update writes another history row and replaces the live update's values, so ordering replay changes against live updates, a redelivered replay task included, is the replay caller's job (#47).
- `apply_rating()` refuses (`RatingApplyError`, fixed text) a summary for another player, an unknown format, a live update without its Match or with a replay, a replay change without its replay or with a Match or a delta, an unsaved record, a Match the player did not play in, a live update for a Match that does not count (`Match.objects.counted()`, hard rule 8), a live update in a format the Match does not count in (a doubles Match counts in its own format and in overall `doubles`), and a replay change whose summary does not come from its replay (the summary's `calculated_as_of`, `config_version`, `params_version`, and `parameter_fingerprint` must equal the replay's, with no live updates since). Values the models refuse raise `ValidationError` before any write. The database also refuses a `rating`, `rd`, or `delta` that is not finite (NaN or infinity).
- A live update stores the installed engine's version and `OPEN_RATING_SPEC_VERSION`. A replay change stores its `RatingReplay`'s versions, and its summary must match the replay's provenance, so a replay row never disagrees with its replay.
- `reliability` is OPEN-earned, and `imported_reliability` is stored apart (hard rule 5). `provisional` is True when the rating holds live updates not yet replayed, or was never replayed (hard rule 3). `established` is the engine's other label. Every stored rating is a demonstration rating while the engine is a demonstration package; #53 labels it in responses.
- `OPEN_RATING_SPEC_VERSION` (`config/settings.py`) is a constant, `"1.0.0rc1"`, from the openpickleball/rating-spec tag `v1.0.0rc1` (the project owner's choice). Bump it when rating-spec tags `v1.0.0`, and only for a new rating-spec tag, followed by the recompute (#48). It is the default spec version: `record_replay(spec_version=...)` takes another, which the recompute (#48) may pass.
- `RatingState.player`, `RatingHistory.player`, `match`, and `replay` use `PROTECT`: a Player with a rating, a Match that caused a rating change, and a replay that produced one cannot be deleted. #116 plans for this.
- `apply_rating()` locks the Player row first with `FOR NO KEY UPDATE` (`select_for_update(no_key=True)`), so applies for one player serialize (a first apply included) without blocking inserts of rows that point at the Player, such as `record_match()`'s Match Participants. Keep it `no_key`: a plain `FOR UPDATE` conflicts with their `FOR KEY SHARE` lock. Then it locks the state row. The locks last until the outermost transaction ends. The callers (#46, #47) own the transactions, the order of replays and live updates, and the lock order across players.
- In tests, build plain engine results with `rating_summary()` and `replay_provenance()` in `apps/ratings/tests/factories.py`, and go through the services.

### Live updates

ADR 0027 records these decisions.

- Confirming a Match (`match_confirmed`) queues `apps.ratings.tasks.update_ratings_for_match` on the `ratings` queue with the Match's row id only, through `transaction.on_commit()` in `apps/ratings/receivers.py`. Only a broker error on publish (kombu's `OperationalError`, or an `OSError`) is caught, and it is logged by id and error class only. Keep the catch that narrow and the callback not `robust`, so an eager task's failure in tests raises instead of hiding. `match_changed` queues nothing: a void, edit, dispute, hold, or release needs a replay (#47).
- `update_ratings_for_match()` (`apps/ratings/services.py`) runs in one transaction. It writes nothing for a missing Match, a Match not in `Match.objects.counted()`, a Match that already has a live update history row or that the stored snapshot already holds (a redelivery), and a Match the engine does not count (its snapshot is not saved, so the engine does not reserve its id). It returns a `LiveUpdateOutcome`.
- Lock order: the `EngineSnapshot` row for the loaded config (`SELECT ... FOR UPDATE`, created with `get_or_create` when new), then the Match's Players by row id (`FOR NO KEY UPDATE`), then the Match row `FOR SHARE` (raw SQL, since Django has no share mode), then `apply_rating()`'s state rows. The service checks `Match.objects.counted()` again under the Match row's share lock, since a Match can be voided or held while it waits, and the share lock makes a void, dispute, or edit (which take the row `FOR UPDATE`) wait until the live update commits. A new hold is not blocked (the near-duplicate flag insert never locks the earlier Match's row), so a Match held during a live update can still be rated live; `match_changed` (`hold`) and the replay (#47) correct it. Every live update for one config serializes on the snapshot row. The replay (#47) must take the snapshot row first too.
- A Match played before any participant's stored `last_played` in a format it updates (its own, and overall `doubles` for a doubles Match), or one the engine reports `late` (or `parent.late`), writes nothing and goes to `schedule_replay(players, earliest_date)`. Until #47 replaces it, that stub only logs the players' OPEN Codes and the date. Never log a name there.
- A live update that the snapshot cannot continue writes nothing, calls `schedule_replay`, and returns `replay_needed`: a participant's stored rating in a format the Match updates names another `parameter_fingerprint` than the loaded config's, or the snapshot is empty while a participant already has a rating in those formats, or the stored snapshot's `config_fingerprint` or `config_version` differs from the loaded config's (an engine upgrade; a new empty row is not checked), or a Match in the confirmed Match's `corrects` chain has a live update history row (a correction of a live-rated Match; every player in the chain goes to the replay, from the chain's earliest date). Never let a live update rate a player from an empty engine when they already have a rating.
- `EngineSnapshot` holds `RatingEngine.to_snapshot()` JSON, one row per parameter fingerprint. Write it only through the live update service (`_save_engine_snapshot`), in the same transaction as the rating changes. The ORM refuses (`EngineSnapshotWriteRefused`) to delete one, insert it in bulk, change it in bulk, or upsert it. Raw SQL and `loaddata` are not guarded. An engine upgrade that changes the config sends live updates to `replay_needed`, and one that changes only the snapshot schema makes `from_snapshot()` raise, until a replay or the recompute (#48) rebuilds the snapshot.
- An error while recording or applying is logged with the Match's row id and error class only (never the error's text, never `logger.exception`), then re-raised, so the transaction rolls back. The task (bound) replaces any error, in a worker, with a fixed-text `LiveUpdateFailed` (`from None`, holding only the Match id and error class) after one log line, so Celery's worker log never holds the original text; in eager mode (`self.request.is_eager`) the original error propagates. Keep any new task that can fail on personal data the same way. The task has no retries: a Match whose live update failed waits for the next replay (#47).
- Engine calls for a live update stay in `engine_adapter.record_live()`, which returns a plain `LiveUpdate`. It passes `as_of` to `player_summary()` explicitly, since the engine refuses no `as_of` before any replay.
- In tests, the task runs eagerly once on_commit callbacks run (`django_capture_on_commit_callbacks(execute=True)`), so any test that confirms a Match and runs its callbacks also runs a live update.

## Partner applications

- `PartnerApplication` (`apps/partners`) is the OAuth client a Partner uses. Approval is security-sensitive (hard rule 8): only #29's approval service (and, in tests, the `approve()` helper) writes `approved_at` and `approved_by`, through `update_fields`. A new application starts unapproved: `save()` refuses a new one that is already approved. `is_sandbox` defaults to true, but staff can change it; #29 and #74 decide how it is enforced. A full `save()` of an existing application never writes the approval fields. An Organizer with an application cannot be deleted (`organizer` uses `PROTECT`). The `save()` docstring lists the writes that skip these rules. An application that submitted a Match cannot be deleted (`Match.submitted_by_application` uses `PROTECT`). An application submits or changes a Match only while approved (`apps.matches.permissions`).
- A new application is always inserted: `save()` refuses `force_update` or `update_fields` on it, so a hand-built instance with another row's pk cannot overwrite that row.
- The client secret is stored hashed: check constraints refuse `hash_client_secret=False` and a blank secret. Any write of `client_secret` must be a raw secret: not blank, and not anything `identify_hasher` recognizes, because django-oauth-toolkit stores such a value as is, and when its hash check fails on it, compares it as plain text. A new raw secret is hashed and replaces the stored one, but a hash-shaped or deferred value is never written back: a full save, or `update_fields` naming `client_secret` (as `update_or_create` always does), leaves it out. The admin shows the generated secret only on the add form. Raw writes (`QuerySet.update`, `bulk_create`, `loaddata`, raw SQL) skip the model's checks; the check constraints still apply.
- Only `/oauth/token/` and `/oauth/revoke_token/` are mounted (`apps/partners/urls.py`). They are plain Django views outside the ninja API: errors use OAuth's JSON format, not `ErrorResponse`, and CORS does not cover them. Until #27, #28, and #29 land, the token endpoint does not check approval, sandbox status, or which scopes each application may have, and no API operation accepts an OAuth token.
- `OAUTH2_PROVIDER` in settings turns on every RFC 9700 behavior django-oauth-toolkit offers (tokens hashed at rest, https redirect URIs only). Turning one off makes `check --deploy` report a warning or an error, and `config/tests/test_settings.py` fails on either. Scopes, token lifetimes, and grant types are #28.
- `PartnerApplication.__str__` returns its `client_id`, and `ClubApplicationGrant.__str__` returns the Club's OPEN Code and the `client_id`. The application's `name` is shown only in the admin.
- In tests, build them with `PartnerApplicationFactory` and `ClubApplicationGrantFactory` (`apps/partners/tests/factories.py`). `approve()` and `approved_application()` there write the approval fields through `update_fields`, with no Audit Event, a test-only stand-in until #29's approval service lands.

## Public identifiers

- A model whose records have a public identity (Player, Club, Event, Organizer, Match) inherits `apps.public_ids.models.PublicCodeModel` and sets `public_code_type`. The system check `public_ids.E001` reports a concrete subclass without one. ADR 0008 records the scheme.
- Codes are created only by `save()` (or `objects.create()`), which issues the code, records it in `IssuedCode`, and refuses to change it later. Fixtures (`loaddata`), `bulk_create`, `QuerySet.update`, and raw SQL skip all of this and must not set codes. To copy a record, set `public_code = None`, `pk = None`, and `_state.adding = True` before saving. Saving a deleted record raises.
- Never expose or accept a row id in the API. A path parameter that names a record is `Annotated[str, PublicCodePath(CodeType.X)]`, and the view looks the record up with `get_by_public_code()`. `PublicCodePath` is for path parameters only, not body or response fields. A test fails on any numeric `id`, `pk`, `*_id`, `*Id`, or plural of these in the OpenAPI document, hidden operations included. allauth's emailed keys are the one exception (see Authentication).
- To read a code from other input (such as a CSV column), use `apps.public_ids.codes.normalize()`, then look up the canonical form.

## Personal data

- ADR 0009 sets what OPEN collects. Every model field that holds personal data is listed in `docs/privacy/personal-data-inventory.md`. Add, change, or remove its entry in the same pull request as the field.
- Never store a full birthdate (store birth year and month only), a raw gender, a street address, a phone number, or payment data.
- Only the player sets their own display name, legal name, birth year and month, gender division, and city and region. The birth year and month and the gender division are set once, at signup or when the Player is created, and the player cannot change them after that (ADR 0023). Others may only remove them (#190, #116).
- Every path that creates a Player refuses anyone under 13, and a new Player always has a birth year and month and a gender division (`mens` or `womens`, ADR 0019). The database still allows an empty gender division, for removal (#190, #116). Players aged 13 to 17 are left out of all partner sharing. A Player whose birth year and month were removed (#190, #116) is excluded from all partner sharing, permanently.
- The identifying personal data fields are email, display name, legal name, birth year and month, gender division, city and region, an Organizer's name (`clubs.Organizer.name`), External IDs (#49), and platform player IDs (#82). An Audit Event about one of them records the field's name, never its value. Account deletion is wider: it removes all personal data except what ADR 0009's Retention section keeps.
- No model's `__str__` returns an identifying field, so the admin log's `object_repr` and admin messages never hold one (a Player's, a Club's, an Organizer's, an Event's, and a Match's return their OPEN Code, a Match Participant's and a Game's their Match's OPEN Code with the team or game number, and a Partner Application's its `client_id`). allauth's `EmailAddress.__str__` returns the email, so its admin is unregistered. `accounts.User.__str__` returns the email, the known exception: #116 clears the admin log entries tied to a deleted Account.

## API

- There is one `NinjaAPI`, `api` in `config/api.py`, mounted at `/api/v1/`. Each app adds its operations to a `Router` in `apps/<app>/api.py`, and `config/api.py` mounts that router. The `config/api.py` docstring shows how. The health checks are the exception: their router is in `config/health.py`. `apps/matches/api.py` also has `me_router`, mounted at `/api/v1/me/`, for lists of the signed-in Account's own matches, and `apps/players/api.py` has another `me_router`, mounted at the same prefix, for the Account's own Player (`/api/v1/me/player`). The OAuth endpoints under `/oauth/` are not part of this API (see Partner applications), and neither are allauth's endpoints under `/_allauth/`, which use allauth's own response and error format, not `ErrorResponse` (see Authentication).
- Every operation passes an explicit `operation_id`. It names the method in the generated client, so never change one for a rename. Building the OpenAPI document raises an error for an operation in the document that has none, and a test checks every operation.
- Validation errors, an unparsable body, `Http404`, `HttpError`, a failed `auth` check, `DuplicateMatchError`, `MatchPermissionDenied`, `MatchValidationError`, `MatchActionDenied`, and `MatchStateError` come back as `ErrorResponse` (`config/api_errors.py`). Validation errors return 422, a failed `auth` check returns 401 with code `unauthorized` and empty `errors` (documented on every operation with `auth`), a `DuplicateMatchError` returns 409 with one `errors` item, which carries `existing_code` only when the error has one (ADR 0011), a `MatchPermissionDenied` returns 403 with code `forbidden` and empty `errors` (ADR 0012), as does a `MatchActionDenied` where an operation does not turn it into a 404 (ADR 0015), a `MatchValidationError` returns 422 with one `errors` item per issue, a `MatchStateError` returns 409 with code `conflict` (ADR 0015), and a throttled request returns 429 with code `throttled` and empty `errors`, with a `Retry-After` header when the throttle gives a wait. With DEBUG off, any other exception goes to Django, which returns its own HTML error page (a 500, or another status for exceptions Django maps, such as 403 for `PermissionDenied`). Raise `HttpError` or `Http404` instead of returning an error body by hand (the readiness check's 503 is not an error: it is a status report with its own documented schema), and use `HttpError(403, ...)` (or let `record_match()`'s `MatchPermissionDenied` propagate), never Django's `PermissionDenied`. Never declare a different 422 schema on an operation that takes input: building the document raises an error if you do. ADR 0005 records the versioning and error format, ADR 0011 adds the 409 for a duplicate match, ADR 0012 adds the 403 for a refused submitter, and ADR 0015 adds the match workflow errors.
- Player search's throttle (`SearchThrottle` in `apps/players/api.py`, ADR 0018) uses fixed-window counters in the default cache, keyed by the Account's id, counted with `cache.add` then `cache.incr`, and keeps no request state shared across threads (what `wait()` needs is in a `threading.local`). It does not use ninja's built-in throttles: `AuthRateThrottle` keys on a hash of `str(request.auth)`, the Account's email, their read and write of the count is not atomic, and ninja asks every throttle on an operation, so a request one refuses still counts against the others. Search stays out of #34's plan for first-party operations: never add a second throttle to it. ninja checks throttles after auth and before it parses input, so a 422 counts and a 401 does not. Tests that call a throttled operation clear the cache.
- Never put the submitted value in a validation message. The 422 response returns the message to the client.
- `openapi/openapi.json` is the API's OpenAPI document, generated by `manage.py export_openapi_schema` (`apps/openapi`) and committed so API changes show in review. Regenerate it in the same change as anything that changes the document, and never edit it by hand. CI (`export_openapi_schema --check`) and a test fail when it differs from the API, byte for byte. OPEN's command replaces django-ninja's command of the same name because `apps.openapi` comes before `ninja` in `INSTALLED_APPS`; keep that order (a test pins it). When a maintainer publishes a GitHub release, `.github/workflows/release.yml` runs `--check` on its tag and then attaches the file to the release. A root `.gitattributes` keeps the file's line endings LF, since the check compares bytes.
- A code path parameter (`PublicCodePath`) that fails returns 404, not 422, which narrows the 422 rule for that parameter (ADR 0008). With the other inputs valid, a malformed code and an unknown one get the same 404. With another input invalid, a well-formed code gets that input's 422 whether or not a record has it, so no response reveals that a record exists. Keep it so for an actor who is refused: an operation with a code in its path answers a refused actor with the same 404 as an unknown code, never a 403 (ADR 0015).

## Settings

- `config/settings.py` reads its deployment values from the environment (and an optional `.env`). Read a new variable with the helpers there (`_raw`, `_required`, `_list`), not django-environ's `Env` getters: those treat a value starting with `$` as a reference to another variable, which silently swaps secrets and URLs.
- The errors that `config/settings.py` raises for a bad or missing variable name the variable and never echo its value. django-environ's own `.env` reader is the exception: it logs a malformed `.env` line in full.
- With DEBUG off, settings turn on the https redirect, secure cookies, and HSTS (see ADR 0004). The test run applies a fixed set of overrides (the list is `_TEST_OVERRIDES` in `config/test_runner.py`), so tests run over plain http, run Celery tasks eagerly with errors propagated, hash passwords with fast MD5 (the production hashers stay listed after it), and need no cache server, no broker, and no `collectstatic`. pytest gets these overrides from `config/settings_test.py`, and `manage.py test` gets them from `config/test_runner.py`. Keep the two sets identical (a test fails if they drift). pytest's set lives in the settings module, so every process that loads it, parallel workers included, gets it; the runner applies its set in spawned parallel workers through `process_setup` (forked workers inherit it).
- `REDIS_URL` takes only the form `redis://[USER:PASSWORD@]HOST[:PORT][/DB]`, or `rediss://` for TLS: a lowercase scheme, a numeric database, and no query string or fragment. Settings refuse at startup a URL that breaks these rules. redis-py lets a query string override settings, certificate verification included, so set connection and TLS options in settings, never in the URL. Percent-encode any URL-reserved character in the password.
- Celery's broker is `REDIS_URL`, the same Valkey database as the cache, so clearing the cache (`RedisCache.clear()` runs FLUSHDB) also drops queued tasks. Settings refuse to start when `CELERY_BROKER_URL`, `CELERY_BROKER_READ_URL`, `CELERY_BROKER_WRITE_URL`, or `CELERY_RESULT_BACKEND` is set to a non-empty value in the environment (or `.env`): Celery would read it ahead of settings and skip the `REDIS_URL` checks. Set broker and TLS options in settings.
- Celery has four queues: `default`, `ratings`, `email`, and `webhooks` (ADR 0006). `CELERY_TASK_ROUTES` routes a task by the start of its name: tasks in `apps.ratings.tasks`, `apps.emails.tasks`, and `apps.webhooks.tasks` go to the matching queue, and every other task goes to `default`. A task given an explicit name outside its module's pattern goes to `default`. Sending to a queue that is not declared raises `QueueNotFound`. A new queue needs a declaration, a route, and the `-Q` list of every worker command (compose, docs, deploy).
- Tasks are acknowledged late, so a crash redelivers them: every task must be safe to run twice. Keep each task's time limit, and any countdown or ETA, below the broker's one-hour visibility timeout, or the task runs twice. Pass ids, not model instances, and keep secrets and personal data out of task arguments and return values (the worker logs return values).
- Static files use WhiteNoise's compressed manifest storage. With DEBUG off, every page that uses `{% static %}` (the admin, `/api/v1/docs`) returns a 500 until `collectstatic` has run, `runserver` and the compose `web` profile included. WhiteNoise sends no CORS header on static files.
- CORS covers `/api/` and `/_allauth/` paths only, for the exact origins in `CORS_ALLOWED_ORIGINS` (empty by default, so no origin is allowed). `CORS_ALLOW_HEADERS` is corsheaders' defaults plus the three headers allauth reads (`X-Session-Token`, `X-Email-Verification-Key`, `X-Password-Reset-Key`), so allauth's app client works cross-origin. The browser client uses the session cookie, so it works same-origin only (served from or proxied through the API host) until #102 allows credentials for first-party origins. Settings refuse at startup an entry that is not exactly `scheme://host[:port]`: no wildcard, path, trailing slash, or default port. `CORS_ALLOW_CREDENTIALS` and `CORS_ALLOW_ALL_ORIGINS` stay False, and `CORS_ALLOW_ALL_ORIGINS` is never read from the environment.
- gunicorn reads `PORT` and `WEB_CONCURRENCY` from the process environment only, never from `.env`. gunicorn parses `WEB_CONCURRENCY` itself before `gunicorn.conf.py` runs, so its own error reports a non-integer value. The config turns off gunicorn's control socket.
- `MATCH_CONFIRMATION_EXPIRY_DAYS` (1 to 36500, empty by default) makes the daily expiry task void pending matches submitted (`created_at`) more than that many days ago (ADR 0013). The task is always scheduled; empty, it does nothing. The task's schedule is `CELERY_BEAT_SCHEDULE` in settings, which the database scheduler copies over the stored row at each beat start, so change a schedule there, not in the admin.
- `FRONTEND_URL` is required: the web app's exact origin, checked like a CORS entry, and https when DEBUG is off. allauth's email links (verify an address, reset a password) open pages under it (`HEADLESS_FRONTEND_URLS`), and so does the match confirmation request's link (`match_url()`).
- `EMAIL_BACKEND` is a Django email backend path from the environment, passed through as is. With DEBUG on and no value, email prints to the console (of the Celery worker, since a task sends it). With DEBUG off it is required, and backends that print or keep messages are refused (the list is in `config/settings.py`). With Resend's backend (`anymail.backends.resend.EmailBackend`) and DEBUG off, `RESEND_API_KEY` is required (read into `ANYMAIL`). `DEFAULT_FROM_EMAIL` is required with DEBUG off, and `SERVER_EMAIL` follows it. Switching to Amazon SES needs no code change: `uv add "django-anymail[amazon-ses]"`, then set `EMAIL_BACKEND` and boto3's AWS variables (boto3 timeouts are optional tuning, see the Email section). Never let a DEBUG-off environment print or log email: messages carry recipient addresses and verification and reset keys.

## Commands

Fill these in as the M0 issues land. A command for a tool or service that has not landed yet fails until its issue does. Every command that loads settings needs the settings variables. That includes `check`, `mypy`, and the pre-commit mypy hook (the django-stubs plugin imports `config.settings`). Copy `.env.example` to `.env` first; process environment values win over it. `migrate`, the tests, `runserver` (which checks migrations at startup), and `celery beat` (which needs the migrations applied) need the Postgres that `DATABASE_URL` names. A Celery worker needs the Valkey that `REDIS_URL` names. `docker compose up -d --wait` starts it and Valkey from `compose.yaml` and waits until both are healthy; the `.env.example` URLs point at them. Docker Compose also reads `.env` and treats a `$` in a value as a variable reference, so wrap a secret key that contains `$` in single quotes. `uv run pytest` runs the suite with coverage and fails when total coverage is below `fail_under` in `pyproject.toml`. The floor counts all of `apps` and `config`, so a narrow run (one file or a `-k` selection) usually fails it even when every test passes: add `--no-cov` to those runs. To build test records, prefer the factory_boy factories (such as `UserFactory` in `apps/accounts/tests/factories.py`), which fill in made-up Faker data. Expected shape:

```bash
cp .env.example .env                      # local settings; never commit .env
uv sync                                   # install from uv.lock
uv run pre-commit install                 # git hooks: ruff, mypy, hygiene checks
uv run python manage.py check             # Django system checks, no database needed
docker compose up -d --wait               # local Postgres and Valkey, healthy
uv run python manage.py migrate
uv run python manage.py runserver
DJANGO_DEBUG=true uv run python manage.py seed_dev_data --players 20   # made-up dev data; DEBUG only; reset with down -v
uv run celery -A config worker -Q ratings,email,webhooks,default -l info   # background tasks, every queue
uv run celery -A config beat -l info      # periodic tasks; run one beat only, after migrate
uv run python manage.py collectstatic --noinput   # before serving with DEBUG off
uv run gunicorn                           # serve with gunicorn.conf.py (PORT, WEB_CONCURRENCY)
docker compose --profile web up -d --wait # optional: the app, a worker, and beat in containers, instead of on the host (beat waits for migrate)
docker compose down -v                    # stop and delete local data
uv run pytest                             # tests with coverage (Postgres, not SQLite)
uv run pytest -n auto                     # the same in parallel, one worker per CPU, as CI runs it
uv run pytest --no-cov apps/accounts      # part of the suite, without the coverage floor
uv run ruff check . && uv run ruff format --check .
uv run mypy .                             # strict; needs the settings variables
uv run python manage.py makemigrations --check --dry-run   # CI fails on missing migrations
uv run python manage.py export_openapi_schema              # regenerate openapi/openapi.json after an API change
uv run python manage.py export_openapi_schema --check      # CI fails when openapi/openapi.json is stale
uv run pre-commit run --all-files
```

`.github/workflows/ci.yml` runs on every pull request and every push to `main`, in three jobs: `lint` (`ruff check`, `ruff format --check`, and the pre-commit hygiene hooks), `types` (`mypy .`), and `test` (`manage.py check`, `makemigrations --check --dry-run`, `export_openapi_schema --check`, and `pytest -n auto` with the coverage floor, against a Postgres service). The job names are meant to be required status checks on `main` alongside `sign-off`, so a change that renames a job must also update the `main` ruleset.

## Hard rules

1. **No real player data, anywhere.** Not in code, fixtures, seed scripts, migrations, logs, issues, pull requests, or screenshots. Use made-up or properly de-identified data. `.gitignore` excludes local data directories and database files; keep it that way.
2. **Do not reimplement rating math.** The backend calls the engine. If a calculation seems wrong or missing, the fix belongs in the engine or the rating spec, not here.
3. **The match ledger is append-only.** Corrections are new records that reference the old one, never in-place edits or deletes of counted matches. Authoritative ratings come from a deterministic replay of the ledger; live updates between replays are provisional and must be labeled as such.
4. **Store replay provenance.** Persist each replay's `as_of` date, config version, and config fingerprint so any published rating can be reproduced.
5. **External ratings are a seed only.** An imported rating initializes a player and needs verified identity and evidence. It can never overwrite an OPEN-earned rating once OPEN matches exist. Show imported reliability separately from OPEN-earned reliability.
6. **Do not name competing rating systems** in code, docs, issues, or comments. Say "standard external rating system" or "external rating".
7. **Charter limits.** No paid tiers, premium features, ads, or payment flows. Players can always export their data. Do not build anything that conflicts with the [mission charter](https://github.com/openpickleball/.github/blob/main/CHARTER.md).
8. **Security-sensitive areas:** score confirmation, organizer verification, duplicate detection, identity linking, and anything that lets one party change another player's rating. Treat bypasses here as security bugs, not feature gaps.

## Contribution conventions

- Every commit needs a DCO sign-off (`git commit -s`). CI (`.github/workflows/dco.yml`) rejects pull requests with unsigned commits. That check runs only on pull requests, so commits pushed straight to `main` must be signed off by hand.
- Founding phase: repository admins may push directly to `main` while the project is getting established. Everyone else, and admins once this phase ends, uses one change per pull request, linked to an issue. Add or update tests and docs when behavior changes.
- `.github/CODEOWNERS` makes the maintainers team the owner of every path. When an app for a security-sensitive area (hard rule 8) or the match ledger lands, give its directory its own entry, owned by the maintainers team, in the same pull request. A test requires every CODEOWNERS path to match a tracked file or a directory that holds one.
- The `.editorconfig` Python settings (indent and line length) must agree with ruff format. A test compares them with ruff's resolved settings, so change both together.
- License: AGPL-3.0-or-later for this repository. API specifications are Apache-2.0 and will be published separately by the `partner-docs` repository (#184), so do not place OpenAPI specs here as the canonical copy. `openapi/openapi.json` is a generated copy for review and release assets, not the canonical copy (see API).
- Before proposing a feature, ask whether it makes the standard more accurate, more trusted, or easier to adopt. If not, it probably belongs in a partner's product.

## Git exception

This section overrides a contributor's global no-commit rule for the `/work-issue` workflow only.

- The workflow may commit (`git commit -s`, with explicit paths) and push, but only on the `issue-<N>-*` branch it creates or resumes.
- After a rebase it may push that branch with `--force-with-lease`. It never force-pushes any other branch.
- It may open a pull request against `main`, edit its description, label it (creating the ready label if it does not exist), and reply to review comments on it.
- It never commits or pushes to `main`, never merges, and never enables auto-merge. A human reviews and merges every pull request.

## Writing style

Docs in this project use plain, short sentences. No emojis and no em dashes. Prefer "player", "match", and "organizer" over generic words like "user" or "entity" (see `CONTEXT.md`).
