# 0047. Account security: login limits, breached passwords, session lifetimes, and sign-in alerts

- Status: Proposed
- Date: 2026-11-26

## Context

ADR 0014 set up email login and mandatory email verification but left the protections around them at allauth's defaults. allauth's per-IP limits read `REMOTE_ADDR`, which is the proxy in production, and its per-account failed login counter is keyed on the Host header as sent, so another port or letter case of an allowed host starts a fresh counter. A player could choose a password already published in a breach. Sessions and app tokens lived as long as Django's two-week cookie age, renewed on every save, and nothing ended them when the password changed. A player could not see where they were signed in or hear about a sign-in they did not make (issue #100).

The maintainer decided four things on #100:

1. The breached password check **fails open**: when the service times out or errors, the password is accepted and the outage is logged with no password, hash prefix, or address. Length rules and login limits still apply.
2. The service is a **public k-anonymity range API**. Only the first 5 hex characters of the password's SHA-1 leave OPEN, padded responses are asked for, and the timeout is 3 seconds.
3. **New device detection** uses a long-lived signed cookie per browser, and for the app client a server-signed token returned at login and sent back on the next login, with no table. No user agent history is kept, and the session rows are never used for it. An Account's first sign-in sends no alert.
4. **Session listing** uses allauth's user sessions app, for listing and ending sessions only. The IP address and user agent it stores are kept only while the session lasts and are listed in the personal data inventory.

## Decision

This amends ADR 0014 (rate limits, lifetimes, and ended sessions), ADR 0039 (the password rules add the breach check), and ADR 0043 (removing TOTP ends other sessions).

- **Client IP.** allauth's per-IP limits and the user session rows take the client IP from `CLIENT_IP_HEADER` only, through the account adapter's `get_client_ip`, which uses the API throttles' parsing (`config.throttling.client_ip`, ADR 0030): never `X-Forwarded-For`, `Forwarded`, or `REMOTE_ADDR`. An IPv4-mapped address is its IPv4 address, and an IPv6 address is its /64 network address. A missing or invalid value is `0.0.0.0`, which every such request shares, so allauth never refuses a request for want of an address.
- **Rate limits.** `ACCOUNT_RATE_LIMITS` sets every account action in settings, in the shared cache: login 30 a minute per IP; failed logins 10 a minute per IP, and 5 per 5 minutes and 20 an hour per address; signup 20 a minute per IP; reset requests 20 a minute per IP and 3 an hour per address; reset from a key 20 a minute per IP; a verification email resend once per 3 minutes per address; reauthentication 10, password change 5, and email management 10 a minute per Account. The failed login counter is keyed on the lowercased address alone, not the host. A login over the failed login limit answers 429, as every other limit does, not allauth's 400 `too_many_login_attempts` (OPEN's login view). allauth's MFA code step keeps its own 400.
- **Breached passwords.** `BreachedPasswordValidator` runs last in `AUTH_PASSWORD_VALIDATORS`, after Django's four standard rules, so signup, the signup password check, password change, reset from a key, and the admin's password forms all refuse a listed password with code `password_breached`. It asks `PASSWORD_BREACH_API_URL` (Pwned Passwords' range API by default) with `Add-Padding: true`, a generic User-Agent (`OPEN-password-check`), and `PASSWORD_BREACH_TIMEOUT_SECONDS` (3, at most 10). A count above 0 refuses; a padding entry (count 0) never does. A timeout, a connection error, an answer other than 200, or a body that is not `SUFFIX:COUNT` lines accepts the password and logs one warning with the error class only. `PASSWORD_MIN_LENGTH` sets Django's minimum length: 8 by default, and never below 8. Tests replace the transport for every test, so none reaches the network.
- **Session lifetimes.** A signed-in session ends `SESSION_MAX_AGE_DAYS` (30) after login or `SESSION_IDLE_DAYS` (7, at most the lifetime) after it was last seen, whichever comes first. This holds for the browser's cookie session (a middleware after the authentication middleware) and for the app's session token, on allauth's endpoints and the OPEN API alike (OPEN's `HEADLESS_TOKEN_STRATEGY`, which both look tokens up through). Both times live in the session itself, so there is no table. Last seen is written at most hourly. Each write sets the session's own expiry to the earlier end, so Django's store refuses the session then and the sweep deletes it. An ended session is deleted with its user session row. A signed-in session made before this change gets fresh times on its next use. `SESSION_COOKIE_AGE` is the lifetime.
- **Ending sessions.** A headless password change ends the Account's other sessions and app tokens and keeps the one that made it. A reset from a key ends every session. Removing TOTP ends the other sessions. Ending a session deletes its store row and its user session row. A password change also ends sessions with no user session row, through Django's session auth hash; removing TOTP does not.
- **Session list.** `allauth.usersessions` is installed with activity tracking off, so no row is written per request. A row is made at login and deleted at logout, when the session is ended, and by a task every 15 minutes (`sweep_sessions`, the default queue) that deletes expired sessions and every row whose session is gone or expired. OPEN's sessions view lists each session by a keyed hash of its session key, never the row id (CLAUDE.md, Public identifiers), and ends the sessions a player names by those ids. An id that is not one of the Account's sessions refuses the whole request with fixed text. allauth's UserSession admin is unregistered.
- **Not encrypted.** The user session row's `ip` and `user_agent` stay plain text, outside ADR 0046's encrypted fields. They are short-lived (deleted with the session), shown to the player in their own session list, and held in a third-party model whose field types OPEN does not change: `ip` is a `GenericIPAddressField` that would refuse a token.
- **Sign-in alert.** When a login completes, after any MFA step, OPEN reads the device marker: the `open_device` cookie (`__Host-open_device`, Secure, with DEBUG off; HttpOnly; SameSite Lax) for the browser client, or the `X-Device-Token` request header for the app client. The marker is a signed list of at most 10 tags, newest first, refused after `SIGN_IN_DEVICE_COOKIE_DAYS` (365). A tag is a keyed hash of the Account's primary key, never an email address or a row id. When the Account had signed in before and the marker lacks its tag, one email is queued through `queue_email` from an on_commit callback. The marker is then written back with the Account's tag first: as the cookie, or in the `X-Device-Token` response header, which the app keeps and sends with its next login's requests (CORS allows and exposes it). The email names the time in UTC to the minute and the client type ("a web browser" or "the OPEN app") and links to `{FRONTEND_URL}/account/sessions`. It holds no IP address, user agent, location, request host, or recipient address. allauth's own security notifications stay off.
- **Audit.** A headless password change and a reset from a key record one `password.change` event in the change's transaction, actor and target the Account, `after` `{"method": "change"}` or `{"method": "reset"}`. Each session a player ends records one `session.end` event, `after` `{"current": true}` or `false`, never the IP address, user agent, or key.

## Consequences

- A guesser gets 5 tries per address per 5 minutes, and at most 20 an hour, wherever they come from. The real player is locked out for that long too; a password reset clears the counter.
- When the range API is down, a breached password can be set. The outage shows in the logs.
- A new web app page, `/account/sessions`, is linked from the alert. It does not exist until the web app adds it.
- The app client must keep the `X-Device-Token` a login returns and send it on every request of its next login, the MFA step included, or each login from it sends an alert.
- Clearing cookies, a new browser profile, or a reinstalled app counts as a new device and sends an alert. A browser or app shared by more than 10 Accounts forgets the oldest.
- A session made before this change has no user session row, so the session list does not show it and removing TOTP does not end it. It ends on a password change, at its lifetime, or at logout.
- The session list's ids changed from allauth's integers to strings; the served OpenAPI document says so.

## Alternatives considered

- **Failing closed** when the range API is down. The maintainer chose to fail open, so an outage never blocks signup or a reset.
- **OPEN's own session table** without an IP address or user agent. The maintainer chose allauth's app, with its rows kept only while their session lasts.
- **Detecting new devices from session rows or user agents.** Ruled out by the maintainer: no user agent history, and no reuse of the session rows.
- **allauth's row ids in the session list.** They would put a row id in the API, which CLAUDE.md rules out.
