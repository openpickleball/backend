# 0057. Organizer and Club admin security

- Status: Proposed
- Date: 2026-11-27

This amends [ADR 0054](0054-organizer-self-service.md) (a new member of a verified Organizer no longer gets authority at once), [ADR 0055](0055-club-self-service.md) (the last Club admin must have MFA), [ADR 0047](0047-account-security-limits-and-sessions.md) (shorter sessions for members and Club admins), and [ADR 0021](0021-organizers-are-the-trusted-submitters.md)'s threat model (a taken-over admin Account is now named and bounded).

## Context

A verified Organizer is the only trusted submitter (ADR 0021), and its admins decide who acts for it. Since self-service (ADR 0054, ADR 0055), an admin adds members, changes roles, and grants without any staff step. So one admin Account, taken over through a stolen session or a phished password plus code, could add helpers who record counted matches at once, and the other admins would not know. Issue #232 asks for step-up authentication, notices, a hold on new members, and rules that keep an admin who can repair the Organizer.

## Decision

- Step-up. `invite_organizer_member`, `change_organizer_member_role`, `remove_organizer_member`, `request_organizer_verification`, `invite_club_admin`, `remove_club_admin`, `grant_club_organizer`, `remove_club_organizer_grant`, and `create_results_file` need a second factor step (an MFA login, an MFA reauthentication, or enrollment) within `ORGANIZER_STEP_UP_SECONDS` (default 300, 30 to 86400) in the session behind the request. For an Account without MFA (it reaches only the upload, and gets its lookup's 404 after), any allauth authentication record within the window counts. Otherwise the answer is 403 `reauthentication_required`, with the fixed text "Confirm a two-factor code again, then retry." for an Account with MFA and the general reauthentication text for one without, before any lookup of the path's records, so it is the same for every well-formed code. After `auth/2fa/reauthenticate` the request succeeds. Reads, rename, profile changes, and creates need no step-up. Verification and Organizer Application Grants are made only in the admin, which already needs an MFA step within `ADMIN_REAUTHENTICATION_SECONDS` for every write, so nothing changes there.
- Security notices. Each change to who may act for an Organizer or Club, or to its verification, queues one email (`clubs/email/security_notice`) per other active admin when the change commits: Organizer Member adds, removals, and role changes; Club admin adds and removals; Club Organizer Grants (to the Club's admins) and Organizer Application Grants (to the Organizer's admins) made or removed; verification granted or removed; and a member removing its last two-factor method (for each Organizer it is a member of and each Club it is an admin of). The acting Account gets none. The Account the change is about gets none either, except on a removal, a role change away from admin, or a staff move of its admin row to another Account, when it is told too unless it made the change itself. The access rows send theirs through a hook that `apps.audit.access` calls after recording, so the admin, self-service, and Account deletion all send them. A change of nothing but a New Member Hold, and a removal recorded by `record_cascaded_removals` (the parent is going), send none. A notice names OPEN Codes, the change, a role, and a hold's end in UTC, never an address, a person's name, an Organizer's or Club's name, or a client id. A failure is logged by row id and error class and never fails the change.
- New Member Hold. A member who joins a verified Organizer by invite gets `OrganizerMember.hold_ends_at` set to `ORGANIZER_NEW_MEMBER_HOLD_HOURS` (default 24, 0 turns it off) from the accept, read under the Organizer lock. Until then the member has no Organizer authority and no admin authority: every rule that grants either, and every query that mirrors one, adds one filter (`apps.clubs.models.not_held`, compared with the database's `Now()`). Staff adds in the admin and `create_organizer` set none. A moderator (`may_close`: active, `clubs.verify_organizer`, not a member) ends an Organizer's holds early with a required reason (`apps.clubs.services.end_member_holds`, and the Organizer admin's "End new member holds" action), each member recording one `organizer_member.change` with the reason. The add event records the hold's end; an unheld member's events keep their shape.
- One admin who can act. An admin role (Organizer Member or Club Role) needs an active Account with a verified login address (`clean()`, and a self-service promotion refuses it with 409). The self-service last-admin checks count only active admins with MFA. Removing TOTP is refused with 409 `last_mfa_admin` (allauth's error shape, fixed text), removing and recording nothing, when it would leave the Account with no method while it is an admin of an Organizer with no other active admin with MFA. That check runs after the reauthentication requirement and locks the Account's admin Organizers `FOR NO KEY UPDATE`, by id, after the Account row, so it runs in turn with self-service changes and another admin's removal. Clubs get no TOTP removal block, since no Club lock may be taken on that path (ADR 0055); the Club notice still goes.
- Shorter sessions. An Account with any Organizer membership or Club Role uses `ORGANIZER_SESSION_MAX_AGE_DAYS` (default 7, or `SESSION_MAX_AGE_DAYS` when lower) and `ORGANIZER_SESSION_IDLE_DAYS` (default 1), each at most its player value and the idle time at most the lifetime. Whether a session is short is stored in it, read from the database at login and when last seen refreshes, so a membership gained mid-session applies within `SESSION_SEEN_REFRESH_SECONDS`.

## Consequences

- ADR 0054's consequence that an accepted invite gives trusted-submitter authority at once no longer holds: it starts after the New Member Hold, and the other admins hear of the add.
- ADR 0021's threat model now names a taken-over admin Account. It is bounded by the step-up, the notices, the hold, and the MFA admin rules, and repaired by the other admins, staff, or a moderator's unverify.
- `create_results_file` has a new 403. A client confirms a code and retries.
- Losing MFA ends authority at once (authority reads `accounts_with_mfa()`), and TOTP removal ends the other sessions that have a user session row.
- A member who joined while the Organizer was unverified gets no hold when it is later verified: the moderator reviews the Organizer, its members included, at that point.
- The only admin with MFA of an Organizer cannot remove TOTP, so it cannot rotate a secret it thinks leaked by removing and adding TOTP without first making another admin with MFA. Staff can help.
- Clubs have no New Member Hold and no TOTP removal block (no Club lock may be taken on that path, ADR 0055), so a Club can end with no admin with MFA through TOTP removal. A Club gives no match authority, and its other admins get the notice.
- Club Organizer Grant notices go only to the Club's admins, not to the Organizer's: the grant is the Club's consent.
- A removed or demoted admin, or one whose admin row staff moved to another Account, gets the notice too, unless it made the change itself, so an attacker who removes the only other admin cannot do it unseen.
- A held admin does not count as the admin who stays: the last-admin checks and the TOTP removal block count only admins with MFA and no hold in force.
- Not done: Account deletion and the staff admin can still leave an Organizer with no admin. Deletion is a player's right (ADR 0048) and must not be blocked by a role; staff are trusted and repair it. The other admins now get a "member removed" notice from both paths.
- Not done: sessions without a user session row (from before user sessions were installed, #100) are not ended on MFA removal. They still have no authority, since authority reads the Account's MFA.
- Not done: step-up for accepting an invite. It is not in the issue's list, and the hold covers it.

## Alternatives considered

- Require a moderator to approve each new member. Rejected: moderators review Organizers, not members (ADR 0054), and the hold plus the notices give the other admins time to act.
- Block TOTP removal for the last Club admin with MFA too. Rejected: it needs a Club lock on the MFA path, which cycles with grants (ADR 0055). A Club gives no match authority, and the notice tells the other admins.
- Recompute the short session flag on every request. Rejected: one more query per request for a change that the refresh catches within the hour.
