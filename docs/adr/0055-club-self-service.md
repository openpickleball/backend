# 0055. Club self-service: profiles, admins, and Club Organizer Grants

- Status: Proposed
- Date: 2026-11-26
- Amended by: [ADR 0057](0057-organizer-and-club-admin-security.md) (Club admin changes need a recent two-factor step, the other admins get security notices, and the last admin must have MFA)

This applies [ADR 0054](0054-organizer-self-service.md)'s invite rules to Clubs, and amends [ADR 0030](0030-api-throttling.md) (inviting a Club admin has its own day throttle), [ADR 0048](0048-account-deletion.md) (deletion also removes Club Invites; the new events keep an Account row), and [ADR 0051](0051-player-data-export.md) (Club Invites are left out of the export).

## Context

ADR 0021 makes a Club where or with whom people play. A Club is never verified and never submits: it only decides which Organizers may name it, through Club Organizer Grants. Until now only staff made Clubs, Club Roles, and grants, in the admin (#20). A club needs to set up its own profile and grant the Organizers that run its leagues and tournaments (issue #230). Who may name a Club on Events and matches is part of who may change ratings (hard rule 8).

## Decision

- Paths, on a new router mounted at `/api/v1/clubs` (no trailing slash): `POST /clubs` (`create_club`), `GET /clubs/{code}` (`get_club`), `PATCH /clubs/{code}` (`update_club`), `POST /clubs/{code}/invites` (`invite_club_admin`), `POST /clubs/invites/accept` (`accept_club_invite`), `GET /clubs/{code}/admins` (`list_club_admins`), `DELETE /clubs/{code}/admins/{player}` (`remove_club_admin`), `GET` and `POST /clubs/{code}/organizer-grants` (`list_club_organizer_grants`, `grant_club_organizer`), and `DELETE /clubs/{code}/organizer-grants/{organizer}` (`remove_club_organizer_grant`). An Organizer's side: `GET /api/v1/organizer/organizers/{code}/club-grants` (`list_organizer_club_grants`).
- Create. An active Account whose login address is verified creates a Club (name, optional city and region) and is its only admin (403 for an unverified address, nothing written). At most `CLUB_CREATE_LIMIT_PER_ACCOUNT` (default 5) admin Club Roles per Account (409 past it). Creating needs no MFA: a Club with no grants changes nothing, and every admin action on it needs MFA.
- Read. Any signed-in Account sees a Club's OPEN Code, name, city, and region. A Club is a place or group, not a person (ADR 0009).
- Profile changes. A Club admin changes the name, city, and region; an explicit `null` or a missing key leaves a field as it is. While any Event or Match names the Club, a name change gets 409 with fixed text. The check reads committed Events and Matches under the Club lock. Nothing on the Event or match paths locks the Club before its commit, so a first Event or match committing at the same moment may miss the check; that is accepted, since nothing is recorded under the old name yet. The reason: the name shows on recorded, trusted matches (ADR 0053), so a Club admin, who is never reviewed, must not change it after the fact. Staff rename it in the admin. City and region still change.
- Admin actions. Every operation with a Club code in its path, except the read, acts for a Club admin: an active Account with MFA (ADR 0043) whose Club Role is admin, read from the database. An Account without MFA gets 403 `mfa_required` before any lookup. A non-admin and an unknown or malformed code get one 404.
- Admins and invites: ADR 0054's rules, with the Club in place of the Organizer and no role choice (admin is the only Club Role, ADR 0021). Admins are shown by their Player's OPEN Code and display name, never an email. A Club always keeps one active admin on these paths (409). Removing an admin deletes the invites it sent to that Club. An invite's answer (202) is the same whatever the address; the email names only the Club's OPEN Code, the expiry, and the link `{FRONTEND_URL}/clubs/invites/{key}`, valid `CLUB_INVITE_DAYS` (default 7). At most `CLUB_OPEN_INVITES_LIMIT` (default 50) open invites per Club, and the invite has its own per-Account day throttle (`API_CLUB_INVITE_THROTTLE_PER_DAY`, default 20). Accepting needs the invited, verified login address, a Player, and a sender who is still an active admin with MFA; every refusal is one 404.
- Grants. A Club admin grants an Organizer by its OPEN Code, verified or not (a grant is consent, not trust), and removes a grant. An unknown Organizer code gets the same 404 as an unknown Club; an existing grant gets 409. So a Club admin with MFA learns whether an Organizer code exists, unverified ones included, and nothing more about it. This is accepted (the project owner's decision on #335, 2026-11-27): OPEN Codes are already public identifiers (ADR 0008), and a match's Event shows its Organizer's OPEN Code (`MatchEventOut.organizer` on `MatchOut`, #319), so this reveals nothing that needs hiding. A grant needs no consent from the Organizer, which sees it in its own list and cannot remove it. The Club's list shows each Organizer's OPEN Code and the grant time, never its name (ADR 0050). An Organizer's admin member with MFA sees the Clubs that granted it, with each Club's code, name, city, region, and grant time. A removed grant stops new Events and matches under the Club's name (`Event.clean()` and `apps.matches.permissions`); recorded matches stay in the Ledger as they are (hard rule 3). A Club Role still gives no authority to submit, confirm, or change a match.
- Audit Events: `club.create` (no values), `club.change` (`after.fields` names the changed fields, never their values: a self-made Club can be named after a person, and the audit log cannot be erased), `club_invite.create` (the Club's OPEN Code, never the address), and the existing `club_role.*` and `club_organizer_grant.*` through `apps.audit.access`, with the acting Account.
- Lock order: the acting Account (`FOR KEY SHARE`, or `FOR NO KEY UPDATE` in the create), then, on accept, the invite sender's Account (`FOR KEY SHARE`, so a sender whose deletion or TOTP removal is in flight is waited for and then refused: Account deletion never locks a Club), then the Club row `FOR UPDATE`, then the Organizer row `FOR KEY SHARE` on a grant, then invite, role, and grant rows. Account deletion takes the Account, then its Organizers, and deletes Club Roles and invites without locking the Club, so no cycle forms. Never add a Club lock to deletion.
- Retention. A Club Invite is deleted when accepted, when it expires (the daily `sweep_club_invites` task), when its sender is removed through self-service, with its Club, and at Account deletion (invites to the Account's addresses and those it sent). Invites are not in the data export.
- A Player-less creator shows `player: null` in the admin list and is managed by staff, as for Organizers (ADR 0054).
- Duplicate and impostor Clubs: staff handle them in the admin, for now (the project owner's decision on #230, 2026-11-27). Nothing stops two Clubs with the same name, and there is no merge or report flow. Staff handle a reported duplicate or impostor in the admin: rename it, remove its admins, or remove its grants. A later issue may add a moderator merge or a report flow. A Club with a Match cannot be deleted (`Match.club` uses `PROTECT`), and a merge would have to leave recorded matches as they are.

## Consequences

- A club sets itself up and grants its Organizers without staff. A grant only lets a verified Organizer name the Club; it never makes anyone a trusted submitter.
- Anyone with a verified address can create a Club with any name, up to the per-Account limit. An impostor Club can only consent to Organizers naming it; it cannot submit or change a match, and it cannot attach a real Club, by its OPEN Code, to an Organizer that Club did not grant. It can copy a real Club's name, which staff handle in the admin (below).
- A third party can make OPEN send a Club invite email to any address, bounded by the day throttle, the open invite cap, and the per-Account Club limit, as with Organizer invites.
- A grant removed while a submission is in flight may let that one submission through: consent is read when the match is submitted.
- Account deletion leaves a Club's name, city, and region as they are, even when the deleted Account was its only admin, since a Club is a place or group, not a person, and its name is not personal data (the personal data inventory, ADR 0009). A Club named after its only admin keeps that name until staff change it; staff rename a Club on request. This is decided (the project owner's decision on #335, 2026-11-27): ADR 0048's placeholder name rule stays Organizer-only, because an Organizer whose only member is the deleted Account is that person, and a Club usually is not.

## Alternatives considered

- Club admin operations under `/api/v1/organizer/`: refused, a Club admin is not an Organizer member.
- Showing granted Organizers' names to the Club: refused, an Organizer's name goes only to its members (ADR 0050).
- Requiring MFA to create a Club: not needed, as for Organizers (ADR 0054).
- Giving a Club a placeholder name when its only admin deletes their Account, as ADR 0048 does for an Organizer: refused (#335). A Club is usually not one person, and the personal data inventory does not count its name as personal data.
- Hiding whether an Organizer code exists from a granting Club admin, by Organizer consent before a grant or by one answer for an unknown code and an existing grant: refused (#335). OPEN Codes are public identifiers already.
