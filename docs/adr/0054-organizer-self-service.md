# 0054. Organizer self-service: create, invite members, request verification

- Status: Proposed
- Date: 2026-11-26

## Context

ADR 0021 makes the verified Organizer the only trusted submitter, but only staff created Organizers and their members, in the admin (#20). A club director, league coordinator, or tournament director needs to set up their Organizer themselves, bring in the people who help run it, and ask to be verified (issue #229). Verification stays a moderator action (#40), and who acts for an Organizer is a security-sensitive area (hard rule 8). The Club self-service issue (#230) needs the same invite rules.

## Decision

- Paths. A member's own Organizer operations live under `/api/v1/organizer/` (ADR 0050), so the issue's paths become: `POST /api/v1/organizer/organizers` (`create_organizer`), `PATCH /api/v1/organizer/organizers/{code}` (`update_organizer`), `POST .../organizers/{code}/invites` (`invite_organizer_member`), `POST /api/v1/organizer/invites/accept` (`accept_organizer_invite`), `GET .../organizers/{code}/members` (`list_organizer_members`), `PATCH` and `DELETE .../organizers/{code}/members/{player}` (`change_organizer_member_role`, `remove_organizer_member`), and `POST .../organizers/{code}/verification-request` (`request_organizer_verification`). The issue's `GET /api/v1/me/organizers` is the existing `list_my_organizers`, which gains `verification_requested`; there is no second list.
- Create. An active Account whose login address (`User.email`) has a verified `EmailAddress` row creates an Organizer and is its only member, as admin (403 otherwise, nothing written). It starts unverified. An Account may be an admin of at most `ORGANIZER_CREATE_LIMIT_PER_ACCOUNT` (default 5) Organizers before a create is refused (409). Creating needs no MFA: an unverified Organizer has no authority, and every admin action on it needs MFA.
- Admin actions. Every operation with an Organizer code in its path acts for an admin member: an active Account with MFA (ADR 0043) whose membership is admin, read from the database. An Account without MFA gets 403 `mfa_required` before any lookup, the same for every code. A non-member, a match manager, and an unknown or malformed code (or member Player code) get one 404, so the answer never says who is a member.
- Members are shown to admins by their Player's OPEN Code and display name, which every signed-in Account can already see (ADR 0002), never by email (ADR 0009), and are addressed by that Player code. Accepting an invite needs a Player, so every member added by invite is addressable; a creator or staff-added member with no Player shows `player: null` and is managed by staff. An Organizer always keeps one active admin: a change or removal that would leave none gets 409. Each locks the Organizer row first, so two concurrent demotions cannot both pass the count.
- Invites. An admin invites an address with a role. The answer (202) is the same whether or not the address has an Account, is a member, or was invited before. A member's address gets nothing; any other address replaces its earlier invite to that Organizer and gets one email, through `queue_email()`, with the single-use link `{FRONTEND_URL}/organizer/invites/{key}`, valid `ORGANIZER_INVITE_DAYS` (default 7). Only the key's SHA-256 is stored. The email names neither the inviter nor the Organizer's name (ADR 0050; the Email rules), only its OPEN Code, the role, and the expiry. An Organizer has at most `ORGANIZER_OPEN_INVITES_LIMIT` (default 50) open invites (409 past it), and the invite operation has its own per-Account day throttle (`API_ORGANIZER_INVITE_THROTTLE_PER_DAY`, default 20), since each one sends an email to an address OPEN does not know.
- Accepting. The signed-in Account accepts when its login address is the invited one and verified, it has a Player, the invite is unexpired, and it is not the verifier of the verified Organizer (the `OrganizerMember.save` rule). Every refusal is one 404, so a holder of a leaked key learns nothing. Already a member: 409, and the invite is used up. The membership goes through `apps.audit.access` with the accepting Account as actor.
- Verification request. An admin asks moderators to verify, with a statement of what the Organizer runs (at most 1000 characters). One open request per Organizer; a verified Organizer cannot ask (409). Nothing is verified automatically. Moderators (`clubs.view_organizerverificationrequest`, added to the Moderator group) see the requests in the admin, except on an Organizer they are a member of. `verify_organizer()` closes the open request in its transaction (rule `verified`); a moderator closes one without verifying with a typed reason (rule `moderator`).
- Audit Events: `organizer.create` (no values), `organizer.change` (`after.fields` names the field), `organizer_invite.create` (the OPEN Code and the role), `organizer_verification_request.create` (the OPEN Code) and `.close` (`closed_at`, `rule`), and the existing `organizer_member.*`. None holds the name, an address, or the statement (ADR 0009). The invite event's target is the invite row, which is later deleted, as a report's is.
- Retention. An invite is deleted when accepted, when it expires (the daily `sweep_organizer_invites` task), and at Account deletion (the invites to the Account's addresses and those it sent). Account deletion blanks the statements of an Organizer whose only member it was, with the name (ADR 0048). Invites are not in the data export: they are short-lived, and the sender's events are.
- Reuse. `apps/clubs/invites.py` holds the generic rules: the abstract `InviteModel` (address, key hash, sender, lifetime), key making and hashing, address normalization with the Account email rules, the lookup by hash, the match to a verified login address, and the sweep. `OrganizerInvite` adds the Organizer and the role; the Club invite (#230) adds its own.

## Consequences

- An Organizer can be set up without staff, but it records nothing that counts until a moderator verifies it.
- A third party can make OPEN send an invite email to any address, bounded by the day throttle, the open invite cap, and the per-Account Organizer limit. The email names no person and asks for nothing but a sign-in.
- Two answers can differ by timing (an email is queued for a new address, not for a member's), which is accepted: the bodies and status codes are the same.

## Alternatives considered

- Members by email in the member list: refused, an email is never returned by any API except to the Account itself (ADR 0009).
- Invite by Player code: an Organizer often invites a helper who has no Player yet, and a code lookup would confirm a Player exists to the inviter.
- A requester field on the verification request: the create event's actor already names the Account, and moderators verify the Organizer, not the person who asked.
