# 0010. Partner applications: a swapped OAuth Application model

- Status: Proposed
- Amended by: [ADR 0021](0021-organizers-are-the-trusted-submitters.md) (the Organizer Application Grant, an Organizer's permission for one application, replaces the Club Application Grant)
- Date: 2026-11-15

## Context

Partners reach OPEN's APIs as OAuth2 clients (decision Q2 in issue #1). django-oauth-toolkit stores each client as an `Application`. OPEN needs more on it than the toolkit gives: an owning Organizer, a moderator's approval (who and when), and a sandbox flag (#29, #74, #79).

The toolkit lets a project swap in its own Application model with `OAUTH2_PROVIDER_APPLICATION_MODEL`. Like `AUTH_USER_MODEL`, the swap is only practical before the toolkit's tables exist: afterwards every token table points at the old model (decision Q3).

The toolkit's first migration has foreign keys to the swapped model but does not depend on it. Without help, Django can run it before the model's own table exists.

Client secrets let a partner submit matches that may count as confirmed, so how they are stored matters (hard rule 8).

## Decision

- `apps.partners.models.PartnerApplication` extends the toolkit's `AbstractApplication` and is the swapped model, from django-oauth-toolkit's first migration on. It is fixed from here: never swap it. ADR 0001 expected this model before every other app's migrations; it only needs to come before the toolkit's, and its migration depends on the `clubs` app for the owning Organizer.
- It adds `organizer` (optional, `PROTECT`), `approved_at` and `approved_by` (`approved_by` uses `PROTECT`; both are written only by #29's approval service), and `is_sandbox` (true by default; #29 and #74 will enforce it). A new application starts unapproved.
- `apps/partners/migrations/0001_initial.py` was generated by makemigrations, then given one hand edit: `run_before = [("oauth2_provider", "0001_initial")]`, as the toolkit's documentation advises for a swapped model. A test checks the order.
- Client secrets are always stored hashed. A check constraint refuses `hash_client_secret=False` and another refuses a blank secret. A secret written through the model must be a raw secret: not blank, and not anything Django's `identify_hasher` recognizes. The toolkit stores a value that looks like a hash as is, and when the hash check fails it compares the value as plain text, so such a value would act as a plain-text secret. A hash-shaped value is never written back, so a save cannot replace the stored hash with one.
- `AuditEvent` gains `actor_application`, a nullable `PROTECT` foreign key to the swapped model, so an action a partner takes is recorded with the application that took it. This adds to ADR 0007's actor.
- `ClubApplicationGrant` (a Club's permission for one application to submit its matches) lives in the same app, since it points at the application.
- Only the toolkit's token and revoke views are mounted, at `/oauth/token/` and `/oauth/revoke_token/`. Other OAuth flows land with their issues (#75).
- Settings turn on every RFC 9700 behavior the toolkit offers, including tokens hashed at rest.

## Consequences

- Swapping the model later would mean migrating every token table by hand. Treat the setting like `AUTH_USER_MODEL`.
- A toolkit upgrade that changes `AbstractApplication` needs a new `partners` migration. `makemigrations --check` catches a missing one. An upgrade that changes the toolkit's first migration needs the `run_before` line checked again.
- An application that has acted cannot be deleted (`actor_application` uses `PROTECT`), and the toolkit's `user` foreign key cascades, so an Account whose application has acted cannot be hard-deleted either. #29 revokes applications instead of deleting them, and #116 plans Account deletion around this. An Organizer with an application cannot be deleted.
- Until #27, #28, and #29 land, the token endpoint issues tokens without checking approval, the sandbox flag, or which scopes each application may have. No API operation accepts an OAuth token yet.
- Raw writes (`QuerySet.update`, `bulk_create`, `loaddata`, raw SQL) skip the model's checks. The database still refuses an empty secret and `hash_client_secret=False`.

## Alternatives considered

- **Keep the toolkit's own Application and add a one-to-one profile model.** Rejected: every token check would need a join to read approval, and nothing would stop an application without a profile from getting tokens.
- **Write our own OAuth2 server.** Rejected: more security-sensitive code for volunteers to maintain, and the toolkit ships an auth class for django-ninja (decision Q2).
- **Leave the migration order to chance.** Rejected: nothing in the migration graph makes `partners` run first, so migrating an empty database could fail.
