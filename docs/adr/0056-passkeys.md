# 0056. Passkeys (WebAuthn) for the browser client

- Status: Proposed
- Date: 2026-11-26

This amends [ADR 0043](0043-mfa-totp-and-recovery-codes.md) (WebAuthn is a method, a passkey can sign in alone, and every passkey change needs a recent reauthentication and is audited) and [ADR 0045](0045-harden-the-admin.md) (the admin needs TOTP in particular).

## Context

ADR 0043 turned on TOTP and recovery codes and left passkeys for issue #117. Passkeys are the phishing-resistant way to sign in. The PWA (#182) uses allauth's headless browser client. Native app passkeys are #185.

allauth's WebAuthn support works, but as it ships it does not meet OPEN's rules. It takes the relying party ID from the request's host. It accepts a credential from any subdomain of that ID. It names the Account to the authenticator by its row id (the WebAuthn user handle), finds a passkey login's Account by decoding that handle, and lists each passkey by its Authenticator row id. Its views record nothing in OPEN's audit log and read the input before the reauthentication rule. Its passkey signup needs email verification by code, which ADR 0043 keeps off, and would skip OPEN's own signup view.

## Decision

- **Methods.** `MFA_SUPPORTED_TYPES` is TOTP, recovery codes, and WebAuthn, and `MFA_PASSKEY_LOGIN_ENABLED` is on. A passkey is a method: `has_mfa` counts it, so an Account that must have MFA can meet the rule with one. Adding a first passkey makes recovery codes, as TOTP does. A passkey login records an MFA step, so the session counts as having passed MFA for the API and the admin. Passkey signup stays off (`MFA_PASSKEY_SIGNUP_ENABLED`), and `auth/webauthn/signup` is not served. "Trust this browser" stays off. `MFA_WEBAUTHN_ALLOW_INSECURE_ORIGIN` stays off.
- **Malformed input.** OPEN reads every credential before allauth does and answers anything malformed with allauth's `incorrect_code`, never a 500: client data over 4 KiB, an attestation object over 16 KiB, authenticator data or a signature over 4 KiB, CBOR or JSON nested past Python's recursion limit, extension results that are not objects (or a non-boolean `rk`), a credential id that is not the attested one, a public key fido2 cannot verify with (checked when the passkey is added), and, for a row stored before these checks, a public key that fails while an assertion is verified.
- **Relying party.** `WEBAUTHN_RP_ID`, read from the environment, default `openpb.org`: the registrable domain, not the PWA's host, so passkeys keep working if the PWA moves to another subdomain and native apps can share them later. #182 confirms the production domain. It must be a lowercase domain name or `localhost`, with no scheme, port, path, IP address, or trailing dot; a bad value stops startup. OPEN's MFA adapter gives allauth this ID, named `OPEN`, never the request's host.
- **Origins.** `WEBAUTHN_ALLOWED_ORIGINS`, exact origins read like `CORS_ALLOWED_ORIGINS` (https only with DEBUG off), defaults to `FRONTEND_URL` alone. Every input that carries a credential (add, the MFA login stage, reauthentication, passkey login) reads the credential's client data and refuses it with allauth's `incorrect_code` unless its origin is exactly an allowed origin, before allauth verifies it, so a refusal uses no challenge and changes nothing. The system check `accounts.W001` warns when an allowed origin is not on the relying party ID or a subdomain of it, since browsers would then refuse the passkey. It is a warning so older local `.env` files keep working; the deploy check fails on it. The app client serves the same views, but a native app's origin is not allowed, so its passkeys wait for #185.
- **No row ids.** The user handle is a keyed hash of the Account id (`apps.accounts.passkeys.user_handle`). Passkey login finds the one passkey with the assertion's credential id, takes its Account, and refuses a user handle that is not that Account's, made with `SECRET_KEY` or a key in `SECRET_KEY_FALLBACKS`. allauth then verifies the assertion against that Account's passkeys and requires user verification. Adding a passkey refuses a credential id any Account already holds (the WebAuthn registration step allauth leaves out), so the lookup finds at most one. Each passkey is named in the API by a keyed hash of its row id (`public_passkey_id`): in the authenticator list and the add and rename answers. Rename and remove accept only those ids, mapped through the Account's own passkeys, and refuse any other value with one fixed message. The session's MFA records lose the Authenticator id, as for TOTP. allauth's OpenAPI document describes the passkey id as a string.
- **Views and rules.** OPEN subclasses allauth's authenticator list, passkey, passkey login stage, passkey reauthentication, and passkey login views and serves them at allauth's paths for both clients (`apps/accounts/mfa_views.py`). Each runs in a transaction and locks the Account row first. Every method of the passkey view, the creation options included, needs a session that passed MFA (for an Account with MFA) and a recent reauthentication, checked before the input is read. The login stage and reauthentication answer allauth's lockout with 429. Passkey login checks the assertion without a lock, then locks the Account row before it writes anything and reads the passkey and its Account again under that lock: a passkey removed meanwhile is refused with `incorrect_code`, and the login uses the Account as it is then. A session signed in to another Account is logged out first (allauth's logout), since Django's login would flush the passkey's MFA step with it. It keeps allauth's per-IP rate limit and every login rule (an inactive Account, the email verification stage, OPEN's adapter).
- **Audit and sessions.** Adding a passkey records `mfa.change` `added webauthn` (and `added recovery_codes` when codes were made); removing records `removed webauthn` per passkey (and `removed recovery_codes` when no method is left) and ends the Account's other sessions, as removing TOTP does (ADR 0047). A password reset from a key removes every passkey of the Account in the reset's transaction, recording `removed webauthn` per passkey (and `removed recovery_codes` when no method is left): someone who knew the password could have added a passkey, which signs in alone, and the reset is how the mailbox owner takes the Account back. A signed-in password change keeps the passkeys, since the player sees and removes them there. A rename, a passkey login, and a passkey reauthentication record nothing. No event holds a credential, a public key, a name, or a handle.
- **Data.** A passkey's Authenticator row holds the name the player chose and the browser's registration response: the credential id, the public key, and the attestation. None of these is a secret, so the row is not encrypted. The data export (ADR 0051) lists each passkey as a `webauthn` method with its name and dates, never its credential, public key, or user handle; the new `name` field is optional and null for the other types, so `format_version` stays `"1"`.

## Consequences

- A player can add a passkey from the PWA and sign in with it, use it as a second factor after the password, or reauthenticate with it.
- A passkey made for a subdomain the PWA does not use, even under `openpb.org`, never signs in to OPEN.
- Rotating `SECRET_KEY` changes every user handle. Old passkeys keep working while the old key is in `SECRET_KEY_FALLBACKS`; once it is removed, a passkey made before the rotation fails passkey login (it still works at the MFA login stage and for reauthentication). The player removes that passkey from the passkey list, then adds it again. Rotating also changes every public passkey id, which the app reads again from the list.
- The admin's login script asks only for codes, so the admin needs a TOTP authenticator in particular (`apps.accounts.mfa.has_totp`): a staff Account whose only method is a passkey gets the page asking it to set up two-factor authentication, and staff or superuser status cannot be granted to it. This amends [ADR 0045](0045-harden-the-admin.md). The API and Organizer rules still count a passkey. A staff Account with TOTP whose session signed in with a passkey passes the admin's time limits, since that is an MFA step.
- Passkey signup needs email verification by code first, with the view overrides ADR 0043 lists, and an OPEN signup view for passkeys. That is a later issue.
- The credential id uniqueness check is a query when a passkey is added, with no database constraint behind it. Accepted: to race it, an attacker would need the victim's credential id before it is registered, and passkey login refuses an id it finds twice.
- Passkey login finds the passkey with an unindexed filter on the Authenticator's JSON data. It runs behind allauth's per-IP `webauthn_login` limit, and the table holds a few rows per Account; an index can come when it is needed.
- allauth's private WebAuthn helpers (`complete_authentication`, the payload builder) may change in a minor release. Tests pin the behavior.
