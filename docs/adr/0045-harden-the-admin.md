# 0045. A private, MFA-only, fully audited admin

- Status: Proposed
- Amended by: [ADR 0048](0048-account-deletion.md) (#317: the Account admin's delete runs Account deletion, and no staff or superuser Account is deleted in the admin)
- Amended by: [ADR 0056](0056-passkeys.md) (the admin needs a TOTP authenticator: a passkey alone does not open it or allow a staff grant, since the login page takes only codes)
- Date: 2026-11-26

## Context

Staff use the Django admin to verify Organizers, void matches, close Organizer Reports, and manage Accounts, Clubs, and Partner Applications. Anyone who reaches it with staff credentials can change other players' records and ratings (hard rule 8). ADR 0043 made the admin need MFA on the Account, but its login still asked for the password only, it sat at the well-known `/admin/` path, only some of its changes wrote Audit Events, and any staff Account with `accounts.change_user` could grant staff or superuser status. Issue #101 asks for a private path, a login with the second factor, short admin sessions, reauthentication before changes, an Audit Event for every admin change, and grants of admin power by superusers only. The admin keeps allauth headless only (ADR 0014): allauth's server-rendered pages are not mounted.

## Decision

This amends ADR 0014 (the admin login is allauth's headless login), ADR 0017 (that login no longer flushes another Account's session), ADR 0033 (a second admin mixin comes first), and ADR 0043 (the admin login asks for the code).

- **Path.** The admin is served at `ADMIN_URL`. With DEBUG on it defaults to `admin/`, so local commands and tests keep working. With DEBUG off it is required and may not be `admin/`, so `/admin/` answers 404 in production. Production sets it in the App Platform console, like a secret. The path is obscurity, not a control: every rule below still applies.
- **Login.** Django's admin login form is gone. OPEN's admin login page takes no password (a POST gets 405) and its inputs have no names, so a submit without its script sends nothing typed. Its same-origin script signs in through allauth's headless browser client: `auth/login`, then `auth/2fa/authenticate`. So the admin login has allauth's rules, mandatory email verification, and rate limits, the same as a player's (#100 tunes them), and OPEN's MFA views (ADR 0043), which audit a recovery code's use. A signed-in staff session that has not passed MFA, or whose admin session has run out, confirms a code through `auth/2fa/reauthenticate`. A server-side two-step form was rejected: allauth's login stages build responses for its headed pages, which OPEN does not mount (with `HEADLESS_ONLY`, reversing those pages fails and allauth returns a 500 that its headless views discard), and only its headless views turn a pending stage into an answer, so the admin would have had to repeat allauth's login steps itself.
- **Who gets in.** `OpenAdminSite.has_permission` needs an active staff Account with MFA whose session's latest MFA step is within `ADMIN_SESSION_SECONDS` (default one hour). A signed-in Account that is not active staff gets 404 on every admin URL, the login page included. An active staff Account without MFA gets a page telling it to set one up in the OPEN app. Logout works for any signed-in active staff Account, whatever the time limits.
- **Reauthentication before changes.** Every admin write (any request but GET, HEAD, and OPTIONS, logout aside) needs an MFA step within `ADMIN_REAUTHENTICATION_SECONDS` (default 300, or the session limit if lower; at least 30). Otherwise nothing runs and the request is redirected to the login page, which asks for a code; the staff member then submits again. Every write counts as sensitive: each one changes another party's records, and picking a subset would leave the next new action unguarded.
- **Audit.** Every registered admin, OPEN's and third-party ones, gets `AdminAuditMixin` first in its bases at registration. Each add, change (when a field changed), and delete records `admin.add`, `admin.change`, or `admin.delete` with `request.user` as actor, in the change's transaction, a delete before the row goes. Values are recorded only for an explicit list of fields per model (the Account's `is_active`, `is_staff`, `is_superuser`, groups, and user permissions; a Group's name and permissions); every other changed field shows by name only, so no identifying value, hash, secret, or token reaches an event. Each custom action records one `admin.action` per selected object, in one transaction with the action, unless its service already records one event per object (verify, unverify, report close, the bulk voids, which must not run in an outer transaction). Admins whose saves and deletes already go through audited services (Events, grants) record no generic model events. The admin's own password change records `password.change`.
- **Admin power.** Only a superuser grants or removes `is_staff`, `is_superuser`, groups, or user permissions, changes or deletes an Account that holds any of them, or edits Groups. A staff or superuser Account is not deleted in the admin at all (ADR 0048, #317). Only a superuser adds, changes, deletes, or runs an action on django_celery_beat's periodic tasks and schedules, since a periodic task or its schedule can send any registered task with chosen arguments. A grant of `is_staff` or `is_superuser` to an Account without MFA is refused, so a stolen password cannot finish an Account's admin enrollment.

## Consequences

- Signing in to the admin needs JavaScript, and a write redirected for a code loses the form's data: the staff member enters it again.
- A staff Account needs a verified login address to reach the admin, as for any allauth login. An Account made with `createsuperuser` verifies its address and sets up TOTP through allauth's endpoints first. Until it enrolls, someone with its password can enroll their own TOTP and reach the admin, so operators should enroll a new superuser at once. The grant rule above closes this for staff granted in the admin.
- An admin session that passed MFA is also a full API session (ADR 0043), as any MFA login is.
- Every staff Account that changes anything in the admin becomes an Audit Event actor, so it can be deactivated but not hard-deleted (ADR 0007). Admin events also point at third-party content types (Group, django_celery_beat, oauth2_provider), which `remove_stale_contenttypes` cannot then drop.
- A custom action's events commit with the action's database changes. Work an action does outside the database (django_celery_beat's `run_tasks`, superuser-only, publishes Celery tasks) is not rolled back if the transaction fails after it, so such work can happen without its event.
- A signed-in non-staff POST without a CSRF token gets Django's CSRF 403 before the 404 rule runs, on every admin URL but the login page, which takes no POST and answers 404 or 405. The CSRF check stays first; an anonymous GET shows the login page anyway, so the 403 reveals nothing more.
- Saving a third-party admin form that shows a date-time field with microseconds stores it without them, and `admin.change` records that field. The Account admin shows `last_login` and `date_joined` read-only for this reason.
