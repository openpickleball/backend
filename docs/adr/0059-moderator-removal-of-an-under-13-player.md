# 0059. Moderator removal of an under-13 player's personal data

- Status: Proposed
- Date: 2026-11-27

This amends [ADR 0009](0009-personal-data.md), [ADR 0029](0029-moderator-review-in-the-admin.md) (the Moderator group also holds `players.view_player` and `players.remove_underage_player`), [ADR 0046](0046-encrypt-personal-data-fields.md) (the Player admin is no longer read-only for this one action), and [ADR 0048](0048-account-deletion.md).

## Context

OPEN refuses anyone under 13 at sign-up and on every path that creates a Player (ADR 0017). A player can still give a wrong birth year and month. Issue #190 asks for a way for a moderator to remove the personal data of a player found to be under 13. The project owner settled the main points in a comment on #190 (2026-11-27): the player is shown exactly as after Account deletion, the removal builds on Account deletion rather than a second set of rules, the data export goes, and a full recompute (ADR 0058) checks the ratings.

## Decision

- **Account deletion's own steps.** `apps.players.underage.remove_underage_player(player, *, moderator)` calls `apps.accounts.deletion.delete_account()` for the Player's Account. Everything `delete_account` removes (ADR 0048) goes, with no step of its own. A Player in the Ledger stays with its OPEN Code, display name `DELETED_PLAYER_NAME`, every other personal data field cleared, and every privacy setting private, rating visibility included. A Player nothing protects is deleted. The Account is kept deactivated or hard-deleted, as ADR 0048 decides. It cannot sign in again.
- **Its own event.** `delete_account` takes a keyword-only `action`: `account.delete` (the default, unchanged) or `player.underage_remove`. Any other value raises before anything is written. The removal records one `player.underage_remove` Audit Event, with the moderator as actor and the Account as target, and `after` = `account_kept`, `player_kept`, and, when the Account had a Player, `fields` (the names of the cleared Player fields). It records no `account.delete` event. It takes no free-text reason, so the event can hold no personal data. Events Account deletion records for access changes (a membership or Club Role removal, an Organizer name removal) still happen, with the moderator as actor.
- **Who may run it.** Only an active Account with the new permission `players.remove_underage_player`. An active superuser holds it. The service reads `is_active` from the stored Account, held `FOR KEY SHARE` (`hold_active_account`), and checks the permission on a freshly loaded instance's `has_perm`, so a stale in-memory Account or permission cache counts for nothing. That lock waits only for a `FOR UPDATE` (Account deletion, `create_player`), not for a plain update: a deactivation of the moderator or a revocation of the permission that commits at the same time may let one removal finish, whichever commits first. It refuses the moderator's own Player, and a Player whose Account is staff, superuser, or holds a group or permission, as the Account admin's delete refuses (#317). It raises `AccountAlreadyDeleted` when a deletion already cleared the Account. Every refusal comes before any write.
- **The Moderator group holds the permission, and `players.view_player`.** Data migrations add them to the group (`players.0009_moderators_remove_underage_players` and `players.0010_moderators_view_players`, the owner's decision so moderators reach the removal in the Player admin), and `MODERATOR_PERMISSIONS` lists both. The group still lacks `players.view_personal_data`. The permission amounts to deleting the personal data of any non-staff Account that holds no group or permission. The service checks no age: whether the player is under 13 is the moderator's judgment. A moderator in the Player admin sees: on the list, each Player's OPEN Code and display name, and a search box that matches the OPEN Code only (no filters, no actions, and every query-string lookup refused with 400); on the change page, the OPEN Code, display name, city, and region, the Account, legal name, birth year and month, and gender division as "Hidden" (never decrypted), the "Remove personal data (under 13)" button and the History link, and no reveal button. The Account shows "Hidden" to anyone without `players.view_personal_data` (the owner's decision), so no Player page shows a moderator the Account email or links to the Account admin; staff who hold it see the Account as its email, linked to the Account admin, as before.
- **The admin.** The Player admin's change page shows a "Remove personal data (under 13)" button only to an Account with `players.view_player` and `players.remove_underage_player`. It leads to `<object_id>/remove-under-13/`: a GET shows a confirmation page naming only the OPEN Code, and a POST runs the service and returns to the change page (Player kept) or the list (Player deleted), with a message naming only the OPEN Code. Both refuse with 403 without both permissions. A POST is an admin write, so it needs a recent MFA step (ADR 0045). The view records no event of its own.
- **Lock order.** The moderator's Account `FOR KEY SHARE`, then the Player's Account `FOR UPDATE`, then what `delete_account` takes (the same Account again, the Player, the Organizers).

## Consequences

- The Ledger does not change, so a full recompute gives every player, the removed player's kept Player included, the same ratings as before. A test checks this.
- A kept Player's birth year and month are NULL, so it is left out of all partner sharing for good (ADR 0009). No partner sharing code exists yet; the rule holds for when it lands.
- The same email can sign up again, as after Account deletion. The sign-up age check trusts the birth year and month entered, so the same person can sign up again with a false date. This is an accepted limit, as it is after Account deletion.
- As for Account deletion, an uploaded CSV results file that names the player is not scrubbed: it ages out within 30 days (ADR 0009, Retention). This is inherited, not new.
- Moderators see more about a player than before. The Organizer report admin shows a reporter only as their Player's OPEN Code, and the match admin shows participants by OPEN Code only (ADR 0037, `apps/matches/admin.py`), but a moderator can now search that code in the Player admin and see the Player's display name and city and region.
- The removal is recorded only as `player.underage_remove`. Anyone reading the audit log can tell a removal from a player's own deletion.

## Alternatives considered

- A separate removal service that clears the Player fields only. Rejected by the project owner: it would be a second set of rules that can drift from Account deletion, and it would leave the Account able to sign in.
- Hold the permission in no role, granted by a superuser to each Account. Not chosen: finding a player under 13 is moderation work.
- Take a free-text reason. Rejected: a moderator's note could hold personal data, and the action itself says why.
