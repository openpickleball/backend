## Players

- Create a Player only through `apps.players.services.create_player()`, which also creates its `PlayerPrivacy` row. Change profile fields only through `update_profile()` and privacy settings only through `update_privacy()`. Both refuse any actor but the Player's own active Account, and record one Audit Event when a value changes. The birth year and month and the gender division are set once, when the Player is created: `update_profile()` refuses them (`SET_ONCE_FIELDS` in `apps/players/models.py`), whatever the value (ADR 0023).
- A profile change records only the changed field names, never a value (ADR 0009). A privacy change records the old and new levels of the changed settings.
- `Player.account` uses `PROTECT`, so an Account with a Player cannot be hard-deleted: Account deletion keeps both, cleared (see Account deletion). `MatchParticipant.player` uses `PROTECT` too, so a Player who has played a Match cannot be deleted.
- Age limits follow `apps/players/age.py` (ADR 0017): the end-of-month rule, judged on the date at UTC-12 (`age_limit_date()`). Never compare ages any other way. `Player` refuses a birth year and month under 13 whenever they are set or changed, and `create_player()` starts a player aged 13 to 17 with every privacy setting `PRIVATE`. Nothing changes privacy at 18.
- `rating_visibility` (current Ratings, ADR 0031) has its own rules in `update_privacy()`: a player created as an adult starts at `SIGNED_IN`, nobody can change it to `PRIVATE` (ADR 0002), and a player aged 13 to 17 cannot widen it to `SIGNED_IN` before 18. An unchanged value is always accepted. Its model default is `PRIVATE`, so a row made outside `create_player()` fails closed.
- `Player.account` and `PlayerPrivacy.player` override Django's foreign key messages with fixed text (`_LinkMessagesModel`, #162), as the clubs links do.
- In tests, build Players with `PlayerFactory` (`apps/players/tests/factories.py`), which goes through `create_player()`. It makes adults only, so default privacy holds; use its `minor` trait for a player aged 13 to 17. A raw `Player.objects.create()` has no `PlayerPrivacy` row.
- The Player fields are the ones ADR 0009 allows. Adding a personal data field updates `docs/privacy/personal-data-inventory.md` in the same pull request.
- `legal_name`, `birth_year`, `birth_month`, and `gender_division` are stored encrypted (`apps.encryption.fields`, ADR 0046): a Fernet token in a text column, read back as the Python value. Any lookup on them but `isnull` raises `FieldError` (tokens never compare equal), so never filter or search on them. `order_by()` and `distinct()` on them still run, on the ciphertext, so their results mean nothing: never use them. `values()` and `values_list()` decrypt. The database cannot check them, so `Player.save()` refuses a birth year below 1900 or not an int, a birth month outside 1 to 12 or not an int, a legal name that is not text or is over 200 characters, and a gender division that is not text or is other than `mens`, `womens`, or `""`, with the model's fixed messages, on every save and for the fields an `update_fields` save names. Raw writes (`QuerySet.update`, `bulk_create`, raw SQL, `loaddata`) skip these checks, so the database no longer limits these fields' values or lengths (the columns are text); the display name's check constraint stays. `save()` reads `update_fields` once (a frozenset), so the check and Django's save see the same fields. The Player admin defers the four fields in its queries, so its list and detail pages never decrypt them (only the reveal does).
- The Player admin (`apps/players/admin.py`) is read-only for everyone, except the under-13 removal (ADR 0059), and shows those four fields only as "Hidden". Only an Account with `players.view_personal_data` (and `players.view_player`) reveals them, with a POST that records a `player.personal_data_view` Audit Event and shows the values in that uncached response only. Superusers hold it implicitly. The Moderator group does not hold it; keep it out of `MODERATOR_PERMISSIONS`. Never list, search, filter, or sort on an encrypted field in an admin.
- A moderator removes the personal data of a player found to be under 13 only through `apps.players.underage.remove_underage_player(player, moderator=...)` (#190, ADR 0059), which runs Account deletion's steps. It needs an active Account with `players.remove_underage_player` (superusers hold it implicitly), with `is_active` read under `hold_active_account` and the permission checked on a freshly loaded Account (a deactivation or revocation that commits at the same time may let one removal finish, whichever commits first), and checks no age (the moderator's judgment), and refuses (`UnderageRemovalRefused`, before any write) the moderator's own Player and a Player whose Account is staff, superuser, or holds a group or permission. No role holds the permission by default; keep it out of `MODERATOR_PERMISSIONS`. In the Player admin, an Account with it and `players.view_player` sees the "Remove personal data (under 13)" button; its confirmation page (`<object_id>/remove-under-13/`) names only the OPEN Code, and its POST needs a recent MFA step (ADR 0045).
- Player search (`search_players`, ADR 0018) returns only each Player's OPEN Code and display name, never a Player whose Account is inactive, and includes players aged 13 to 17. It is allowed before Ratings are published. Keep its minimum query length, result limit, and per-Account throttle when changing it.
- A player's profile (`get_player`, `GET /api/v1/players/{code}`) shows any signed-in Account only the OPEN Code, the display name, and the city and region while `city_region_visibility` lets the viewer (null when hidden or empty, so the two look alike). A Player whose Account is inactive gets the same 404 as an unknown code. Never add the legal name, birth year or month, or gender division to it.
- `POST /api/v1/me/player` (`create_my_player`) creates the Account's Player only when the Account's own login address (`User.email`) has a verified `EmailAddress` row (403 otherwise), and gives 409 for a second Player, including one that loses the race to `create_player()`'s lock. Every value comes from the signup hold (`peek_signup_details`, then `take_signup_details` once the Player exists or on a 409, so a create refused for any other reason can retry), the held legal name as the legal name and, for an adult, the display name (a player aged 13 to 17, judged with `is_minor()` at create, starts with "First L."), and from the body only when the session holds none, where the display name, birth year, month, and gender division are then required (ADR 0017, ADR 0019, ADR 0022). `GET` and `PATCH /api/v1/me/player` return and change the own profile; PATCH calls `update_profile()` and `update_privacy()` in one transaction, so a 422 on either changes nothing. PATCH refuses the birth year and month and the gender division with a fixed 422 (`set_once`) on each one sent, and the OpenAPI document does not list them for PATCH (ADR 0023).
