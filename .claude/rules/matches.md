## Matches

- `apps/matches` is the match ledger (hard rule 3). A Match is never deleted, and no field but its status ever changes. The ORM refuses (`MatchImmutable`) to delete a Match, Match Participant, Game, Match Confirmation, Match Vouch, or Submission Batch, to save an existing one (except a Match with `update_fields=["status"]`, and a Submission Batch's `expected_size`, set once while empty, see below), and `QuerySet.update`, `delete`, `bulk_update`, and an upsert on any of them. Raw SQL, raw saves (`loaddata`), and migrations' historical models are not guarded. In tests, change a Match only through a service, or through the `raw_update()` helper (`apps/matches/tests/factories.py`, Match only) when a test needs a state no service produces.
- Every change to a Match after it is created goes through `apps.matches.workflow` (ADR 0013): `confirm_match`, `dispute_match`, `withdraw_dispute`, `resolve_dispute`, `void_match`, `edit_match`, `expire_unconfirmed_matches`, `expire_disputes_and_holds`, and the moderator bulk voids (see below). `vouch_for_match` resolves flags and changes no status. The only other status change is `record_match()`'s duplicate path, which confirms a pending Match. Never set `status` anywhere else. An edit voids the old Match and creates a corrected one through `record_match()`'s creation core, with `corrects` pointing to the old one; the correction is pending when the old Match was pending, and confirmed otherwise (an edit of a disputed Match, by the settling Organizer, confirms it). A player's correction is the exception (#267). Only the `correct_match` operation makes one, through `edit_match(as_player=True)`. The actor is a participant of a pending or disputed self-reported Match, and the correction keeps its two teams, in either order (`corrects_as_player`). The correction is pending, and the corrector's `confirm` row is written in the same transaction. A player gives no reason, and a confirmed Match gets `MatchStateError`. Its `match.edit` event's `after` adds `correction_status`. Unlike other corrections, its submitter is the correcting player's Account, so `void_submitter_matches` finds it under that player (ADR 0013, ADR 0034). Each service checks permission first (`MatchActionDenied`, fixed text), then locks and checks state (`MatchStateError`, fixed text), writes one Audit Event per transition, and sends its signals inside the transaction. A moderator is an active Account with `matches.moderate_match`. Moderators do not review single matches (ADR 0034, #273): no service gives a moderator, as moderator, a way to confirm, resolve, edit, or void one match, or resolve a flag; their only match action is the bulk void (see below). Free-text reasons are stored only from the Event's verified Organizer settling a dispute (`settles_dispute`, ADR 0034), where the reason is required, and from a moderator's bulk void; anyone else giving one gets `ReasonRefused`, and `dispute_match` takes none, because the audit log cannot be erased. `resolve_dispute` allows only `settles_dispute`, and `void_match` only `can_change_match`, with no reason. Apart from a player's correction, `edit_match` lets an actor edit a disputed Match only when `settles_dispute` holds for it and the new teams, with a reason; anyone else gets `MatchStateError`, and a reason on a Match that is not disputed is refused. Every status change takes the Match's lineup advisory lock before its row lock: keep that order in any new path. Those locks last until the outermost transaction ends, so call each service in its own transaction, as with `record_match()` (the one exception is `create_match`, see below). Each transition writes one Audit Event: `match.confirm`, `match.dispute`, `match.dispute_withdraw`, `match.void`, `match.expire`, `match.edit`, or `dispute.outcome`. `withdraw_dispute` (ADR 0034) lets a participant withdraw their open dispute. It adds a `withdraw` row and never edits the dispute row. A dispute period starts at its opening row: the dispute row of the latest `match.dispute` event's actor. The open disputes are the period's dispute rows from the opening row on whose player has no `withdraw` row. So rows from a period a resolution settled never count again. While another player's dispute stays open, the Match stays disputed and nothing else is written. The last withdrawal returns it to the status in that event's `before`: confirmed, with `match_confirmed`, or pending, with no signal. A voided Match gets `MatchStateError` first. Then a repeat changes nothing, and a player with no open dispute gets `MatchStateError`. With no opening row, every withdrawal is refused. `vouch_for_match` writes one `match.vouch` per vouch row, and one `match.flag_resolve` per flag its vouch completes, with the completing voucher as actor.
- `expire_disputes_and_holds` (ADR 0034, #268, the daily task of the same name) voids a disputed Match whose open dispute began more than `MATCH_DISPUTE_EXPIRY_DAYS` ago (`dispute_started_at()`, see the next rule), then the newer Match of each open `possible_duplicate` flag older than `MATCH_DUPLICATE_HOLD_DAYS` whose earlier Match is confirmed and whose newer Match is not voided, which ends its hold on the earlier Match: that Match counts again (`release`) unless another open flag still holds it. A hold against a pending or disputed earlier Match never voids the newer one under this rule (maintainer decision on #268 and #265): otherwise a player's pending self-submission could void a verified Organizer's result. A correction keeps its original's place only while its chain keeps the same teams and date (maintainer decisions on #268): `_hold_sides()` gives each side its `_place()`, the row id reached by following `corrects` back until the match that corrects nothing or the first step whose teams (in either order) or `played_on` differ, and the lower one is the earlier Match; with no correction, or equal places, `duplicate_of` is the earlier one. So the flag's `match` is voided as the newer one unless it corrects a same-teams-and-date Match recorded before the other side's place, and then `duplicate_of` is voided instead when the correction is confirmed. Never let a correction that changed its teams or date keep an older place: an Organizer could edit an old match onto another Organizer's confirmed result and get that result voided. Like `expire_unconfirmed_matches`, each Match is voided in its own transaction through `_void`, trying the lineup lock and skipping a locked row, never waiting, and the rule is checked again under the locks. Each void writes one `match.expire` Audit Event, no actor, whose `after` holds the status and `rule` (`dispute` or `duplicate_hold`). The flag stays open: only `vouch_for_match` resolves one. A failed Match is logged by id and skipped (the hold pass skips a Match the dispute pass failed, so it counts once), then the run raises `ExpiryFailed` with the count.
- `dispute_started_at()` returns the `created_at` of the Match's latest `match.dispute` Audit Event while the period's opening row is still open. When the opener has withdrawn, it returns the `created_at` of the first dispute row still open. With no opening row it returns the event's time, the later and safe start. With no event, or no open dispute, it returns None. Rows are chosen by id, never by comparing times from different hosts. The expiry's candidate query matches a `match.dispute` event or a `dispute` row older than the cutoff, so it stays a superset of what `dispute_started_at()` can return.
- A `SubmissionBatch` holds the Submissions one submitter sent in one upload (#71) or bulk request (#72) (ADR 0032). A batch path creates one batch and passes it to `record_match(submission_batch=...)` for every match, which sets `Match.submission_batch` at creation only; single submissions leave it empty, and an edit's correction never inherits it. `expected_size` is how many matches the batch path means to record. It may be given at insert, or set once later, while empty, through `SubmissionBatch.set_expected_size()`; the CSV path sets it after parsing, before the first row, under the Results File lock (ADR 0049). `record_match()` refuses (`ValueError`, `BATCH_REFUSED`, fixed text) a batch whose stored row does not exist, whose submitter is not exactly the match's, or whose Event or Club (when set) differs from the match's, after the permission checks and before validation. It reads the batch from the database by id, never from the instance.
- A moderator voids a whole batch (`void_submission_batch`) or every match one submitter (Account or Partner Application) recorded on or after a date (`void_submitter_matches`, `created_at` in UTC, not `played_on`). Both refuse anyone but `is_moderator` with `MatchActionDenied` before reading anything, then a blank reason. They find matches by the batch link or the submitter link, never by a time range alone, and void each in its own transaction (`_void_as_moderator`, one `match.void` Audit Event with the run's reason), applying the own-Player rule (`moderates`) per match, and, under that match's locks, to every match an open flag links to it, since voiding it ends that hold (#326). They return `BulkVoidResult(voided, skipped, refused)`: skipped is already voided, refused is a match `moderates` refused for it or for a linked match. They refuse a batch or submitter that is not a stored row (`ValueError`) before reading any match, and record one `match.bulk_void` Audit Event per run that finishes, even one that voids nothing. Never call them inside an outer `transaction.atomic()`. A rerun resumes a run that stopped partway.
- `apps.matches.signals` sends `match_confirmed` once each time a Match becomes confirmed (a correction of a counting Match sends `match_changed` with `change=edit` instead) and `match_changed` (with `change` and `earliest_date`) when a counting Match is voided, corrected, disputed, or held by a new flag, and when a held Match counts again because the Match holding it was voided or vouches resolved the flag. Both are sent synchronously inside the transaction that made the change: a receiver may write rows there (the webhook outbox, #85), must enqueue other work with `transaction.on_commit`, and rolls the whole change back if it raises. Which Matches count is `Match.objects.counted()`: confirmed and not held by an open (unresolved) `possible_duplicate` flag linked to a Match that is not voided. A receiver checks it, since a held Match can be confirmed.
- The database enforces allowed choice values, exactly one submitter (`submitted_by_user` or `submitted_by_application`), each Player once per Match, game numbers 1 to `MAX_GAMES` with each number once per Match, no negative scores, a `match_type` that fits the Match's Event and Club links (see the choice values rule below), the `played_at` and `external_id` rules below, and one Match that is not voided per fingerprint (see duplicate detection below). `full_clean()` reports each of these with a plain message, except the game number range, which gives Django's generic constraint message. No model or database rule requires a game or contiguous game numbers. The models check only the score range, not the scoring rules (see the next rule). `record_match()` creates a Match with an Event confirmed (its submitter passed the permission rules, decision F4; a match with a Club and no Event is refused, ADR 0021), with a `match.confirm` Audit Event and `match_confirmed`, and a self-submission pending. `record_match()` records no confirmation itself; `create_match` (`apps/matches/api.py`) then calls `confirm_match` for the submitter in the same transaction, so a player's submission counts as their team's confirmation and the match waits only for the other team (ADR 0013, #197). That is the one place two services share a transaction: `confirm_match` takes the lineup lock `record_match()` already holds, then the row lock of a Match no other transaction can see yet, so the lock order holds. `record_match()` returns `RecordedMatch(match, created)`: `created` is False when a permitted submitter's exact duplicate confirmed an existing pending Match instead of raising `DuplicateMatchError` (ADR 0013), which never happens with a `submission_batch` (ADR 0036).
- Every path that submits a Match creates it through `apps.matches.services.record_match()`, never `Match.objects.create()`. `record_match()` first checks that each submitter it is given may submit the match (see the next rule), before any validation, then its batch, then refuses a Player whose Account is inactive (see Account deletion), then reads the Event's stored dates by id and calls `validate_match()` and then `full_clean()` on the Match, its participants, and its games before any lock, duplicate lookup, or write (the Event's dates are read by id after the permission checks, with the batch and inactive player reads, before validation), then checks for duplicates and writes the Match, its participants, games, and flags in one transaction. `validate_match()` holds the score validation rules, such as the game scores (the winner reaches the target and wins by 2 or more, or, past the target, wins by exactly 2), team size per format, no player twice, the allowed best-of and game target, 1 to `MAX_GAMES` games that decide the match, no future `played_on`, and, for a match with an Event, a `played_on` from the Event's `start_date` to its `end_date` (`outside_event_dates`, fixed text naming neither date, not added when `played_on` already has an issue; #207, ADR 0052). `validate_match()` takes those dates as plain input (`event_dates`); `draft_match()` reads them by id after the caller's permission check, so every `edit_match()` correction is checked too, and they are not read again under `hold_event()`'s lock (a date change in the admin or, while no match names the Event, the organizer Event API can slip in between; accepted). It also applies the defaults for a submission (target 11, side-out) and infers a missing best-of. Add a new score validation rule there, never in a submission path.
- A CSV upload (#71, ADR 0036) reads files only through `apps.matches.csv_format.parse_results_csv()` and records each parsed row with `record_match()` in its own transaction. The format is `docs/csv-format.md`; change the doc, the template, and the parser together. Change a `ResultsFile` only through `apps.matches.results_files` (and `void_submission_batch` and `void_submitter_matches`, which fail a pending one before voiding). Its task gets only the row id; the raw file (names and player IDs) lives in `content` until processing ends, and the report never holds a name or a cell value. Each row's transaction locks the Results File row before `record_match()`'s Event and advisory locks: keep that order. A row whose sequence already has a match in the batch, voided included, is never recorded again. Only valid rows are recorded; there is no all-or-nothing mode. Before the first row, under the file lock, processing sets the batch's `expected_size` to the file's number of match rows (`len(parsed.rows)`, failed rows included) when it is empty, so a rerun keeps it.
- Who may submit and change a Match is a security-sensitive area (hard rule 8), decided in one place: `apps.matches.permissions` (ADR 0012, amended by ADR 0021: the verified Organizer is the only trusted submitter). `can_create_match(actor, submission)`, where `submission` is a `MatchSubmission`, needs event authority for a match with an Event (a member, either role, of the Event's Organizer while it is verified and while the member's Account has MFA, or an approved application that verified Organizer owns or granted an `OrganizerApplicationGrant`) and club consent (a `ClubOrganizerGrant` to the Event's Organizer from the match's Club and from the Event's stored Club, each when set, read by id). A member's MFA is checked in `_account_acts_for` (ADR 0043). Every Account rule that grants Organizer authority reads membership through it, and `organizer_disputes`, `vouchable_holds`, and the notice recipients filter on `accounts_with_mfa()` to agree. Each also leaves out a member whose New Member Hold is in force (`apps.clubs.models.not_held()`, #232, ADR 0057). A match with a Club and no Event is refused for every actor. A match with neither is a player's self-submission (decision F1): only an active Account whose Player plays in it, never an application. A Club Role gives nothing. `can_change_match(actor, match)` allows only the approved application that submitted the match or a member of its Event's verified Organizer, never a Club admin; an edit also needs `can_create_match` for the new match. `settles_dispute(actor, match, new_player_ids=...)` decides who settles a dispute as the Event's verified Organizer (ADR 0034): `can_change_match` and `can_confirm_as_organizer` both hold (so an application whose Organizer is unverified, or whose grant was removed, is refused), and an Account has no Player in the Match's correction chain or in `new_player_ids` (the same own-result rule `moderates` applies to a bulk void). A Match with no Event has no Organizer level. Moderators (`is_moderator`) get no match rule of their own (ADR 0034, #273): a moderator is refused like anyone else unless another rule allows them, and the dispute operations in the API refuse a moderator who is not a member with the same 404. Their only match action is the bulk void, which applies `moderates(actor, match)` to each match: False when the Account has a Player in any match of the Match's correction chain (through `corrects`, both ways), read from the database by ids, so a moderator never voids their own result. The admin uses `is_moderator` only to show the bulk void actions. The `Moderator` group (`MODERATOR_GROUP`, `MODERATOR_PERMISSIONS`) holds only the permissions organizer verification, Organizer Reports, the bulk void, and the read-only admin need; a moderator also needs `is_staff` and MFA to reach the admin. `participant_player` decides who may confirm, dispute, or withdraw a dispute as a player, and who may read one match (`get_match`). `can_correct_as_player(actor, match)` (a participant of a Match with no Event and no Club) and `corrects_as_player(actor, match, team_a_ids=..., team_b_ids=...)` (the same, with the stored two teams in either order) decide a player's correction (#267); the API answers a refusal of either with the unknown-code 404. `can_confirm_as_organizer` decides who may confirm a pending Match alone. Every rule reads verification, approval, roles, grants, and `is_active` from the database by id, and refuses an unsaved actor, Event, or Club. `record_match()` raises `MatchPermissionDenied`, with fixed text that never says which rule failed, before any validation detail, duplicate lookup, lock, or write, so a refused submitter learns nothing about other matches. No rule reads payment status (hard rule 7). Add a submission rule there, never in a submission path.
- `validate_match` raises one `MatchValidationError` that lists every issue it finds as field, code, and message, the shape of the API's `FieldError`.
- Give `validate_match` one canonical reference per player: resolved Players, or codes already passed through `normalize()`. Use one kind for the whole call. The duplicate and both-teams checks compare references by equality, and a call that mixes kinds fails with `mixed_player_references`.
- `validate_match` sets no upper bound on scores and does not read `played_at`. `Game.full_clean()` refuses a score above the field's limit, and `Match.clean()` ties `played_at` to `played_on`.
- Duplicate detection is a security-sensitive area (hard rule 8). `record_match()` refuses an exact duplicate (a Match that is not voided, from any submitter, with the same two teams in either order, the same `played_on`, and the same game scores) and an `external_id` its Partner Application already used (for a Match in any status). Both raise `DuplicateMatchError` with `kind` and `existing_code`. The exception: a submitter with Event authority (ADR 0021) whose exact duplicate matches a pending Match confirms that Match and gets it back (`RecordedMatch(created=False)`), as does its retry (ADR 0013). A call with a `submission_batch` never confirms this way: its exact duplicate of a pending Match raises like any other (ADR 0036). `existing_code` is the earlier Match's OPEN Code only when the submitter may know it (the same Account or Partner Application submitted it, or the submitting Account's Player played in it), otherwise None; a repeated external id always names it. For an edit's duplicate, the editor takes the submitter's place. The API turns it into a 409 `ErrorResponse` (`config/api_errors.py`) whose item carries `existing_code` under the same rule, and leaves the key out when it is None. A near duplicate (same teams and date, other scores) is saved with one `MatchFlag(reason=possible_duplicate, duplicate_of=...)` per earlier Match. Advisory locks serialize submissions of one lineup and date, and of one external id, so concurrent submissions are caught too. The locks last until the outermost transaction ends, so call `record_match()` in its own transaction, never several times inside one outer `transaction.atomic()`: two such callers can deadlock whatever order they sort their matches in. A batch path (#71, #72) must record each match in its own transaction and report a result per match; an all-or-nothing mode, deferred for now (ADR 0036), must get its all-or-nothing result another way (ADR 0011).
- `Match.fingerprint` is the SHA-256 of the teams, date, and scores (`match_fingerprint()`). A partial unique constraint allows one Match per non-blank fingerprint unless it is voided, so the same teams playing the same scores twice on one day count as one match (`sequence` is not in the fingerprint). A Match written outside `record_match()` has a blank fingerprint and escapes the exact check, though a later submission flags it as a near duplicate. The factories set the fingerprint when a Match has participants and games.
- A `MatchFlag` marks a Match for review (CONTEXT.md, Flagged Match) and is its own row; only a `possible_duplicate` flag holds one (an `unusual_submission` flag is a signal, see below), so review never edits the Match. An open `possible_duplicate` flag holds both its `match` and its `duplicate_of` from counting until both its Matches are vouched for or the hold period voids the newer Match, whatever the new Match's status or submitter: `counted()` excludes both, unless the other Match is voided (ADR 0011, ADR 0013). This lets any permitted submitter hold a real Match until review, including a match from another Club or Event (ADR 0011, ADR 0012). Flags are not under the ledger guard; never delete one (nothing enforces this). Only `apps.matches.workflow.vouch_for_match` resolves one, through `_resolve_flag_rows`: it sets `resolution` (approved; `dismissed` is a legacy value nothing writes) and `resolved_at` and writes one `match.flag_resolve` Audit Event per flag, and the caller sends `match_changed` with `change=release` for each Match that counts again. The resolver is recorded only in the Audit Event. `vouch_for_match` (ADR 0034, #270) ends a hold: each Match of the flag is vouched for at its own level (`permissions.vouch_level`), a Match with an Event by its Event's verified Organizer (`settles_dispute`: a member whose Player is not in its correction chain, or the approved application that submitted it and still acts for that Organizer), a self-reported Match by its participants, and a legacy club-only Match by nobody. A self-reported Match is vouched for once Accounts whose Players play on each team have vouched, an Event Match once any vouch exists. A vouch covers every open `possible_duplicate` flag that holds the Match and whose other Match is not voided, writing one append-only `MatchVouch` row (under the ledger guard) and one `match.vouch` Audit Event per flag; a flag opened later needs a new vouch, and a repeat writes no vouch row and no `match.vouch` event (it can only resolve a flag already vouched for on both sides, which the services never leave open). A voided Match, and one no such flag holds, get `MatchStateError`. When both Matches of a flag are vouched for, the flag is resolved as approved with no reason, the completing voucher as actor, and `after["rule"] = "vouched"`. A vouch takes no text. A vouch row keeps counting after its voucher loses standing (a member removed, an Organizer unverified, an application unapproved, an Account deactivated), as a confirmation row does. Neither the service nor the API names the other Match of a flag (ADR 0011). A flag reason that is a signal only (`SIGNAL_FLAG_REASONS`) must stay out of `counted()` (ADR 0029), and every query that decides holds, vouches, expiry, notices, or the match admin filters on `reason=possible_duplicate` or leaves signal reasons out. An open `possible_duplicate` flag older than `MATCH_DUPLICATE_HOLD_DAYS` voids its newer Match when the earlier one is confirmed, where a correction keeps its original's place while its chain keeps the same teams and date (ADR 0034, see `expire_disputes_and_holds`); the flag stays open. Both links use `PROTECT`, so a flagged Match cannot be deleted.
- Unusual submissions (#206, ADR 0049): `record_match()` writes one `MatchFlag(reason=unusual_submission, rule=...)` per rule that fires, only for a new Match with an Event, as the last step of its write transaction, after a per-submitter advisory lock (`submitter_lock_key()`) that is the last lock it takes. The rules (`apps/matches/unusual.py`): `first_matches`, among the first `UNUSUAL_SUBMISSION_FIRST_MATCHES` on the Organizer's Events since its current `verified_at`, or the submitting application's first since its `approved_at`; `large_batch`, a Submission Batch whose `expected_size` is over `UNUSUAL_SUBMISSION_BATCH_SIZE`; `daily_volume`, past `UNUSUAL_SUBMISSION_DAILY_MATCHES` of the submitter's on the UTC `created_at` day; `player_daily_matches` (#207, ADR 0052), one of its players past `UNUSUAL_SUBMISSION_PLAYER_DAILY_MATCHES` matches on its `played_on`, one flag however many players are past. Every count but the last takes only new trusted submissions (Event matches with no `corrects`, any status, voided ones included). `player_daily_matches` counts every match of the player that day that is not voided, self-reported ones included (a correction counts once in place of the original it voided, and is never flagged), and takes no lock of its own, so concurrent submissions may miss each other (errs toward no flag). A self-submission, an `edit_match()` correction, and a submission that confirms a pending duplicate are never flagged. These flags hold nothing, change no rating, send no signal, notice, or Audit Event, and appear in no API response and not in the match admin: moderators see them only as `organizer_review()` counts. Keep any new lock out of the path after the submitter lock.
- `played_at` is stored with `played_at_utc_offset` (minutes east of UTC where the match was played), because Postgres keeps a timestamptz in UTC and drops its offset. Both are set or both empty, and `played_at` shifted by the offset must fall on `played_on` (a check constraint). `clean()` refuses a `played_at` without a time zone. A plain `save()` stores a naive value as UTC, so always pass an aware datetime.
- `external_id` is a Partner Application's own id for the Match. Only an application's Match has one, unique per application among Matches that are not voided, so a correction keeps it; `record_match()` still refuses an id used by a Match in any status. A check constraint refuses leading or trailing whitespace (every character `str.isspace()` matches).
- `location` is a place's name, such as a court or park, never a street address, postcode, or exact location (ADR 0009). Nothing enforces this.
- Choice values follow the engine: `ScoringType` has `open_engine.ScoringType`'s values, `GameTarget` the points in `ALL_GAME_FORMATS`, and `MatchFormat` the two base `RatingFormat` values. `BestOf` is 1, 3, or 5 (decision F15). Import these and the limits (`MAX_GAMES`) from `apps.matches.models`; never redefine them. `Match.match_type` (`MatchType`, the engine's four values) is stored once. `record_match()` reads it from the Event under the share lock in `hold_event()` (`draft_match()` sets a provisional value for the model checks). An `edit_match()` correction copies the type of the match it corrects (it keeps that match's Event and Club), so a correction never changes a match's type. Nothing changes it afterward (ADR 0035, amending ADR 0024). An Event match gets its Event's kind at that moment, a match with a Club and no Event is `rec_verified` (none can be submitted since ADR 0021, so only one already in the Ledger or its correction), and a match with neither is `self_reported`. A check constraint ties it to the Event and Club links; nothing ties it to the Event's current kind, which may change. The adapter reads the stored value, never the Event.
- `Match.rating_format` is the match's engine rating format (`singles`, `doubles`, `mixed_doubles`, `doubles_men`, or `doubles_women`, ADR 0024). `record_match()`'s creation core (and so each `edit_match()` correction) sets it from the players' gender divisions at that moment, through `derive_rating_format()`, and nothing changes it afterward, so a later division removal never moves a past match. An `edit_match()` correction (every path, a player's included) with the same format and the same two teams, in either order, keeps the stored format of the match it corrects (`keep_rating_format()`, under the locks, read by id), so a correction after a player's Account deletion keeps its category (#318). One that changes a team, or moves a player to the other team, derives it again. A check constraint ties it to `format`. The adapter reads it, never the players' current divisions. The API does not return it, because a category value reveals all four players' divisions.
- The adapter sends `confirmed_by` as the players with a confirm decision, always. ADR 0024's every-participant rule for a self-reported match a moderator confirmed was removed along with moderator match review (ADR 0034, #273), so the adapter reads no Audit Event.
- `Match.submitted_by_user`, `submitted_by_application`, `event`, `club`, `corrects`, `submission_batch`, `MatchParticipant.player`, `MatchConfirmation.player`, every link on `MatchVouch` (`flag`, `match`, `account`, `application`), and every link on `SubmissionBatch` (`submitted_by_user`, `submitted_by_application`, `event`, `club`) use `PROTECT`. An Account that submitted a Match or a Submission Batch, an Account whose application submitted one, an Account or application that vouched for a Match, and a Player who played one cannot be hard-deleted, and neither can an Event or Club a batch names. Account deletion keeps such an Account as a cleared row (see Account deletion).
