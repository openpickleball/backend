## Email

ADR 0016 records the outbox decisions (the rules on queuing, sending, retries, and the sweep). The template rules come from issue #36, and ADR 0044 adds OPEN's branding and its one image, the logo (#306).

- Every email goes through `apps.emails.services.queue_email()`, never `EmailMessage.send()` or `send_mail()` in a request. It stores the rendered message as a `QueuedEmail` row and, after commit, queues `send_queued_email` with only the row's id. allauth's emails reach it through `AccountAdapter.send_mail`. A message must have one recipient and no cc, bcc, reply-to, extra headers, or attachments, and at most one text/html alternative.
- A `QueuedEmail` row holds the address and often a key. It is deleted once sent or finally failed, and the sweep (`sweep_queued_emails`, every 15 minutes) deletes any row older than three days and queues again rows with no attempt in the last hour. Before a retry, `last_attempt_at` is set so the lease ends exactly when the retry is due: the retry claims the row, and any other task for it (a sweep copy, a redelivered message) skips it during the wait, so a row has one retry chain. When the sweep queues a row, it sets `last_attempt_at` to one lease ago, so the queued task can claim it at once but later sweeps skip it for most of an hour. Never register an admin for it, and never log a row's address, subject, or body.
- `ANYMAIL_REQUESTS_TIMEOUT` (5 seconds to connect, 20 to answer) keeps a provider request well under `send_queued_email`'s 60-second soft time limit, so a slow provider is a retried timeout. Keep it so when changing either. It applies only to anymail's requests-based backends, Resend among them. The SES backend uses boto3 and ignores it: a slow SES request reaches the soft time limit, the row is kept, and the sweep retries it about an hour later. Optional tuning, not a switch step: `ANYMAIL["AMAZON_SES_CLIENT_PARAMS"]` with a botocore `Config(connect_timeout=5, read_timeout=20, retries={"max_attempts": 1})` gives SES timeouts backoff retries too.
- `send_queued_email` retries network errors, timeouts, 429, and 5xx (and SMTP and socket errors) up to five times, each wait at most 600 seconds, and treats every other provider error as final. It never logs a provider error's text, which can quote the address: retries and failures carry `EmailSendRetry` and `EmailSendFailed`, which hold only the id, template, error class, and status code. Keep any new log line to those values.
- Delivery is at least once: after a crash between the provider accepting a message and the row's delete, the sweep queues the row again about an hour later (it waits for an hour with no attempt, then for its next 15-minute run), and the message is sent twice.
- A `QueuedEmail` row has no link to the Account. Account deletion (`delete_account`) deletes the rows addressed to the Account's addresses, compared lowercased.
- Email templates live in the root `templates/` directory (`TEMPLATES` `DIRS`), which is searched before app directories, so `templates/account/email/` overrides allauth's own. Every email has `<prefix>_subject.txt`, `<prefix>_message.txt`, and `<prefix>_message.html`, and the message files build on the shared layout in `templates/emails/` (`base_message.txt` and `.html`), whose `reason` block says why the person received it. Text templates turn autoescape off themselves (the text base and every `_subject.txt` wrap in `{% autoescape off %}`), so a new text template extends the base or wraps itself; HTML keeps autoescape on. Templates never use `current_site`, `user_display`, or `{{ email }}`, so the request's host and the recipient's address stay out of the body. Subjects are the template's text alone (`ACCOUNT_EMAIL_SUBJECT_PREFIX` is empty). Render OPEN's own emails with `apps.emails.rendering.render_email()`, then queue them with `queue_email()`.
- Templates hold no promotional or marketing content, tracking pixels, scripts, external stylesheets or fonts (no `<link>`, `@import`, `url(`, or `@font-face`), and no link but action links built from `FRONTEND_URL`. The one image allowed is the OPEN logo (ADR 0044): one `<img>` in the shared HTML layout, whose `src` is the logo PNG's absolute URL (`BACKEND_URL` joined with `static()`), the same for every message and recipient, with no query string or fragment, with `alt="OPEN"`, explicit `width` and `height`, and `display: block; border: 0`. Never use SVG, a `data:` URI, a Content-ID attachment, or a background image. An `href` in a template is a single template variable. The hygiene checks in `apps/emails/tests/hygiene.py` check for these (a short word list and the usual image, script, and stylesheet markers, so they catch the common cases, not all) on every template file and on each rendered message a test passes them; run them on any new email. Until #306 lands, the checks still refuse every image.
- Emails follow the OPEN brand (ADR 0044, `openpickleball/brand-assets`). Colors come only from the ivory palette: background `#f7f3e8`, text `#17150f`, muted `#4d493f`, line `#d8d1bf`, faint `#6c6658`, surface `#fcfaf3`; the action button is ink with ivory text, and text and button colors meet WCAG AA contrast. The wordmark uses `'Krona One', Arial, Helvetica, sans-serif`, uppercase with `letter-spacing: 0.1em`, and text uses `'Instrument Sans', Arial, Helvetica, sans-serif`, as font stacks only, never loaded. Styles are inline (no `<style>` block) and live in the shared layout and partials in `templates/emails/`; other templates add no colors or fonts. The layout is a single-column `role="presentation"` table at most 600px wide, declares `color-scheme` and `supported-color-schemes` as `light`, and reads correctly with images blocked. The text version starts with "OPEN" and has no styling.
- The new sign-in email (`accounts/email/new_sign_in`, ADR 0047): `AccountAdapter.login`, which runs once every login stage passed, calls `apps.accounts.devices.note_sign_in`. When the Account's `last_login` was set before this login and the device marker (the `SIGN_IN_DEVICE_COOKIE_NAME` cookie for the browser client, the `X-Device-Token` header for the app client) lacks the Account's tag, it registers a `transaction.on_commit` callback that queues one email through `queue_email()`; an Account's first sign-in sends nothing. `DeviceMarkerMiddleware` writes the marker back with the tag first: an HttpOnly, SameSite Lax cookie (Secure and `__Host-` with DEBUG off), or the `X-Device-Token` response header. The marker is a signed list of at most `SIGN_IN_DEVICE_MAX_TAGS` keyed hashes of Account primary keys (`account_tag`), never an email address or a row id, refused after `SIGN_IN_DEVICE_COOKIE_DAYS`. Never detect a device from `UserSession` rows or a user agent. The email names the time (UTC, to the minute) and the client type and links to `{FRONTEND_URL}/account/sessions`; it holds no IP address, user agent, location, request host, or recipient address. allauth's own notifications stay off.
- OPEN has templates only for the allauth emails its settings can send: verification (`email_confirmation`, `email_confirmation_signup`), password reset (`password_reset_key`), and `account_already_exists`. Security notifications (`ACCOUNT_EMAIL_NOTIFICATIONS`), the unknown account email (`ACCOUNT_EMAIL_UNKNOWN_ACCOUNTS`), and the code flows stay off, and a test pins them. Turning one on needs OPEN's templates for the emails it sends first, or allauth's defaults go out. Security notifications include allauth's MFA notices (TOTP added or removed, recovery codes made).
- An email names no other player and quotes no text another person wrote. The match confirmation request lists each Match's OPEN Code, date, and scores from the recipient's side, with a link to `{FRONTEND_URL}/matches/{code}` (`match_url()`, a new web app route that #37 and the web app adopt). `render_confirmation_request()` refuses a Player whose Account is inactive, an empty list, a repeated Match, a Match the Player did not play in, a Match that is not pending, and a Match with no games. It reads the Match's status and the Account's `is_active` from the instances it is given, so a caller passes freshly fetched rows.
- Dispute and hold notices (#272): when `dispute_match` moves a Match into disputed, and when `insert_draft` (so `record_match` and `edit_match`) writes possible duplicate flags, it registers a `transaction.on_commit` callback (`apps.matches.notices.schedule_dispute_notices` and `schedule_hold_notices`) in the change's transaction, so a rolled-back change queues nothing. The callback reads the Match again and queues one email per Match per recipient through `render_dispute_notice()` or `render_hold_notice()` and `queue_email()`, until #37's digest. Recipients come from the rules that decide who may act, never a rule of their own: a dispute goes to the other team's active Accounts and, for an Event match, to the Event's Organizer members `settles_dispute` allows; a hold goes, for the new Match and each earlier Match its flags hold, to the active Accounts `vouch_level` allows (nobody for a club-only Match). A Match that is no longer disputed, voided, or no longer held by those flags gets nothing, and the skip for an earlier Match is per recipient: an earlier Match's recipient is not told again while their own side (the players of their team, or the Organizer) still has an older open hold on that Match to vouch on (older means a lower flag id than the new submission's flags; they were told when that hold began, and the vouch they owe covers the new flag too), while a side that has vouched on every older hold is told, so repeat near duplicates never mail every earlier Match again; the new Match is always notified (the maintainer's decision on #272). Each notice lists the OPEN Code, date, scores from the recipient's side (team A first for an Organizer member), the date the dispute or hold ends on its own (`MATCH_DISPUTE_EXPIRY_DAYS` from `dispute_started_at()`, `MATCH_DUPLICATE_HOLD_DAYS` from the latest of those flags), and `match_url()`; it never names the other Match of a flag. Both render functions refuse an inactive Account, a Match with no games, and a Match that is not disputed (dispute) or is voided (hold). A failure while building or queuing them is logged with the Match's row id and error class only and never fails the change.
- The data export email (`exports/email/data_export_ready`, ADR 0051): `build_data_export` queues one to the Account's `User.email` in the build's transaction, with the single-use link `{FRONTEND_URL}/account/export/{key}` and the expiry time in UTC, and no attachment. See Data export.
- Recorded match notices (#208, ADR 0041): a Match with an Event created confirmed (a trusted submitter's match, or the Organizer's correction), and a pending self-submission the Organizer's exact duplicate confirms (which the other team never confirmed), count without the players' confirmation, so each participant `participant_player` allows (an active Account) gets an email listing it, with the OPEN Code, date, scores from their side, and `match_url()` to dispute it. `insert_draft` registers the callback (`schedule_recorded_notice`) for such a Match with no Submission Batch. `record_match()`'s duplicate path registers it too when the Organizer's exact duplicate confirms a pending self-submission. A batch path never notifies per match: it calls `schedule_batch_notices(batch_id)` once the batch is done, which queues the `send_batch_notices` task (batch row id only) to send each player one email listing their confirmed or disputed Matches in the batch. For a CSV upload, `_finish` in `apps/matches/results_files.py` calls it when processing ends, except for a file a bulk void stopped (`voided`): `void_submission_batch` and `void_submitter_matches` call it for those batches after voiding, so the matches they left counting are announced. A bulk request path (#72) must call it once, the same way. A pending self-submission and a player's correction send none. There is no setting to turn these notices off: they are a security notice (ADR 0041). `render_recorded_notice()` refuses an inactive Account, an empty list, a repeated Match, a Match the Player did not play in, a Match that is neither confirmed nor disputed, and a Match with no games. Failures are logged with the Match's or batch's row id and the error class only, except the soft time limit, which stops the batch task.
- In tests, tasks run eagerly, but the test transaction never commits, so a queued email is not sent until on_commit callbacks run. The accounts tests run each test client request's callbacks when it returns (`run_on_commit_after_each_request` in `apps/accounts/tests/headless.py`); mark one `hold_on_commit` to keep them instead. Any other test that reads allauth's emails (through the `headless.py` helpers, say) uses the `commit_after_each_request` fixture from the root `conftest.py`. Elsewhere, use `django_capture_on_commit_callbacks(execute=True)`.
- The Organizer invite email (`clubs/email/organizer_invite`, ADR 0054): `apps.clubs.self_service.invite_member` queues one to the invited, normalized address in the invite's transaction, rendered by `render_organizer_invite()` (`apps/clubs/emails.py`), with the Organizer's OPEN Code, the role, the expiry in UTC, and the single-use link `{FRONTEND_URL}/organizer/invites/{key}` (`invite_url()`, a new web app route). It never names the inviter or the Organizer's name (ADR 0050). An address that is a member's login gets none. The Club invite email (`clubs/email/club_invite`, ADR 0055) is the same with the Club's OPEN Code, no role, and the link `{FRONTEND_URL}/clubs/invites/{key}`, queued by `apps.clubs.club_self_service.invite_admin`; it never names the inviter or the Club's name, and an address that is an admin's login gets none.
- Security notices (`clubs/email/security_notice`, #232, ADR 0057): `apps.clubs.notices` queues one email per other active admin of an Organizer (members with role admin) or Club (admin Club Roles), never to the acting Account, nor to the Account the change is about except on a removal, a role change away from admin, or an admin row moved to another Account, when that Account is told too while it is active and is not the actor, from a `transaction.on_commit` callback registered in the change's transaction, so a rolled-back change queues nothing. Events: Organizer Member added, removed, or given another role, Club admin added or removed, Club Organizer Grants and Organizer Application Grants made or removed (each row's `access_notice`, called by `apps.audit.access`, so the admin, self-service, and Account deletion send them; a hold-only change and `record_cascaded_removals` send none), verification granted or removed (`verify_organizer`, `unverify_organizer`, when the status changes), and a member losing its last two-factor method (`ManageTOTPView.delete`, `ManageWebAuthnView.delete`, or a password reset that wipes its last passkeys, `remove_passkeys_after_reset`, which is never refused; for each Organizer it is a member of and each Club it is an admin of). The text is fixed sentences in `apps/clubs/notices.py` with only OPEN Codes, a role, and a New Member Hold's end in UTC, rendered by `render_security_notice()`; never an address, a person's name, an Organizer's or Club's name, or a client id, and no link. A failure is logged with row ids and the error class only and never fails the change.
