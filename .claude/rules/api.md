## API

- There is one `NinjaAPI`, `api` in `config/api.py`, mounted at `/api/v1/`. Each app adds its operations to a `Router` in `apps/<app>/api.py`, and `config/api.py` mounts that router. The `config/api.py` docstring shows how. The health checks are the exception: their router is in `config/health.py`. `apps/clubs/api.py`'s router is mounted at `/api/v1/organizers/` (a player's report of an Organizer), apart from `/api/v1/organizer/`, which holds an Organizer member's own operations. `apps/matches/api.py` also has `me_router`, mounted at `/api/v1/me/`, for lists of the signed-in Account's own matches, and `apps/players/api.py` has another `me_router`, mounted at the same prefix, for the Account's own Player (`/api/v1/me/player`), and so does `apps/exports/api.py`, for the data export (`/api/v1/me/export`, ADR 0051). `apps/ratings/api.py`'s router shares the `/api/v1/players/` prefix with the players router. `apps/events/api.py`'s router, `apps/matches/api.py`'s `organizer_router` (CSV results files), and `apps/clubs/api.py`'s `organizer_router` (`list_my_organizers`, the Account's own memberships, ADR 0050, and the Organizer self-service operations, ADR 0054) are mounted at `/api/v1/organizer/`. `apps/clubs/club_api.py`'s `club_router` (Club self-service, ADR 0055) is mounted at `clubs`, with no trailing slash, so the create is `POST /api/v1/clubs`. The OAuth endpoints under `/oauth/` are not part of this API (see Partner applications), and neither are allauth's endpoints under `/_allauth/`, which use allauth's own response and error format, not `ErrorResponse` (see Authentication). The one exception on both is the body limit's 413, an `ErrorResponse` on every path (ADR 0040).
- Every operation passes an explicit `operation_id`. It names the method in the generated client, so never change one for a rename. Building the OpenAPI document raises an error for an operation in the document that has none, and a test checks every operation.
- Validation errors, an unparsable body, `Http404`, `HttpError`, a failed `auth` check, `DuplicateMatchError`, `MatchPermissionDenied`, `MatchValidationError`, `MatchActionDenied`, and `MatchStateError` come back as `ErrorResponse` (`config/api_errors.py`). Validation errors return 422, a failed `auth` check returns 401 with code `unauthorized` and empty `errors` (documented on every operation with `auth`), an Account `mfa_required` holds that has no method, and an Account with MFA whose session has not passed it, gets 403 with code `mfa_required` and empty `errors` on every signed-in operation (`config.auth.MFARequired`, raised by both auth classes after authentication and after the browser client's CSRF check, documented on every operation with `auth`, keeping an operation's own 403 description with the case added; ADR 0043), a `DuplicateMatchError` returns 409 with one `errors` item, which carries `existing_code` only when the error has one (ADR 0011), a `MatchPermissionDenied` returns 403 with code `forbidden` and empty `errors` (ADR 0012), as does a `MatchActionDenied` where an operation does not turn it into a 404 (ADR 0015), a `MatchValidationError` returns 422 with one `errors` item per issue, a `MatchStateError` returns 409 with code `conflict` (ADR 0015), and a throttled request returns 429 with code `throttled` and empty `errors`, with a `Retry-After` header when the throttle gives a wait. A CSV results upload whose file is over the size limit returns 413 with code `too_large`. An operation that needs a recent reauthentication (Account deletion, a data export request) returns 403 with code `reauthentication_required` (`config.auth.ReauthenticationRequired`). A request that declares a body over the file limit plus a 64 KiB allowance gets that 413 before Django reads the body, signed in or not (`apps/matches/upload_limits.py`). Any other request that declares a body over `DATA_UPLOAD_MAX_MEMORY_SIZE` (2.5 MiB) gets a 413 `ErrorResponse` with code `too_large` before Django reads it, on every path and method, signed in or not, `/_allauth/`, `/oauth/`, and the admin included (`config/body_limits.py`, ADR 0040); a POST to the CSV upload keeps its own limit. The limit holds only under WSGI: production serves `config.wsgi` with gunicorn, and Django's ASGI handler reads the whole body before any middleware, so serving over ASGI needs a server-side body limit first. With DEBUG off, any other exception goes to Django, which returns its own HTML error page (a 500, or another status for exceptions Django maps, such as 403 for `PermissionDenied`). Raise `HttpError` or `Http404` instead of returning an error body by hand (the readiness check's 503 is not an error: it is a status report with its own documented schema), and use `HttpError(403, ...)` (or let `record_match()`'s `MatchPermissionDenied` propagate), never Django's `PermissionDenied`. Never declare a different 422 schema on an operation that takes input: building the document raises an error if you do. ADR 0005 records the versioning and error format, ADR 0011 adds the 409 for a duplicate match, ADR 0012 adds the 403 for a refused submitter, and ADR 0015 adds the match workflow errors.
- API throttles (ADR 0030) are fixed-window counters built on `FixedWindowThrottle` (`config/throttling.py`): counted in the default cache with `cache.add` then `cache.incr`, a minute and a day window, a later window counted only when the earlier ones allow the request, and no request state kept on the shared throttle (what `wait()` needs is in a `threading.local`). Never use ninja's built-in throttles: `AuthRateThrottle` keys on a hash of `str(request.auth)`, the Account's email, their read and write of the count is not atomic, and ninja asks every throttle on an operation, so a request one refuses still counts against the others. Give an operation exactly one throttle.
- Every router whose operations need sign-in passes `throttle=account_throttle` next to `auth=account_auth`, so they share one per-Account budget keyed by the Account's id. An operation's own `throttle=` replaces its router's. Player search keeps only `SearchThrottle` (`apps/players/api.py`, ADR 0018), with its fixed limits, `report_organizer` keeps only `OrganizerReportThrottle` (`apps/clubs/api.py`, ADR 0037), `request_data_export` keeps only `DataExportThrottle` (`apps/exports/api.py`, ADR 0051, which counts a request without a recent reauthentication against the Account throttle's windows), `invite_organizer_member` keeps only `OrganizerInviteThrottle` (`apps/clubs/api.py`, ADR 0054), and `invite_club_admin` keeps only `ClubInviteThrottle` (`apps/clubs/club_api.py`, ADR 0055), the last four each a day window from settings; never add a second throttle to any of them. Health checks are never throttled. A test walks every operation to pin this, so a new operation needs sign-in and the Account throttle, or a deliberate entry there.
- A public operation (no sign-in) uses `ClientIPThrottle`. It reads the client IP only from the header named by `CLIENT_IP_HEADER`, never `X-Forwarded-For`, `Forwarded`, or `REMOTE_ADDR`. A missing or invalid value shares one fallback bucket, and IPv6 counts by its /64. Whether App Platform strips a client-sent `do-connecting-ip` is unverified until the deploy check on #61 passes; no public operation goes live before then. No public operation is mounted yet.
- A throttle's refusal is a 429 `ErrorResponse` (see above) with a `Retry-After` header in whole seconds. Every throttled operation documents that 429 in the OpenAPI document, and may not declare a different 429 schema. ninja checks throttles after auth and before it parses input, so a 422 counts and a 401 or a 403 `mfa_required` does not. Tests that depend on a throttle's count clear the cache and pin the throttle's `timer`, so a window edge cannot reset a count mid-test.
- The rating lookup (`get_player_ratings`, ADR 0031) needs sign-in and follows `rating_visibility` (`PlayerPrivacy.visible_to`): a viewer it hides the player from gets the same 404 as an unknown code. It reads no age, so no answer changes when a player turns 18: keep it so, or the lookup reveals a birthday. Rating history (`list_player_rating_history`) needs sign-in and follows `rating_history_visibility` as match history follows its setting. Never return a rating without its reliability, and keep `demonstration: true` on every rating. The OpenAPI document says that the OPEN standard requires any app that shows an OPEN rating to show its reliability next to it.
- Never put the submitted value in a validation message. The 422 response returns the message to the client. To turn a model `ValidationError` into the 422, use `config.api_errors.model_validation_error()`, which copies the model's messages as they are, so the model must first override any message that repeats a submitted value.
- `openapi/openapi.json` is the API's OpenAPI document, generated by `manage.py export_openapi_schema` (`apps/openapi`) and committed so API changes show in review. Regenerate it in the same change as anything that changes the document, and never edit it by hand. CI (`export_openapi_schema --check`) and a test fail when it differs from the API, byte for byte. OPEN's command replaces django-ninja's command of the same name because `apps.openapi` comes before `ninja` in `INSTALLED_APPS`; keep that order (a test pins it). When a maintainer publishes a GitHub release, `.github/workflows/release.yml` runs `--check` on its tag and then attaches the file to the release. The committed document is generated with `.env.example`'s DEBUG on, so its `SessionAuth` names the DEBUG-on cookie, `sessionid`; a deployment with DEBUG off serves a document that names `__Host-sessionid` (django-ninja reads `SESSION_COOKIE_NAME`, ADR 0040). Run the export and `--check` with DEBUG on, or they report a difference. A root `.gitattributes` keeps the file's line endings LF, since the check compares bytes.
- A code path parameter (`PublicCodePath`) that fails returns 404, not 422, which narrows the 422 rule for that parameter (ADR 0008). With the other inputs valid, a malformed code and an unknown one get the same 404. With another input invalid, a well-formed code gets that input's 422 whether or not a record has it, so no response reveals that a record exists. Keep it so for an actor who is refused: an operation with a code in its path answers a refused actor with the same 404 as an unknown code, never a 403 (ADR 0015). The auth-level 403s (CSRF and `mfa_required`) are the exception: they come before any lookup and are the same for every code.
- The Organizer's dispute operations (`resolve_match_dispute`, `correct_disputed_match`, ADR 0034) answer anyone `settles_dispute` refuses with the unknown-code 404 before reading any team code, and a Match that is not disputed with 409. Their `reason` is required, at most 1000 characters, with no control character but a line break or tab, and a blank, long, or refused one gets a 422 with fixed text. `list_organizer_disputes` lists the disputed Matches of verified Organizers the Account is a member of while it has MFA, except those `settles_dispute` refuses it because its Player plays in a Match of the correction chain (`workflow.organizer_disputes`, one recursive query, no check per row; the maintainer's decision on #272), and is empty for anyone else.
- `MatchOut`, the match in every first-party match response, shows the match's Event (`event`: its OPEN Code, name, and Organizer's OPEN Code) and its own Club (`club`: `Match.club`'s OPEN Code and name), each null when the match has none, to whoever the response already shows the match to (ADR 0053, #302). It never shows the Organizer's name (an identifying field, which goes only to that Organizer's members, ADR 0050), `rating_format`, or a row id. `with_match_details()` loads the Event, Organizer, and Club with the match, so load every `MatchOut` through it and keep `match_out()` free of queries.
- `vouch_for_match` (`POST /api/v1/matches/{code}/vouch`, #270) answers anyone `vouch_level` refuses with the unknown-code 404 before reading the Match's status or flags, and a voided or unheld Match with 409. `list_my_holds` (`GET /api/v1/me/matches/holds`) lists the held Matches the Account may vouch for (`vouchable_holds`) as `HoldOut` (the Match and whether the Account's own level has vouched, `vouched_at_own_level`), paged by `HoldPagination`. Neither response names the other Match of a flag. `list_my_disputes` (`GET /api/v1/me/matches/disputes`, #272) lists the disputed Matches the Account's Player played in, paged by `MatchHistoryPagination`, and an empty page for an Account with no Player.
- Organizer self-service (ADR 0054): every operation with an Organizer code in its path calls `_mfa_admin` first, so an Account without MFA gets 403 `mfa_required` before any database lookup, the same for every well-formed code (a malformed code is already a 404 when `PublicCodePath` reads the path); then a non-member, a match manager, and an unknown or malformed Organizer or member Player code all get the same 404 (`Http404`). An operation that changes who may act (invites, a member's role and removal, the verification request, and the Club admin and grant changes, #232, ADR 0057) calls `require_step_up` right after `_mfa_admin`, so an old two-factor step gets 403 `reauthentication_required` before the lookup, between the MFA 403 and the 404. Keep that order (MFA, then step-up where it applies, then the lookup) in a new admin operation. `invite_organizer_member` answers one fixed 202 body whether or not the address has an Account, is a member, or was invited, and neither it nor any other response names an address. `accept_organizer_invite` answers every refusal with one 404. The member list shows each member by Player OPEN Code and display name, never an email or a row id. Name and statement inputs are checked in `apps/clubs/schemas.py` with fixed 422 texts. Club self-service (ADR 0055) follows the same order: every Club operation with a Club code in its path except `get_club` calls `_mfa_admin` first, then a non-admin and an unknown or malformed Club, admin Player, or granted Organizer code all get the same 404; `invite_club_admin` answers one fixed 202 body, and `accept_club_invite` one 404 for every refusal. `list_organizer_club_grants` follows the Organizer rule.
