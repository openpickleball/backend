## Partner applications

- `PartnerApplication` (`apps/partners`) is the OAuth client a Partner uses. Approval is security-sensitive (hard rule 8): only #29's approval service (and, in tests, the `approve()` helper) writes `approved_at` and `approved_by`, through `update_fields`. A new application starts unapproved: `save()` refuses a new one that is already approved. `is_sandbox` defaults to true, but staff can change it; #29 and #74 decide how it is enforced. A full `save()` of an existing application never writes the approval fields. An Organizer with an application cannot be deleted (`organizer` uses `PROTECT`). The `save()` docstring lists the writes that skip these rules. An application that submitted a Match or a Submission Batch, or vouched for a Match (`MatchVouch.application`), cannot be deleted (`Match.submitted_by_application`, `SubmissionBatch.submitted_by_application`, and `MatchVouch.application` use `PROTECT`). An application submits or changes a Match only while approved (`apps.matches.permissions`).
- A new application is always inserted: `save()` refuses `force_update` or `update_fields` on it, so a hand-built instance with another row's pk cannot overwrite that row.
- The client secret is stored hashed: check constraints refuse `hash_client_secret=False` and a blank secret. Any write of `client_secret` must be a raw secret: not blank, and not anything `identify_hasher` recognizes, because django-oauth-toolkit stores such a value as is, and when its hash check fails on it, compares it as plain text. A new raw secret is hashed and replaces the stored one, but a hash-shaped or deferred value is never written back: a full save, or `update_fields` naming `client_secret` (as `update_or_create` always does), leaves it out. The admin shows the generated secret only on the add form. Raw writes (`QuerySet.update`, `bulk_create`, `loaddata`, raw SQL) skip the model's checks; the check constraints still apply.
- Only `/oauth/token/` and `/oauth/revoke_token/` are mounted (`apps/partners/urls.py`). They are plain Django views outside the ninja API: errors use OAuth's JSON format, not `ErrorResponse` (except the body limit's 413, an `ErrorResponse` on every path, ADR 0040), and CORS does not cover them. Until #27, #28, and #29 land, the token endpoint does not check approval, sandbox status, or which scopes each application may have, and no API operation accepts an OAuth token.
- `apps.partners.tasks.clear_expired_tokens` (daily beat entry `clear-expired-tokens`, 04:20 UTC, `default` queue) runs django-oauth-toolkit's `clear_expired()`. It keeps revoked refresh tokens (reuse detection), expired access tokens that have a refresh token, and device grants. It returns nothing and raises a fixed-text `ClearTokensFailed`.
- `OAUTH2_PROVIDER` in settings turns on every RFC 9700 behavior django-oauth-toolkit offers (tokens hashed at rest, https redirect URIs only). Turning one off makes `check --deploy` report a warning or an error, and `config/tests/test_settings.py` fails on either. Scopes, token lifetimes, and grant types are #28.
- `PartnerApplication.__str__` returns its `client_id`, `OrganizerApplicationGrant.__str__` returns the Organizer's OPEN Code and the `client_id`, and `ClubOrganizerGrant.__str__` returns the Club's and the Organizer's OPEN Codes. The application's `name` is shown only in the admin.
- An approved application acts for an Organizer that owns it (`organizer`) or granted it an `OrganizerApplicationGrant` (ADR 0021), which replaced the Club Application Grant; a platform that serves many Organizers holds one grant from each. Each grant add, change, and removal through the admin, a cascade from an application deleted there included, records an Audit Event (see Audit log).
- In tests, build them with `PartnerApplicationFactory` and `OrganizerApplicationGrantFactory` (`apps/partners/tests/factories.py`). `approve()` and `approved_application()` there write the approval fields through `update_fields`, with no Audit Event, a test-only stand-in until #29's approval service lands.
