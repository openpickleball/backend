## Authentication

ADR 0014 records these decisions. Login and the lookups behind it are the base for identity linking, a security-sensitive area (hard rule 8).

- django-allauth runs headless only (`HEADLESS_ONLY`), at `/_allauth/browser/v1/` (session cookie and CSRF) and `/_allauth/app/v1/` (`X-Session-Token`). Its OpenAPI document is at `/_allauth/openapi.json`, `.yaml`, and `.html`, with OPEN's age check (ADR 0020) and password check (ADR 0039) added. No social login is installed (#176). allauth's user sessions app is installed for the session list only (#100, ADR 0047).
- MFA (ADR 0043, ADR 0056): `allauth.mfa` with TOTP, recovery codes, and passkeys (WebAuthn, #117), with passkey login on; passkey signup and "trust this browser" stay off. Codes are shown once, and adding or removing TOTP or a passkey, renaming a passkey, viewing the codes, or making new ones needs a recent reauthentication. An Account has MFA when it has a TOTP authenticator or a passkey; recovery codes alone never count. Ask only through `apps.accounts.mfa`: `has_mfa`, `has_totp` (the admin's rule), `accounts_with_mfa` (a subquery for filters), `mfa_required` (staff, superusers, moderators, owners of a non-sandbox Partner Application), `lacks_required_mfa` and `mfa_status` (both in one query), each read from the database by id, `session_passed_mfa` (whether this session passed MFA, read from the session), and `last_mfa_at` (the time of the session's latest MFA step, for the admin's time limits). An Account with MFA counts only in a session that passed MFA: a session that signed in with the password alone (for example a session from before the Account enrolled) gets 403 `mfa_required` on the API until it reauthenticates with a code, and OPEN's MFA management views (adding and removing TOTP, viewing and making recovery codes, every passkey change and the passkey creation options) refuse it with allauth's 401 offering only `mfa_reauthenticate`. Enrolling (TOTP or a passkey) records an MFA step for the enrolling session, and so does a passkey login. Reauthentication is by password or MFA only (`ACCOUNT_REAUTHENTICATION_METHODS`), never by an emailed code, and OPEN's TOTP, recovery codes, and passkey views ask for it before they read the input. MFA sends no email (security notifications stay off). An Account with MFA cannot add an email address (allauth's `add_email_blocked`).
- MFA changes are audited in the change's own transaction: OPEN serves subclasses of allauth's MFA authenticate, reauthenticate, TOTP, recovery codes, authenticator list, passkey (WebAuthn), passkey authenticate, passkey reauthenticate, and passkey login views at allauth's paths, for both clients (`apps/accounts/mfa_views.py`, mounted by `headless_urlpatterns()`), each `dispatch` in `transaction.atomic()`, recording one `mfa.change` event per change through `record_mfa_change` (`after` is `change` and `type` only, never a secret or code). Each view locks the Account row `FOR UPDATE` first, before any authenticator row (the order allauth's recovery code regeneration uses), so keep that order in any new MFA path. A removal records first, inside a savepoint, so allauth's reauthentication refusal rolls it back. The views strip the Authenticator row id from allauth's `mfa` authentication records, so allauth's `methods` payload carries no row id. Keep allauth's responses otherwise unchanged, apart from the session rule's 401 and the reauthentication-first order above. allauth's Authenticator admin is unregistered (it shows secrets). TOTP secrets and recovery code seeds are stored encrypted through OPEN's MFA adapter (ADR 0046).
- Passkeys (ADR 0056): the relying party is `WEBAUTHN_RP_ID` named `OPEN` (OPEN's MFA adapter), never the request's host. Every input that carries a WebAuthn credential (add, `auth/webauthn/authenticate`, `auth/webauthn/reauthenticate`, `auth/webauthn/login`) refuses one whose client data origin is not exactly in `WEBAUTHN_ALLOWED_ORIGINS` with allauth's `incorrect_code`, before allauth verifies it (`apps.accounts.passkeys.check_origin`); `MFA_WEBAUTHN_ALLOW_INSECURE_ORIGIN` stays off. The WebAuthn user handle is a keyed hash of the Account id (`user_handle`), never allauth's row id. Passkey login finds the one passkey with the assertion's credential id and refuses a user handle that is not its Account's (made with `SECRET_KEY` or a fallback key), then allauth verifies the assertion and requires user verification; it keeps allauth's per-IP `webauthn_login` limit, then locks the Account row before it writes anything and reads the passkey and its Account again under the lock, refusing a passkey removed meanwhile with `incorrect_code`. Adding a passkey refuses a credential id any Account holds. The API names a passkey only by `public_passkey_id`, and rename and remove accept only those ids, refusing any other with one fixed message. Adding records `mfa.change` `added webauthn` (and `added recovery_codes` when codes were made); removing records `removed webauthn` per passkey (and `removed recovery_codes` when no method is left) and ends the Account's other sessions; a rename, a passkey login, and a passkey reauthentication record nothing. Passkey signup is not served: allauth needs email verification by code for it, which stays off. The app client serves the views, but native app origins are not allowed until #185. In tests, `SoftwarePasskey` (`apps/accounts/tests/webauthn.py`) makes and signs made-up credentials.
- The admin (ADR 0043, ADR 0045): `config.apps.OpenAdminConfig` replaces `django.contrib.admin` in `INSTALLED_APPS` and makes `config.admin.OpenAdminSite` the `admin.site`, served at `settings.ADMIN_URL`. Its `has_permission` needs an active staff Account with `has_totp` (a TOTP authenticator: a passkey alone does not count in the admin, whose login script takes only codes, ADR 0056) whose session's latest MFA step (`apps.accounts.mfa.last_mfa_at`) is within `ADMIN_SESSION_SECONDS`, and every unsafe request but logout needs one within `ADMIN_REAUTHENTICATION_SECONDS` (otherwise it is redirected to the login page, which asks for a code, and nothing runs). A signed-in Account that is not active staff gets 404 on every admin URL, the login page included; an active staff Account without TOTP gets a page telling it to set one up. Django's admin login form is gone: OPEN's login page takes no password and answers a POST with 405. Its script (`apps/accounts/static/accounts/admin_login.js`) signs in through allauth's browser client (`auth/login`, then `auth/2fa/authenticate`) or confirms a code (`auth/2fa/reauthenticate`), so allauth's login rules, email verification, and rate limits and OPEN's MFA views apply. Logout works for any signed-in active staff Account, whatever the time limits. Only a superuser grants or removes `is_staff`, `is_superuser`, groups, or user permissions (read-only for anyone else in the Account admin), changes or deletes an Account that holds any of them (no staff or superuser Account is deleted in the admin at all, see Account deletion), edits Groups, or adds, changes, deletes, or runs an action on django_celery_beat's periodic tasks and schedules (OPEN's admins for these replace the packages' own in `apps/accounts/admin.py`). The Account admin refuses to grant `is_staff` or `is_superuser` to an Account without TOTP. The admin's own password change records `password.change`. `OpenAdminSite.register` also adds `SafeAutocompleteAdminMixin` (`config/admin_autocomplete.py`, #161) after `AdminAuditMixin`, and the mixin wraps every inline the admin shows, so a tampered autocomplete id gets the form's error instead of a 500. The fix covers integer keys only. An admin that gives an autocomplete field its own widget uses the safe widgets there. The mixin also gives every choice and many-to-many form field the admin builds from a model field fixed error text (#162), since Django's form messages repeat the submitted value; a caller's own `error_messages` win. A field a form declares itself skips the mixin, so the form that declares it sets `CHOICE_ERRORS` itself, and a test walks every registered admin's forms for a message that names the value. In tests, `UserFactory` enrolls staff and superusers in TOTP unless `mfa=False` (`mfa=True` enrolls anyone), and `enroll_totp`, `totp_code`, and `totp_secret` in `apps/accounts/tests/factories.py` build and use a method. `HeadlessSession.mfa_login` passes the MFA stage. The root `conftest.py` makes `Client.force_login` record the MFA step for an Account with MFA, as a real MFA login does; tests of the MFA rules use real logins.
- Login is by email only, and email verification is mandatory: no login before the address is verified. Verification and password reset use emailed links to `FRONTEND_URL` pages, not codes. Sign-up and password reset answer the same way whether or not an Account has the address, and neither mails an address that has no Account.
- An address allauth stores (sign-up, change of address) goes through `AccountAdapter.clean_email` (`apps/accounts/adapter.py`), which normalizes it and applies the Account email rules. An address used to find an Account (login, password reset) must be canonical (`is_canonical_email`): stripping and lowercasing it gives its normalized form, and it is ASCII. A variant that NFKC folds onto an Account's address never logs in and gets no reset mail. The one exception is the Kelvin sign (U+212A), which allauth's email field lowercases to ASCII `k` before OPEN's check, so it reaches the same Account (accepted, ADR 0014). A reset key is mailed only to the Account's own `User.email`.
- allauth's own lookups match any `EmailAddress` row, including another Account's pending change of address. So OPEN overrides allauth's sign-up, password reset request, and email verification views (`apps/accounts/headless_views.py`, served ahead of `allauth.headless.urls` for both clients). Sign-up counts an address as taken only when it is some Account's login, reset finds an active Account only through `get_by_natural_key`, and verify refuses (`email_taken`) an address that is another Account's login. When allauth adds a view that looks up an Account by email, override it the same way, for both clients, with a test on each.
- A save that changes `User.email` (staff in the admin, or any code) deletes the Account's other `EmailAddress` rows in the same transaction (`User.save()`), so an old address never stays tied to the Account. Raw writes (`QuerySet.update`, `bulk_update`, raw SQL, `loaddata`) skip this, so change an Account's email only through a save. When the Account has no row for the new address, its next headless login adds one, unverified.
- Code-based flows stay off (`ACCOUNT_LOGIN_BY_CODE_ENABLED`, `ACCOUNT_EMAIL_VERIFICATION_BY_CODE_ENABLED`, `ACCOUNT_PASSWORD_RESET_BY_CODE_ENABLED`, `ACCOUNT_EMAIL_VERIFICATION_SUPPORTS_CHANGE`), and so does reauthentication by code (`ACCOUNT_REAUTHENTICATION_METHODS` is password and MFA only, ADR 0043). Login by code opens allauth's login code request, which finds an Account with allauth's own lookup. Verification by code together with `ACCOUNT_EMAIL_VERIFICATION_SUPPORTS_CHANGE` opens allauth's change-email input, which skips `clean_email` and the sign-up rule. An issue that turns these on must first override those views like the sign-up, reset, and verify views. It must also add OPEN templates for the emails they send (see Email). Verification by code also lifts allauth's `add_email_blocked` for an Account with MFA.
- `AUTHENTICATION_BACKENDS` lists `ModelBackend` first (every successful headless login, the admin's included) and OPEN's allauth backend second. Both find the Account through the manager. The admin signs in through allauth's headless login, so a staff Account needs a verified login address like any other.
- allauth's user payload carries no row id (`HeadlessAdapter`), and OPEN's session list names each session by a keyed hash of its key (`public_session_id`), never the `UserSession` row id. allauth's verification and reset keys do encode a row id (a signed `EmailAddress` id, and the Account id in base36). They are opaque, and only the mailbox owner sees them: the one exception to the row-id rule (see Public identifiers).
- Sign-up requires `accepted_terms` and `accepted_privacy` on both clients, each JSON `true` (`SignupAgeForm`, ADR 0026), checked with the age. A new Account gets one `AgreementAcceptance` row per agreement, with the version in settings (`TERMS_OF_SERVICE_VERSION`, `PRIVACY_POLICY_VERSION`) and the time, in the transaction that creates it (`SignupInput.try_save`, `apps/accounts/agreements.py`). A taken address records nothing. The accepted versions are held in the session with the other signup details. Asking again after a version change is #237.
- Sign-up takes `birth_year`, `birth_month`, `gender_division` (`mens` or `womens`), `first_name`, and `last_name`, and optionally `city` and `region`, on both clients (`SignupAgeForm`, ADR 0017, ADR 0019, ADR 0022). OPEN's `SignupView` checks allauth's rate limit, then allauth's 409 and 403, then these details, then allauth's input, so a refused age never reaches the email lookup or sends mail. Under 13 gets one fixed `signup_refused` answer and flags the session (`open_signup_refused`), and every later sign-up in that session gets the same answer; `AccountAdapter.logout` keeps the flag. The Player create endpoint sets and honors the same flag: an under-13 or future age there gets one fixed 422 on `body.birth_month`, and so does every later create in that session. Two concurrent requests in one session can lose the flag; ADR 0017 accepts this. The age check (`POST /_allauth/{client}/v1/auth/signup/age-check`, `SignupAgeCheckView`, ADR 0020) runs the same screen on `birth_year` and `birth_month` alone (`SignupBirthForm`, which `SignupAgeForm` extends), in sign-up's order and on sign-up's rate limit counter: a pass writes nothing to the session, and under 13 gets `signup_refused` and flags it. It reads no email address. Sign-up and the check share `_screen_birth()`, so change the screen there. allauth's OpenAPI document lists the check because OPEN serves `/_allauth/openapi.json` and `.yaml` itself (`apps/accounts/openapi.py`, built on allauth's internal `get_schema()`). Read and set the flag only through `apps.players.signup.is_signup_refused()` and `refuse_signup()`. A passing sign-up holds the age, gender division, legal name ("First Last"), first name, and city and region in the session bound to the new Account (`open_signup_details`); read them only through `apps.players.signup.peek_signup_details()` and take them only through `take_signup_details()`. The Player create endpoint takes them once the Player exists, or when the Account already has one (409). Keep the session changing the same way for a new and a taken address, or the app client's session token reveals which it was. In tests, the headless `signup()` helper sends an adult age, a gender division, a made-up name, and a place (`SIGNUP_DETAILS`).
- The password check (`POST /_allauth/{client}/v1/auth/signup/password-check`, `SignupPasswordCheckView`, ADR 0039) takes `password` and an optional `email` and runs signup's password rules, in the age check's order and on signup's rate limit counter: allauth's 409 and 403, then the refusal flag (`signup_refused`), then the input. A pass is `{"status": 200}`; a fail is allauth's 400 with one `password` error per failed validator, with Django's message and code. The rules run through `clean_signup_password()` (allauth's `clean_password()` with an unsaved Account holding only the address, so `UserAttributeSimilarityValidator` runs, which allauth's headless signup skips), and OPEN's `SignupInput.clean()` calls it too, so the check and signup give the same errors: change the rules there. The address is only compared, never validated or looked up, and the check writes nothing to the session and sends no mail.
- Protect a first-party API operation with `auth=account_auth` (`config/auth.py`), which accepts either client. `request.auth` is the Account itself on both, so pass it straight to a service. To read or change a session value (the signup details), use `auth_session(request)`: the session the `X-Session-Token` names for the app client, `request.session` for the browser client. Django's middleware saves only `request.session`, so a view that changes the token session calls its `save()`, which keeps the key. A request with no signed-in user gets 401 before any CSRF check; a signed-in session's unsafe request still needs its CSRF token (ADR 0015). Operations for partners will use OAuth tokens instead (#27).
- Rate limits (ADR 0047): `ACCOUNT_RATE_LIMITS` in settings sets every account action, in the shared cache. allauth's per-IP key and the user session rows' IP come from `AccountAdapter.get_client_ip`, which reads only `CLIENT_IP_HEADER` through `config.throttling.client_ip` (the API throttles' parsing, one function; never copy it): an IPv6 address is its /64 network address, an IPv4-mapped one its IPv4 address, and a missing or invalid value is `0.0.0.0`, shared. Never read `X-Forwarded-For`, `Forwarded`, or `REMOTE_ADDR`. So allauth's per-IP limits and the session list's IPs trust `CLIENT_IP_HEADER`, which stays unverified until the deploy check in the API section: a client-sent value that the proxy does not strip voids the per-IP limits (the per-address limits still hold), and every request without a valid header shares the `0.0.0.0` bucket, so once its per-IP limits fill (failed logins, logins, signups, resets) every headerless request is refused. The failed login counter is keyed on the lowercased address alone (`_get_login_attempts_cache_key`), never the Host header. OPEN's login, MFA login stage, password reauthentication, and MFA reauthentication views answer allauth's `too_many_login_attempts` with allauth's 429 (`LockoutAnswers429`, `apps/accounts/lockout.py`): give it to any new view that can raise that lockout.
- Password text (ADR 0047): `apps.accounts.validators.EncodablePasswordValidator` runs first in `AUTH_PASSWORD_VALIDATORS` and refuses a password that is not UTF-8 text (a lone surrogate from JSON) with `password_invalid_characters`, so none reaches the hasher; `AccountAdapter.authenticate` and `User.check_password` treat one as a wrong password. Keep both when touching password paths.
- Breached passwords (ADR 0047): `apps.accounts.breached.BreachedPasswordValidator` runs last in `AUTH_PASSWORD_VALIDATORS`, after Django's four rules (`MinimumLengthValidator` takes `PASSWORD_MIN_LENGTH`), so every path that sets a password refuses a listed one with `password_breached`. Only the first 5 hex characters of the uppercase SHA-1 leave OPEN, with `Add-Padding: true`, a generic User-Agent, `PASSWORD_BREACH_TIMEOUT_SECONDS` on each socket wait and on the body read as a whole (not on name resolution, so not a hard bound on the request), no redirect followed, and at most `MAX_BODY_BYTES` (1 MiB) read; a count of 0 never refuses, and a repeated suffix takes its highest count. It fails open: any outage, protocol error, redirect, oversized, empty, or malformed answer accepts the password and logs one warning with the error class only, never the password, hash, prefix, suffix, URL, or address. Tests never reach the service: the root `conftest.py`'s autouse `breach_service` fixture replaces `breached.fetch_range` (`FakeBreachService` in `apps/accounts/tests/breach.py`, which knows no breached password unless a test adds one), and the test settings point the URL at a local port nothing listens on.
- Session lifetimes (ADR 0047): a signed-in session, browser cookie or app token alike, ends `SESSION_MAX_AGE_DAYS` after login or `SESSION_IDLE_DAYS` after it was last seen. The times live in the session (`open_session_started`, `open_session_seen`); `AccountAdapter.login` starts them, and `apps.accounts.sessions.check_lifetime` checks them on every path: `SessionLifetimeMiddleware` (after `AuthenticationMiddleware`) for the browser, and OPEN's `HEADLESS_TOKEN_STRATEGY` (`apps/accounts/token_strategy.py`) for app tokens, which allauth's endpoints and `config/auth.py` both look up through. Keep both paths when changing either. Last seen is written at most once per `SESSION_SEEN_REFRESH_SECONDS`, and each write sets the session's expiry to the earlier end, so in real time the store refuses an ended session first (it loads empty: 401 on every path). The token strategy then deletes the token's `UserSession` row; a browser session's row goes with the next sweep. When the store still holds a signed-in session past its times, `end_session` deletes it with its row (an app token then gets allauth's 410). For an app token, a save error from a session deleted meanwhile (`UpdateError`) reads as no session. In tests, `Client.force_login` starts the clocks too (root `conftest.py`).
- Ending sessions (ADR 0047): OPEN's `ChangePasswordView` ends the Account's other sessions and app tokens, `ResetPasswordView` ends every session and removes every passkey (audited like a removal, ADR 0056: a passkey added by someone who knew the old password signs in alone; a signed-in password change keeps them), and TOTP and passkey removal (`ManageTOTPView.delete`, `ManageWebAuthnView.delete`) end the other sessions, each through `apps.accounts.sessions` in the change's transaction. In the admin, Django cycles the acting staff session's key on both password paths, even when staff set another Account's password, so `end_sessions_after_password_change` first moves the acting session's row to the new key; then a staff member's own change ends their other sessions, and setting another Account's password ends all of that Account's sessions. A reset answers signed out when it ended its own session. Only sessions with a `UserSession` row are ended that way; a password change ends the rest through Django's session auth hash. Keep `ACCOUNT_LOGOUT_ON_PASSWORD_CHANGE` False, so the changing session stays.
- Session list (ADR 0047): `allauth.usersessions` with `USERSESSIONS_TRACK_ACTIVITY` False. OPEN's `SessionsView` (`apps/accounts/session_views.py`, both clients) lists sessions by `public_session_id` and ends the ones a player names by those ids, purging dead rows first and refusing any other id with fixed text. A `UserSession` row holds the IP address and user agent only while its session lasts: logout deletes it (`forget_session_on_logout`), ending a session deletes it, and `sweep_sessions` (every 15 minutes, default queue) deletes expired sessions and every row whose session is gone or expired. allauth's UserSession admin is unregistered. These views look up no Account by email.
- Audit (ADR 0047): a headless password change, a first password set, and a reset from a key record one `password.change` event (`after` `{"method": "change"}`, `{"method": "set"}`, or `{"method": "reset"}`), and each session a player ends one `session.end` event (`after` `{"current": bool}`), actor and target the Account, in the change's transaction. Never put an IP address, user agent, or session key in either.
- In tests, drive the flows through the helpers in `apps/accounts/tests/headless.py`. allauth's rate limits use the cache: the accounts tests clear it in an autouse fixture, and any other test that drives allauth's flows must clear it too.
