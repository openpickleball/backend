## Ratings

ADR 0025 records these decisions. Rating changes are a security-sensitive area (hard rule 8).

- Write `RatingState`, `RatingHistory`, and `RatingReplay` only through `apps.ratings.services`: `apply_rating()` and `record_replay()`, and the replay's private `_remove_rating()`, the only path that deletes a `RatingState` (see Replays). `RatingHistory` and `RatingReplay` rows are append-only: the ORM refuses (`RatingHistoryImmutable`) to save an existing row, to delete one, and `QuerySet.update`, `delete`, `bulk_update`, and an upsert, through the default and base managers. Save a `RatingState` only through `apply_rating()` (the ORM does not refuse a plain `save()` or `create()`). The ORM refuses (`RatingStateWriteRefused`) to delete one, insert it in bulk (`bulk_create`), or change it in bulk. `bulk_create` of history and replay rows still inserts, but it skips the services' checks and Audit Event, so never use it outside tests. Raw SQL and `loaddata` are not guarded.
- Store what the engine returns (hard rule 2): values come from `engine_adapter.rating_summary()`. Never compute or round a rating in the backend, and compare stored values exactly (no tolerance) when deciding whether anything changed.
- Every rating change records one `rating.change` Audit Event in the same transaction, with no actor, targeting the `RatingState`: `before` is the old values (None for a new state), `after` is the new values plus the `kind`, the Match's OPEN Code, the replay's id, and the player's OPEN Code (`player`, so the data export finds a state's events after a replay removes it, ADR 0051). For a replay's removal of a rating, the whole `after` is None, and its `removed` history row names the replay. An apply whose values equal the stored state writes nothing and returns None, and so does a live update when that Match already updated that player in that format (a redelivery, even after an engine or spec version change). A partial unique constraint allows one live update row per player, format, and Match. This guard covers live updates only: a redelivered replay change after a newer live update writes another history row and replaces the live update's values, so ordering replay changes against live updates, a redelivered replay task included, is the replay caller's job: `replay_ratings()` (see Replays).
- `apply_rating()` refuses (`RatingApplyError`, fixed text) a summary for another player, an unknown format, a live update without its Match or with a replay, a replay change without its replay or with a Match or a delta, an unsaved record, a Match the player did not play in, a live update for a Match that does not count (`Match.objects.counted()`, hard rule 8), a live update in a format the Match does not count in (a doubles Match counts in its own format and in overall `doubles`), and a replay change whose summary does not come from its replay (the summary's `calculated_as_of`, `config_version`, `params_version`, and `parameter_fingerprint` must equal the replay's, with no live updates since). Values the models refuse raise `ValidationError` before any write. The database also refuses a `rating`, `rd`, or `delta` that is not finite (NaN or infinity).
- A live update stores the installed engine's version and `OPEN_RATING_SPEC_VERSION`. A replay change stores its `RatingReplay`'s versions, and its summary must match the replay's provenance, so a replay row never disagrees with its replay.
- `reliability` is OPEN-earned, and `imported_reliability` is stored apart (hard rule 5). `provisional` is True when the rating holds live updates not yet replayed, or was never replayed (hard rule 3). `established` is the engine's other label. Every stored rating is a demonstration rating while the engine is a demonstration package; every rating in an API response carries `demonstration: true` (`DEMONSTRATION_RATINGS` in `apps/ratings/schemas.py`).
- `OPEN_RATING_SPEC_VERSION` (`config/settings.py`) is a constant, `"1.0.0rc1"`, from the openpickleball/rating-spec tag `v1.0.0rc1` (the project owner's choice). Bump it when rating-spec tags `v1.0.0`, and only for a new rating-spec tag, followed by the recompute (`recompute_ratings`, see Recompute). It is the default spec version: `record_replay(spec_version=...)` takes another, which the recompute passes (only the setting's own value, when it writes).
- `RatingState.player`, `RatingHistory.player`, `match`, and `replay` use `PROTECT`: a Player with a rating, a Match that caused a rating change, and a replay that produced one cannot be deleted. Account deletion leaves ratings as they are (see Account deletion).
- `apply_rating()` locks the Player row first with `FOR NO KEY UPDATE` (`select_for_update(no_key=True)`), so applies for one player serialize (a first apply included) without blocking inserts of rows that point at the Player, such as `record_match()`'s Match Participants. Keep it `no_key`: a plain `FOR UPDATE` conflicts with their `FOR KEY SHARE` lock. Then it locks the state row. The locks last until the outermost transaction ends. The callers (the live update and the replay) own the transactions, the order of replays and live updates, and the lock order across players.
- In tests, build plain engine results with `rating_summary()` and `replay_provenance()` in `apps/ratings/tests/factories.py`, and go through the services.

### Live updates

ADR 0027 records these decisions.

- Confirming a Match (`match_confirmed`) queues `apps.ratings.tasks.update_ratings_for_match` on the `ratings` queue with the Match's row id only, through `transaction.on_commit()` in `apps/ratings/receivers.py`. Only a broker error on publish (kombu's `OperationalError`, or an `OSError`) is caught, and it is logged by id and error class only. Keep the catch that narrow and the callback not `robust`, so an eager task's failure in tests raises instead of hiding. The receiver does not check `counted()` itself: the service checks it, twice. A broker error also stores a replay request (see Replays), so the next replay rates the Match. `match_changed` queues no live update: it requests a replay.
- `update_ratings_for_match()` (`apps/ratings/services.py`) runs in one transaction. It writes nothing for a missing Match, a Match not in `Match.objects.counted()`, a Match that the stored snapshot already holds (a redelivery, or a Match a replay counted), and a Match the engine does not count (its snapshot is not saved, so the engine does not reserve its id). It returns a `LiveUpdateOutcome`.
- Lock order: the `EngineSnapshot` row for the loaded config (`SELECT ... FOR UPDATE`, created with `get_or_create` when new), then the Match's Players by row id (`FOR NO KEY UPDATE`), then the Match row `FOR SHARE` (raw SQL, since Django has no share mode), then `apply_rating()`'s state rows. The service checks `Match.objects.counted()` again under the Match row's share lock, since a Match can be voided or held while it waits, and the share lock makes a void, dispute, or edit (which take the row `FOR UPDATE`) wait until the live update commits. A new hold is not blocked (the near-duplicate flag insert never locks the earlier Match's row), so a Match held during a live update can still be rated live; `match_changed` (`hold`) and the replay correct it. Every live update for one config serializes on the snapshot row, and so does the replay, which takes it first too.
- A Match played before any participant's stored `last_played` in a format it updates (its own, and overall `doubles` for a doubles Match), or one the engine reports `late` (or `parent.late`), changes no rating and goes to `schedule_replay(players, earliest_date)`, which logs the players' OPEN Codes and the date and stores a replay request. Never log a name there. Before this and the history checks, under the locks, the service returns `unchanged` when the stored snapshot already holds the Match (`engine_adapter.snapshot_holds_match()`, for example after a replay counted it), and a Match with a live update history row that the snapshot no longer holds (a replay dropped it while it was disputed or held, and it counts again) goes to `schedule_replay` and returns `replay_needed`.
- A live update that the snapshot cannot continue changes no rating, calls `schedule_replay`, and returns `replay_needed`: a participant's stored rating in a format the Match updates names another `parameter_fingerprint` than the loaded config's, or the snapshot is empty while a participant already has a rating in those formats, or the stored snapshot's `config_fingerprint` or `config_version` differs from the loaded config's (an engine upgrade; a new empty row is not checked), or a Match in the confirmed Match's `corrects` chain has a live update history row (a correction of a live-rated Match; every player in the chain goes to the replay, from the chain's earliest date). Never let a live update rate a player from an empty engine when they already have a rating.
- `EngineSnapshot` holds `RatingEngine.to_snapshot()` JSON, one row per parameter fingerprint. Write it only through the live update, the replay, and the recompute (`_snapshot_row()` creates it empty, `_save_engine_snapshot()` saves it), in the same transaction as the rating changes. The ORM refuses (`EngineSnapshotWriteRefused`) to delete one, insert it in bulk, change it in bulk, or upsert it. Raw SQL and `loaddata` are not guarded. An engine upgrade that changes the config sends live updates to `replay_needed`, and one that changes only the snapshot schema makes `from_snapshot()` raise, until a replay or the recompute rebuilds the snapshot.
- An error while recording or applying is logged with the Match's row id and error class only (never the error's text, never `logger.exception`), then re-raised, so the transaction rolls back. The task (bound) replaces any error, in a worker, with a fixed-text `LiveUpdateFailed` (`from None`, holding only the Match id and error class) after one log line, so Celery's worker log never holds the original text; in eager mode (`self.request.is_eager`) the original error propagates. The task has no retries: in a worker it stores a replay request in its own transaction before it raises, so the next replay rates the Match.
- Engine calls for a live update stay in `engine_adapter.record_live()`, which returns a plain `LiveUpdate`. It passes `as_of` to `player_summary()` explicitly, since the engine refuses no `as_of` before any replay.
- In tests, the task runs eagerly once on_commit callbacks run (`django_capture_on_commit_callbacks(execute=True)`), so any test that confirms a Match and runs its callbacks also runs a live update.

### Replays

ADR 0028 records these decisions.

- Every recalculation is a full replay of `Match.objects.counted()` (`replay_ratings()` in `apps/ratings/services.py`, through `engine_adapter.run_replay()`), as of `replay_as_of()`: today's UTC date, or the latest counted `played_on` when later. It never resumes from a checkpoint. The earliest affected date is for the log only.
- A change asks for one through `request_replay()`, which stores a `RatingReplayRequest` (earliest date and reason; no Player) in the caller's transaction and, after commit, queues `apps.ratings.tasks.replay_ratings` (no arguments) with a countdown of `RATING_REPLAY_DELAY_SECONDS`. Callers: the `match_changed` receiver in `apps/ratings/receivers.py`, `schedule_replay()`, the live update receiver's broker-error branch, the live update task's worker failure path, and `decay_reliability()` (reason `scheduled`). The `match_changed` receiver only inserts that row: the workflow holds Match locks there, so it must never take the snapshot row. Every `MatchChange` value must be a `ReplayReason` value (a test checks it), or the receiver raises and rolls the change back.
- `replay_ratings()` runs only while a request is pending, so quick changes share one replay and a redelivered task writes nothing. It checks for a request without a lock, then, in one transaction, locks the `EngineSnapshot` row, reads the requests again, reads the ledger, stores the `RatingReplay`, locks every Player it rated or that has a rating (one query, by row id), applies each rating through `apply_rating(kind=replay)`, removes each rating it no longer produces, saves its snapshot on the row, and deletes exactly the requests it read. It never locks a Match row. A failure rolls it all back and the requests stay. Keep the snapshot row first in every path that writes ratings.
- A removed rating: `_remove_rating()` appends a `removed` history row (names the replay, no Match, no delta, the removed values), records a `rating.change` Audit Event with the old values as `before` and `after` None before the delete, then deletes the `RatingState`. `apply_rating()` refuses kind `removed`.
- Errors are logged by class only and re-raised. In a worker the task replaces them with a fixed-text `ReplayFailed`; it has no retries. A beat entry (`replay-ratings`, every 15 minutes) runs the task, which does nothing when no request is pending. Nothing replays without a request, apart from the recompute (see Recompute), which an operator runs.
- Reliability decay is the scheduled replay (ADR 0060). The engine measures inactivity at a replay's date, so the backend computes nothing (hard rule 2). `decay_reliability()` (`apps/ratings/services.py`) stores one `scheduled` request through `request_replay()` when a rating is stored and either no replay has run or the latest `RatingReplay.as_of` is at least `engine_adapter.replay_interval_days()` (the engine config's published schedule, 7 days in `v1`) before `replay_as_of()`. It returns a `DecayOutcome`: `requested`, `not_due`, `already_requested` (a `scheduled` request is pending; requests for other reasons do not block it), or `no_ratings`. It takes no lock and logs the outcome and dates only. The `apps.ratings.tasks.decay_reliability` task runs it (errors as for the replay task, fixed-text `ReplayFailed` in a worker), from the daily beat entry `decay-reliability` at 03:45 UTC, after the two match expiry tasks. Each changed rating then writes its `replay` history row and `rating.change` Audit Event through the replay, as for any replay.
- A held or disputed Match stays out of ratings after the next replay until the Event's verified Organizer settles the dispute (ADR 0034), both Matches of every open flag holding it are vouched for (`vouch_for_match`, ADR 0034), the last dispute is withdrawn and the Match returns to confirmed (which sends `match_confirmed`, #267), a participant's correction voids a disputed self-reported Match (#267; the pending correction counts once the other team confirms it), or until the dispute or hold period ends and `expire_disputes_and_holds` voids the disputed or newer held Match (ADR 0034). Resolving a flag sends `release` for each Match that counts again, which asks for a replay. A dispute resolved as confirmed sends `match_confirmed`, which queues a live update; one resolved as voided stays out.
- In tests, eager tasks ignore the countdown, so a replay runs as soon as on_commit callbacks run. A test that needs coalescing, or a live update before the replay, holds the callbacks or replaces `tasks.replay_ratings.apply_async`.

### Recompute

ADR 0058 records these decisions.

- `manage.py recompute_ratings` (`apps/ratings/management/commands/recompute_ratings.py`) calls `recompute_ratings()` in `apps/ratings/services.py`: a full replay of `Match.objects.counted()`, as of `--as-of` (default `replay_as_of()`), whether or not a replay request is pending. A write shares `_replay_and_write()` with `replay_ratings()`: one transaction, the `EngineSnapshot` row locked first, then the same writes as a replay. Never split it into batches or separate transactions: the stored ratings and the snapshot must change together (ADR 0028).
- A write deletes the replay requests it read after taking the snapshot lock; later ones stay.
- `--dry-run` replays and compares with the stored ratings (`_planned_changes()`, which must decide changed or unchanged exactly as `apply_rating()` does, and list the same changes in the same order as `_apply_replay()`; a test compares them), takes no lock, and writes nothing, not even a snapshot row. It is a preview, not one consistent read.
- Only a dry run takes `--format`, an `--as-of` before the latest counted `played_on` or after `replay_as_of()`, or a `--spec-version` other than `OPEN_RATING_SPEC_VERSION`. A write refuses them (`RecomputeRefused`, fixed text) before writing.
- The output and the log hold counts and dates only (at verbosity 2, counts per rating format), never a player: a player's code next to a category format would reveal their gender division. An error is logged by class only, and the command prints only its class.
