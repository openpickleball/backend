## Audit log

- Write an `AuditEvent` only through `apps.audit.services.record_event()`, inside the same `transaction.atomic()` as the change it records. Record a delete before calling `delete()`. Build `before` and `after` with `snapshot(instance, fields)`, which takes an explicit field list, so a password hash is never captured by accident. `record_event` redacts values under sensitive key names, but never put a secret, token, recovery code, or the value of an identifying personal data field (ADR 0009) in `before`, `after`, or `reason`.
- Audit rows are append-only. In app code the ORM refuses every change or delete. A database trigger (migration `0002_append_only`) refuses `UPDATE`, `DELETE`, and `TRUNCATE` of a non-empty table. Inside a migration, a historical model gets no ORM guard, so only the trigger protects the rows. The trigger does not stop the table's owner or a database superuser, who can disable it. The runtime database role must not own the table: #103 must make sure of that (a comment there asks for it).
- Every admin change is audited (#101, ADR 0045). `OpenAdminSite.register` puts `AdminAuditMixin` (`apps/audit/admin_audit.py`) first in the bases of every registered admin, OPEN's and third-party ones. Each add, change (only when a field changed), and delete records `admin.add`, `admin.change`, or `admin.delete` in the change's transaction, actor `request.user` (none when a delete removes the acting Account); `values` hold only the fields `AUDIT_VALUE_FIELDS` lists for the model (no identifying value, hash, secret, or token), and `admin.change`'s `after.fields` names every changed field. Each custom action records one `admin.action` per selected object in one transaction with the action, unless it is marked `@audited_by_service` (its service records per object; the bulk voids must never run inside an outer transaction) or is `delete_selected`. An admin whose saves and deletes go through an audited service sets `audited_by_service = True` and records no generic model events (the Event and grant admins). An admin whose `delete_queryset` deletes each object through `delete_model` sets `deletes_each_through_delete_model = True`, so each delete records its `admin.delete` in that object's own transaction instead of one around the selection (the Account admin, #317). A new admin needs nothing more, unless a model field's values may be recorded (add it to `AUDIT_VALUE_FIELDS`) or an action audits itself (mark it `@audited_by_service`).
- A new action type is a new `AuditAction` value plus its generated migration. The issue that adds a feature records that feature's events, with a test.
- A staff reveal of a Player's personal data in the admin records one `player.personal_data_view` event (ADR 0046): the staff Account as actor, the Player as target, and `after={"fields": [...]}` with the field names only, never a value. Every reveal records one, before the values are shown.
- `flush` (and so the teardown of a transactional test) fails once the audit table has a row. Tests that record events should run in a transaction that rolls back (the default `django_db` mark).
- Organizer Members, Club Roles, Club Organizer Grants, and Organizer Application Grants decide who may submit counted matches, so each add, change, and removal made through the admin or a service records one Audit Event with an explicit actor (#158, ADR 0033): `organizer_member.*`, `club_role.*`, `club_organizer_grant.*`, and `organizer_application_grant.*`, each with `add`, `change`, and `remove`. Change these rows only through `apps.audit.access`: `save_access_row(row, actor=...)` records an add or a change in its own atomic block (nothing when the stored values are unchanged, nothing when the save raises), `delete_access_row(row, actor=...)` records the removal before the delete, and `record_cascaded_removals(objs, actor=...)`, called in the delete's transaction just before it, records a removal for each of these rows a delete of other rows will cascade to. `before` and `after` come from each model's `audit_values()`: the role, the OPEN Codes, the Account's row id (an Account has no other identifier that is not its email), and the application's `client_id`, never an email or an Organizer's name.
- `AccessAuditAdminMixin` (`apps/audit/admin_access.py`) goes first in the declared bases (after the `AdminAuditMixin` that registration adds) of every admin that saves or deletes these rows or deletes a row that cascades to them (Club, Organizer, Partner Application, and Account admins, and the two grant admins). It routes `save_model`, `delete_model`, `delete_queryset` (so `delete_selected`), and the inline formsets through those functions with `request.user` as actor. A new admin of that kind adds it. When a delete removes the acting Account itself, every removal it records has no actor (other selected Accounts' rows included), since an event naming a deleted Account fails the delete at commit.
- Known gap: a plain ORM save or delete of these rows, a cascade from a Club, Organizer, Partner Application, or Account deleted outside the admin (the ORM, a shell, a later service that does not call `record_cascaded_removals`), and raw writes (`bulk_create`, `QuerySet.update`, `bulk_update`, raw SQL, `loaddata`) record nothing. Factories record nothing. A service that changes these rows or deletes their parents (`delete_account`, a later self-service API) calls these functions with its actor.
- An event's actor is an Account (`actor_user`), a Partner Application (`actor_application`, `record_event(actor_application=...)`), both, or nobody. `actor_user`, `actor_application`, and `target_content_type` use `PROTECT`: an Account or application that has acted cannot be hard-deleted (deactivate an Account; #29 revokes applications), and a content type an event points at cannot be removed. django-oauth-toolkit's `PartnerApplication.user` cascades, so an Account whose application has acted cannot be hard-deleted either. The same holds for an Account or application that submitted a Match or a Submission Batch (see Matches), and for an Account that reported an Organizer (its `organizer_report.create` event), so Account deletion deletes that Account's report rows itself (`delete_reporter_reports`). Every Account that changed or used its MFA is the actor of its `mfa.change` events, every staff Account that changed anything in the admin is the actor of its `admin.*` or `password.change` events, every Account that changed, set, or reset its password or ended a session is the actor of its `password.change` or `session.end` events (ADR 0047), every Account that requested or downloaded a data export is the actor of its `data_export.*` events (ADR 0051), and every Account that created, renamed, invited to, or requested verification of an Organizer, or accepted an invite, is the actor of its `organizer.create`, `organizer.change`, `organizer_invite.create`, `organizer_verification_request.create`, or `organizer_member.add` events (ADR 0054), so none of them can be hard-deleted: Account deletion keeps such a row, cleared (see Account deletion).
