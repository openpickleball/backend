## Clubs and organizers

- The verified Organizer is the only trusted submitter (ADR 0021): its submissions count as confirmed, so verification is a security-sensitive area (hard rule 8). A Club is never verified and gives no submission authority. Change `Organizer.verified_at` and `verified_by` only through `apps.clubs.services.verify_organizer()` and `unverify_organizer()`. They refuse any actor but an active Account with the `clubs.verify_organizer` permission that is not a member of that Organizer, and record one Audit Event when the status changes. An unverify that changes the status also closes the Organizer's open Organizer Reports in the same transaction (see below). The `Organizer.save()` docstring lists the writes that skip them; `bulk_create` and `loaddata` skip them too (see Public identifiers).
- While an Organizer is verified, the Account that verified it cannot become its member (`bulk_create` and `QuerySet.update` skip this check). A verified Organizer cannot be deleted: unverify it first (`QuerySet.delete()` skips this check). An Organizer with an Event, a Partner Application, an Organizer Report, or an Organizer Verification Request (open or closed) cannot be deleted either, even through `QuerySet.delete()` (see Events, Partner applications; `OrganizerReport.organizer` and `OrganizerVerificationRequest.organizer` use `PROTECT`). A Club with a Match or a Submission Batch cannot be deleted (`Match.club` and `SubmissionBatch.club` use `PROTECT`).
- `ClubRole.role` has one value, admin (`ClubRoleKind`): a Club admin manages the Club and its Club Organizer Grants, and gives no authority to submit, confirm, or change a match. Organizer Members keep both roles (`MemberRole`: admin and match manager). A `ClubOrganizerGrant` (Club, Organizer) is a Club's consent for that Organizer to name it on Events and matches; it gives no trust, and both links cascade. Club admins manage them through Club self-service (#230, ADR 0055, below), and staff through the admin.
- `OrganizerMember.account` uses `PROTECT`, so an Account that is a member cannot be hard-deleted. `Organizer.verified_by` uses `PROTECT` while the Organizer is verified; after that, the verify event's actor keeps the Account row (Audit log). `ClubRole.account` cascades.
- Every Organizer's name may be a person's name, so it is an identifying field. Account deletion removes the Account's memberships and Club Roles through `apps.audit.access`, and an Organizer whose only member it is gets the placeholder name `REMOVED_ORGANIZER_NAME` with an `organizer.name_remove` Audit Event (ADR 0048), and its verification request statements are blanked.
- The admin's verify and unverify actions need a reason typed next to the action menu (`ReasonActionForm`, `apps/audit/admin_actions.py`), stored in the Audit Event; a blank one, or one over 1000 characters, changes nothing. The services still accept an empty reason from other callers.
- An Organizer Report (ADR 0037, #271) is a player's report of a verified Organizer to OPEN Moderators. Change one only through `apps.clubs.reports`: `report_organizer()` (any active Account with a Player, a verified Organizer, one reason from `OrganizerReportReason`, no free text), `close_report()` (an Account `may_close` allows: active, with `clubs.verify_organizer`, and not a member of the Organizer; this is the organizer verification rule, not `is_moderator`; with a required reason), and `close_open_reports()`, which only `unverify_organizer` calls, under its Organizer lock. Each create and close records one Audit Event (`organizer_report.create`, `organizer_report.close` with `after.rule` `moderator` or `organizer_unverified`) in the same transaction. A partial unique constraint allows one open report per Account and Organizer. A report changes no Match, flag, rating, or Organizer field: moderators act only through `unverify_organizer` and the bulk void. Lock order: `report_organizer` takes the Organizer row `FOR NO KEY UPDATE` and `unverify_organizer` takes it `FOR UPDATE`, each before any report row, so a report never stays open after an unverify; `close_report` locks only the report row and never the Organizer. Keep both orders.
- The reporter is stored only on the report row and as the create event's actor. Never put them in an API response, an email, an Audit Event value, or anything an Organizer member can reach. The one exception is the reporter's own data export (ADR 0051), which lists their own reports without the closer or the close reason. The report admin shows them only as their Player's OPEN Code; the generic Audit Event admin shows every event's actor (the email) to holders of `audit.view_auditevent`, which no Moderator or Organizer role holds. `OrganizerReportAdmin` leaves out every report on an Organizer the viewer is a member of, and the Organizer page's "Moderator review" section shows only to an Account with `clubs.verify_organizer` and `clubs.view_organizerreport` that is not a member of that Organizer. `OrganizerReport.__str__` names neither the Organizer nor the reporter, since the Account admin's delete page lists it. The review (`organizer_review()`) counts, over `ORGANIZER_REVIEW_WINDOW_DAYS`, the Audit Events of Matches on the Organizer's Events: `match.dispute`, `match.dispute_withdraw`, `dispute.outcome` by `after.status`, and `match.expire` with `after.rule` `dispute`, plus `MatchFlag` rows whose reason is in `SIGNAL_FLAG_REASONS` (`apps/matches/models.py`: `unusual_submission`, ADR 0049, with the `player_daily_matches` rule from ADR 0052). A `player_daily_matches` flag can come from other players' pending self-reports that name the same player, so a third party can raise an Organizer's count (ADR 0052). Keep those Audit Events' keys as they are: the review reads them.
- Every link on these models overrides Django's foreign key messages, which name the row id or the submitted value, with fixed text (`_LinkMessagesModel`, #162). Give a new link the same.
- `list_my_organizers` (`GET /api/v1/organizer/organizers`, ADR 0050) returns the signed-in Account's own memberships: each Organizer's OPEN Code, name, `verified`, `verification_requested` (an open Verification Request, ADR 0054), and the Account's role, verified or not, empty for a non-member. It reads only the Account's own `OrganizerMember` rows and never lists another member. `verified` is the Organizer's state, not Organizer authority (which also needs MFA, ADR 0043): an authority flag, if one is added, reuses `apps.matches.permissions` and `apps.accounts.mfa`.
- The permission rules that use these roles are in `apps.matches.permissions` (see Matches). In tests, build a verified Organizer with `verify()` or `verified_organizer()` (`apps/clubs/tests/factories.py`), which go through `verify_organizer()` and so record an Audit Event (use a test transaction that rolls back, see Audit log). Changes to members, roles, and grants made through the admin or the self-service services record Audit Events (see Audit log); the factories record none. Build grants with `ClubOrganizerGrantFactory` (`apps/clubs/tests/factories.py`) and `OrganizerApplicationGrantFactory` (`apps/partners/tests/factories.py`).
- Organizer self-service (#229, ADR 0054) goes only through `apps.clubs.self_service`. `create_organizer` needs an active Account with a verified login address (`apps.accounts.addresses.has_verified_login_address`, only the row for `User.email`), refuses past `ORGANIZER_CREATE_LIMIT_PER_ACCOUNT` admin memberships, and makes an unverified Organizer with the creator as its only admin. Every other function acts for an admin member only: an active Account with MFA whose membership is admin, read from the database (`_admin_organizer`); anyone else gets `NotFound`, the same as an unknown Organizer. Creating, inviting, accepting, and requesting verification never verify anything: authority still comes only from `verify_organizer()`. On these paths an Organizer always keeps one active admin with MFA (`Conflict`); Account deletion and the staff admin can still leave one without an admin. A self-service rename of a verified Organizer is refused (`Conflict`, under the Organizer lock): a moderator verified it under its name, so a moderator unverifies it first, or staff rename it in the admin. Once an Organizer is verified, an admin's invite gives the new member trusted-submitter authority with no moderator review, after its New Member Hold (below). Membership changes go through `apps.audit.access` with the acting Account. Lock order: the acting Account (`hold_active_account`, or `FOR NO KEY UPDATE` in the create), then the Organizer row `FOR UPDATE`, then invite and membership rows, so the last admin count runs in turn; keep it.
- Organizer Invites (`clubs.OrganizerInvite`) use the generic rules in `apps/clubs/invites.py` (`InviteModel`, also used by `ClubInvite`, ADR 0055): one invite per Organizer and normalized address, only the key's SHA-256 stored, found by that hash while unexpired (`ORGANIZER_INVITE_DAYS`), and accepted only by the Account whose login address is the invited one and verified, with a Player, and not the verifier of the verified Organizer, while the invite's sender still has admin authority there, by `_is_admin`'s rule (active, admin role, MFA; checked under the Organizer lock). Demoting or removing an admin through self-service deletes the invites it sent there in the same transaction; a staff change in the admin leaves them, and the accept check refuses them. Every accept refusal is `NotFound`. Inviting a member's address stores and sends nothing; any other address replaces its earlier invite and gets one email (`apps/clubs/emails.py`). At most `ORGANIZER_OPEN_INVITES_LIMIT` open invites per Organizer. An invite holds an address: it has no admin, never appears in a response, an Audit Event, or a log line, and is deleted on accept, by the daily `sweep_organizer_invites` task, when its sender is demoted or removed through self-service, with its Organizer, and at Account deletion.
- An Organizer Verification Request (`clubs.OrganizerVerificationRequest`) is an admin member's request that moderators verify the Organizer, with a statement (at most 1000 characters) shown only to moderators. One open request per Organizer (a partial unique constraint); a verified Organizer cannot request. `verify_organizer()` closes the open request under its Organizer lock (`close_open_verification_requests`, rule `verified`); a moderator closes one without verifying through `close_verification_request()` (`may_close`, a required reason, rule `moderator`), which locks only the request row. Each create and close records one Audit Event; none holds the statement. `OrganizerVerificationRequestAdmin` is read-only for holders of `clubs.view_organizerverificationrequest` (the Moderator group) and leaves out requests on an Organizer the viewer is a member of.
- Club self-service (#230, ADR 0055) goes only through `apps.clubs.club_self_service`, with its operations on `club_router` (`apps/clubs/club_api.py`, mounted at `/api/v1/clubs`) and `list_organizer_club_grants` on `organizer_router`, whose service is `apps.clubs.self_service.list_club_grants` (an Organizer admin action, through `_admin_organizer`). `create_club` needs an active Account with a verified login address and does not need MFA, refuses past `CLUB_CREATE_LIMIT_PER_ACCOUNT` admin Club Roles, and makes the creator the only admin. Every other function but `accept_club_invite` acts for a Club admin only: an active Account with MFA and an admin Club Role there, read from the database (`_admin_club`); anyone else gets `NotFound`, the same as an unknown Club. A Club admin never gains authority to submit, confirm, or change a match. A self-service name change is refused (`Conflict`) while any committed Event or Match names the Club (read under the Club lock; a first Event or match committing at the same moment may miss it, accepted); staff rename it in the admin. On these paths a Club always keeps one active admin with MFA; removing an admin deletes the invites it sent there. Club Invites (`clubs.ClubInvite`) follow the Organizer Invite rules above (one per Club and address, key hash only, the accept checks and every refusal `NotFound`, no address anywhere), except that there is no role choice, no verifier rule, and no demotion, an admin's address gets nothing, and the sender's authority is `_is_club_admin`, checked under the Club lock after holding the sender's Account; they use `CLUB_INVITE_DAYS`, `CLUB_OPEN_INVITES_LIMIT`, the daily `sweep_club_invites`, and the link `{FRONTEND_URL}/clubs/invites/{key}`. A grant may go to any Organizer, verified or not, by OPEN Code; the Club's list shows Organizer codes only, never a name. Lock order: the acting Account, then (on accept) the sender's Account, then the Club `FOR UPDATE`, then (on a grant) the Organizer `FOR KEY SHARE`, then invite, role, and grant rows. Account deletion never locks a Club; keep it so, or it cycles with a grant.
- Admin security (#232, ADR 0057). Step-up: `invite_organizer_member`, `change_organizer_member_role`, `remove_organizer_member`, `request_organizer_verification`, `invite_club_admin`, `remove_club_admin`, `grant_club_organizer`, `remove_club_organizer_grant`, and `create_results_file` call `config.auth.require_step_up` right after the MFA check and before any lookup (see Authentication); a new admin operation that changes who may act does the same. New Member Hold: `accept_invite` sets `OrganizerMember.hold_ends_at` to now plus `ORGANIZER_NEW_MEMBER_HOLD_HOURS` when the Organizer is verified (read under its lock); staff adds and `create_organizer` set none. While it is in the future the member has no Organizer authority and no admin authority: every rule that grants either (`apps.matches.permissions._account_acts_for`, the `vouchable_holds` and `organizer_disputes` queries, the match notice recipients, and `self_service._is_admin`, so also `_sender_still_admin`) adds `apps.clubs.models.not_held()`. Keep every new authority rule on that helper. A moderator ends holds early only through `apps.clubs.services.end_member_holds` (`may_close`, a required reason, the Organizer lock first, one `organizer_member.change` per member through `save_access_row(..., reason=...)`), or the Organizer admin's "End new member holds" action. `audit_values()` adds `hold_ends_at` only when set. Admin roles: `OrganizerMember.clean()` and `ClubRole.clean()` refuse an admin role for an existing Account that is inactive or has no verified login address (`admin_account_refused`, fixed text on `account`), and `change_member_role` refuses such a promotion with `Conflict`; `save()` does not check it, so factories still work (`verify_login_address` in `apps/clubs/tests/factories.py` gives an Account the row). Removing TOTP is refused for the last Organizer admin with MFA (see Authentication). Security notices: `apps.clubs.notices` (see Email). Each access model's `access_notice` builds its notice; a new access model gives one.
