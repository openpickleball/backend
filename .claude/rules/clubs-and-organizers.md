## Clubs and organizers

- The verified Organizer is the only trusted submitter (ADR 0021): its submissions count as confirmed, so verification is a security-sensitive area (hard rule 8). A Club is never verified and gives no submission authority. Change `Organizer.verified_at` and `verified_by` only through `apps.clubs.services.verify_organizer()` and `unverify_organizer()`. They refuse any actor but an active Account with the `clubs.verify_organizer` permission that is not a member of that Organizer, and record one Audit Event when the status changes. An unverify that changes the status also closes the Organizer's open Organizer Reports in the same transaction (see below). The `Organizer.save()` docstring lists the writes that skip them; `bulk_create` and `loaddata` skip them too (see Public identifiers).
- While an Organizer is verified, the Account that verified it cannot become its member (`bulk_create` and `QuerySet.update` skip this check). A verified Organizer cannot be deleted: unverify it first (`QuerySet.delete()` skips this check). An Organizer with an Event, a Partner Application, an Organizer Report, or an Organizer Verification Request (open or closed) cannot be deleted either, even through `QuerySet.delete()` (see Events, Partner applications; `OrganizerReport.organizer` and `OrganizerVerificationRequest.organizer` use `PROTECT`). A Club with a Match or a Submission Batch cannot be deleted (`Match.club` and `SubmissionBatch.club` use `PROTECT`).
- `ClubRole.role` has one value, admin (`ClubRoleKind`): a Club admin manages the Club and its Club Organizer Grants, and gives no authority to submit, confirm, or change a match. Organizer Members keep both roles (`MemberRole`: admin and match manager). A `ClubOrganizerGrant` (Club, Organizer) is a Club's consent for that Organizer to name it on Events and matches; it gives no trust, and both links cascade. Only Django's admin manages grants until the Club self-service issue (#230) lands.
- `OrganizerMember.account` uses `PROTECT`, so an Account that is a member cannot be hard-deleted. `Organizer.verified_by` uses `PROTECT` while the Organizer is verified; after that, the verify event's actor keeps the Account row (Audit log). `ClubRole.account` cascades.
- Every Organizer's name may be a person's name, so it is an identifying field. Account deletion removes the Account's memberships and Club Roles through `apps.audit.access`, and an Organizer whose only member it is gets the placeholder name `REMOVED_ORGANIZER_NAME` with an `organizer.name_remove` Audit Event (ADR 0048), and its verification request statements are blanked.
- The admin's verify and unverify actions need a reason typed next to the action menu (`ReasonActionForm`, `apps/audit/admin_actions.py`), stored in the Audit Event; a blank one, or one over 1000 characters, changes nothing. The services still accept an empty reason from other callers.
- An Organizer Report (ADR 0037, #271) is a player's report of a verified Organizer to OPEN Moderators. Change one only through `apps.clubs.reports`: `report_organizer()` (any active Account with a Player, a verified Organizer, one reason from `OrganizerReportReason`, no free text), `close_report()` (an Account `may_close` allows: active, with `clubs.verify_organizer`, and not a member of the Organizer; this is the organizer verification rule, not `is_moderator`; with a required reason), and `close_open_reports()`, which only `unverify_organizer` calls, under its Organizer lock. Each create and close records one Audit Event (`organizer_report.create`, `organizer_report.close` with `after.rule` `moderator` or `organizer_unverified`) in the same transaction. A partial unique constraint allows one open report per Account and Organizer. A report changes no Match, flag, rating, or Organizer field: moderators act only through `unverify_organizer` and the bulk void. Lock order: `report_organizer` takes the Organizer row `FOR NO KEY UPDATE` and `unverify_organizer` takes it `FOR UPDATE`, each before any report row, so a report never stays open after an unverify; `close_report` locks only the report row and never the Organizer. Keep both orders.
- The reporter is stored only on the report row and as the create event's actor. Never put them in an API response, an email, an Audit Event value, or anything an Organizer member can reach. The one exception is the reporter's own data export (ADR 0051), which lists their own reports without the closer or the close reason. The report admin shows them only as their Player's OPEN Code; the generic Audit Event admin shows every event's actor (the email) to holders of `audit.view_auditevent`, which no Moderator or Organizer role holds. `OrganizerReportAdmin` leaves out every report on an Organizer the viewer is a member of, and the Organizer page's "Moderator review" section shows only to an Account with `clubs.verify_organizer` and `clubs.view_organizerreport` that is not a member of that Organizer. `OrganizerReport.__str__` names neither the Organizer nor the reporter, since the Account admin's delete page lists it. The review (`organizer_review()`) counts, over `ORGANIZER_REVIEW_WINDOW_DAYS`, the Audit Events of Matches on the Organizer's Events: `match.dispute`, `match.dispute_withdraw`, `dispute.outcome` by `after.status`, and `match.expire` with `after.rule` `dispute`, plus `MatchFlag` rows whose reason is in `SIGNAL_FLAG_REASONS` (`apps/matches/models.py`: `unusual_submission`, ADR 0049, with the `player_daily_matches` rule from ADR 0052). A `player_daily_matches` flag can come from other players' pending self-reports that name the same player, so a third party can raise an Organizer's count (ADR 0052). Keep those Audit Events' keys as they are: the review reads them.
- Every link on these models overrides Django's foreign key messages, which name the row id or the submitted value, with fixed text (`_LinkMessagesModel`, #162). Give a new link the same.
- `list_my_organizers` (`GET /api/v1/organizer/organizers`, ADR 0050) returns the signed-in Account's own memberships: each Organizer's OPEN Code, name, `verified`, `verification_requested` (an open Verification Request, ADR 0054), and the Account's role, verified or not, empty for a non-member. It reads only the Account's own `OrganizerMember` rows and never lists another member. `verified` is the Organizer's state, not Organizer authority (which also needs MFA, ADR 0043): an authority flag, if one is added, reuses `apps.matches.permissions` and `apps.accounts.mfa`.
- The permission rules that use these roles are in `apps.matches.permissions` (see Matches). In tests, build a verified Organizer with `verify()` or `verified_organizer()` (`apps/clubs/tests/factories.py`), which go through `verify_organizer()` and so record an Audit Event (use a test transaction that rolls back, see Audit log). Changes to members, roles, and grants made through the admin record Audit Events (see Audit log); the factories record none. Build grants with `ClubOrganizerGrantFactory` (`apps/clubs/tests/factories.py`) and `OrganizerApplicationGrantFactory` (`apps/partners/tests/factories.py`).
- Organizer self-service (#229, ADR 0054) goes only through `apps.clubs.self_service`. `create_organizer` needs an active Account with a verified login address (`apps.accounts.addresses.has_verified_login_address`, only the row for `User.email`), refuses past `ORGANIZER_CREATE_LIMIT_PER_ACCOUNT` admin memberships, and makes an unverified Organizer with the creator as its only admin. Every other function acts for an admin member only: an active Account with MFA whose membership is admin, read from the database (`_admin_organizer`); anyone else gets `NotFound`, the same as an unknown Organizer. Creating, inviting, accepting, and requesting verification never verify anything: authority still comes only from `verify_organizer()`. An Organizer always keeps one active admin (`Conflict`). Membership changes go through `apps.audit.access` with the acting Account. Lock order: the acting Account (`hold_active_account`, or `FOR NO KEY UPDATE` in the create), then the Organizer row `FOR UPDATE`, then invite and membership rows, so the last admin count runs in turn; keep it.
- Organizer Invites (`clubs.OrganizerInvite`) use the generic rules in `apps/clubs/invites.py` (`InviteModel`, reused by #230): one invite per Organizer and normalized address, only the key's SHA-256 stored, found by that hash while unexpired (`ORGANIZER_INVITE_DAYS`), and accepted only by the Account whose login address is the invited one and verified, with a Player, and not the verifier of the verified Organizer. Every accept refusal is `NotFound`. Inviting a member's address stores and sends nothing; any other address replaces its earlier invite and gets one email (`apps/clubs/emails.py`). At most `ORGANIZER_OPEN_INVITES_LIMIT` open invites per Organizer. An invite holds an address: it has no admin, never appears in a response, an Audit Event, or a log line, and is deleted on accept, by the daily `sweep_organizer_invites` task, with its Organizer, and at Account deletion.
- An Organizer Verification Request (`clubs.OrganizerVerificationRequest`) is an admin member's request that moderators verify the Organizer, with a statement (at most 1000 characters) shown only to moderators. One open request per Organizer (a partial unique constraint); a verified Organizer cannot request. `verify_organizer()` closes the open request under its Organizer lock (`close_open_verification_requests`, rule `verified`); a moderator closes one without verifying through `close_verification_request()` (`may_close`, a required reason, rule `moderator`), which locks only the request row. Each create and close records one Audit Event; none holds the statement. `OrganizerVerificationRequestAdmin` is read-only for holders of `clubs.view_organizerverificationrequest` (the Moderator group) and leaves out requests on an Organizer the viewer is a member of.
