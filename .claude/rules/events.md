## Events

- An Event's `kind` is the Match Type its matches are recorded with (ADR 0035). Its values are the engine's `MatchType` values except `self_reported`, since self-reported matches have no Event (decision F1). Never add a value the engine lacks.
- An Event has no weight. The engine weights a match only by its Match Type and takes no per-event weight (openpickleball/engine#30), so never add or apply one in the backend (hard rule 2).
- An Event that names a Club needs that Club's `ClubOrganizerGrant` to the Event's Organizer (ADR 0021). `Event.clean()` (so the admin form) refuses a new Event, or a change of its Club or Organizer, without it, with fixed text; an Event whose stored Club and Organizer are unchanged is not checked again, so a Club that removes its grant does not block an unrelated edit. `objects.create()` and raw writes skip `clean()`, but `apps.matches.permissions` checks the Event's stored Club on every submission.
- `Event.organizer` and `Event.club` use `PROTECT`, so an Organizer or Club with an Event cannot be deleted. `Match.event` and `SubmissionBatch.event` use `PROTECT`, so an Event with a Match or a Submission Batch cannot be deleted.
- Event fields override Django's default messages that include the submitted value: an invalid choice or date, a foreign key that names no row (whose default names the row id), and a non-integer foreign key id (`_LinkMessagesModel`, in `apps/clubs/models.py`, which other apps' models share).
- A form that edits an Event subclasses `apps.events.admin.EventAdminForm`, and an override of its `clean()` calls `super().clean()`. The form gives `kind` a message without the value (a ModelForm's choice field repeats it), and its `clean()` clears a date that failed, so the model's order check does not compare the other new date with the stored one.
- A match with an Event must be played within the Event's stored dates (`outside_event_dates`, ADR 0052), checked on every new match and every `edit_match()` correction. Changing an Event's dates can refuse a later correction of an older match until the dates cover it again. Once a match names the Event, only the admin can change its dates (the organizer Event API refuses with 409).
- An Event's `kind` may change at any time; the change applies only to matches recorded after it, since each Match stores its own match type (see Matches, ADR 0035). Its `organizer` and its `club` cannot change once any Match, in any status, names the Event: `Event.save()` refuses either change and `Event.clean()` reports the same message. `Event.save()` locks an existing Event row `FOR UPDATE` on every save and compares the stored organizer and Club under that lock, and `record_match()` and `edit_match()` take the row `FOR KEY SHARE` at the start of their write transaction, right after the acting Account's own share lock (`hold_event()`; see Account deletion), check the submitter's or editor's permission again, and `record_match()` reads the Event's kind again. So an Event change and a match in flight run in turn (the foreign key is deferred, so it gives no order by itself). Keep both sides when changing either. Raw writes skip the lock.
- Save and delete an Event only through `apps.events.services`: `save_event(event, actor=...)` and `delete_event(event, actor=...)` record one Audit Event (`event.create`, `event.change` with only the changed fields, `event.delete`) in the same transaction, and nothing for a save that changes nothing or raises. The admin and the organizer Event API use them. A plain ORM save or delete (the factories included), and raw writes, record nothing.
- The organizer Event API (`apps/events/api.py`, mounted at `/api/v1/organizer/`, #125) lists the Events of every Organizer the signed-in Account is a member of (either role, verified or not). Only an Account that `apps.matches.permissions.can_manage_events` allows (an active member, either role, of the Event's Organizer while it is verified and while the member's Account has MFA) creates, changes, or deletes one, through `save_event()` and `delete_event()`. Create names the Organizer in the body and answers every refusal (an unknown or malformed code included) with one fixed 403 before it reads the Club. Change and delete check permission without a lock, answering a refused actor with the unknown-code 404, then lock the Event row `FOR UPDATE` and check again, so a refused actor never holds the lock. Change takes only `name`, `kind`, and the dates: `kind` may change at any time, while `name` and the dates change only while no Match names the Event (409). The name and dates rule is the API's own, from #125: the admin and the services do not apply it. A delete that a Match or Submission Batch protects gets 409.
- In tests, build Events with `EventFactory` (`apps/events/tests/factories.py`).
